## A. 当前阶段判断

当前是 FFA/Kill Race 已有可运行实现、CF 等待房间/TDM/聊天尚待实施的起点。本轮检查尚无 Docs/27 新契约，也未发现完整 CF Team/Chat 实现。不要从旧代码注释中的“Docs/27”推断新契约已完成。

实际接入点与风险：

- 后端 `RoomService` 创建即租 DS、签票；`RoomsController` 创建/加入返回连接 DTO；现有成员心跳为兼容空操作。CF 必须拆分等待房间与比赛租约，而非只添加 Ready 按钮。
- `ServerInstanceService` 已有事务、版本令牌、票据消费与断线清理。扩展比赛身份守卫，保留鉴权和一次性消费，不能换网络栈。
- `MatchRules` 是纯函数；`MatchLifecycle` 是状态机和跨端静态镜像。适合先做可独立测试的团队策略，再接生命周期，避免一次改完整个大类。
- `RoomConnectionGate` 仍要求地址/端口/票据；`AccountSession` 已有连接代际；`MatchSettlementFlow` 仍回大厅且个人击杀上限为 30。TDM 规则可达 150 团队杀，必须同步核查前后端结算限制与胜负来源，不可简单放开客户端提交上限。
- `GameplayInputGate`、菜单状态机及 UI DesignSystem 已存在。聊天增加独立输入占用原因，复用既有输入出口；不另建一套同时争夺输入/光标的管理器。
- `Game.Gameplay` 当前只引用 Core/InputSystem/FishNet；不要为 HTTP 聊天或 UI 倒置依赖，Account/UI 负责相应边界适配，Gameplay 保持网络玩法和纯策略。
- 历史记录为 EditMode 596/596、后端 96 过/1 跳过；上轮弹药补丁定向 14/14。都是历史证据，不是当前 CF 验收。MySQL 用例固定 Skip，提供凭据也不会自动启用；InMemory 测试不能证明真实事务/唯一索引竞态。

近期目标：优先形成“等待房间 → 一局 TDM → 原房间 → 再开一局”的可测主链，并完成跨阶段聊天。P1/P2/P3 属同一个交付批次，但可跨多晚、多个 Session；**8 小时不是承诺完成三大系统的截止期**。首次粗估完整批次约 12–24 小时有效工作加运行验证，现场以任务实际耗时重新估算。

## C. 执行卡

共用禁止范围 R：不改 FishNet/传输库、tick/预测算法、账号鉴权基础、支付/商城经济、LPFP 原厂/LPW 实验资产、热更新基础和程序集依赖方向；不引入新网络框架、第二套权限事实或新通用架构。Docs/26 明确要求的房间状态、比赛代际、TDM 规则、聊天输入占用及结算适配是已授权范围，不因出现“生命周期”三个字就逐次请求审批。确实需要越过 R 才 BLOCKER。

共用失败策略 F：首次失败保存摘要并定位，最多 3 个有区别的假设/修复尝试，单个失败诊断累计不超过 30 分钟；一次有效进展不重置总预算。只重跑失败用例及直接依赖；无新证据不重复。仍失败则 BLOCKED，保存状态并转独立任务。编译不通时先用最多 15 分钟恢复本次变更的可编译边界，仍做不到仅从本次前置备份撤回自己的未完成切片，绝不覆盖用户原改动。

## D. 分层测试与全量 Gate

| 等级 | 触发与允许范围 | 禁止/升级条件 |
|---|---|---|
| Level 1 | 单函数、局部 bug、无接口变更：编译+直接用例，文档改动免代码测试 | 禁止全量；发现明确接口影响才升 L2/L3 |
| Level 2 | 一个系统内完整功能：专项+模块+直接依赖 | 不扫所有系统；多个模块实际交互升 L3 |
| Level 3 | 房间/DS/客户端、结算返房、聊天跨阶段：相关集成+必要回归/构建 | 不以“保险”升全量；记录具体跨模块风险和 Gate |
| Level 4 | 阶段完成、重大状态/生命周期/底层网络变化、跨模块异常无法定位 | 必须登记原因、套件、源码标识、预算和 Gate；不自动包含全部 PlayMode/资产扫描 |

### 仅保留的正常全量位置

1. **G123：P1/P2/P3 一体交付，Astra 审计前。** 默认 Unity EditMode 全量一次、后端全量一次；原因是 Room API、比赛/退出/静态状态、输入 UI、结算资格跨多模块同时改变，定向测试不能覆盖原有场景状态残留、账号/结算兼容及全套 fixture 顺序影响。Q02/Q05 的生命周期风险统一合并到这里，不各自全跑。真实 MySQL 迁移/事务并发和 2/4/16 连接、IME 属额外定向集成证据，不会因全量绿自动通过。
2. **GFINAL：P4 和集中必要修复完成，最终发布前。** Unity EditMode 全量一次；命中、瞄具、资源生命周期和归档修复一起验证。后端若 G123 后有改动则全量一次；若后端源/依赖/配置/契约均未变，复用 G123 后端全量，仅验证最新客户端互操作。理由是武器/输入/相机/生命周期交互全貌无法只靠倍率镜测试验证。合并 P4 结束、旧问题收口、发布前回归为同一个 Gate。

没有“每晚一次全量”“每卡结束全量”“Astra 再跑同一全量”。Astra 先查失败样例、覆盖质量和实际差异；仅在结果失效或有明确怀疑时复跑对应范围。

例外 G-DIAG（每窗口最多一次，不能与同一源码的 G123 重复）：多个模块同时异常且 30 分钟定向诊断仍不能区分共享状态/依赖回归，可以一次有明确诊断目的的全量；写明为什么 L3 不足。若失败状态机正在反复改，不先跑全量碰碰运气。距离窗口结束容不下该运行则排到下一窗口，继续可隔离工作。

### 结果与预算纪律

- 测试账本每项记录 fixture/命令/filter、源码文件或补丁哈希、环境、开始结束/耗时、collected/pass/fail/skip、结果路径。失败仅给前 5 个摘要，原日志留文件，单次工具输出建议不超 200 行。
- 代码/依赖/场景/配置/测试改变会使受影响证据失效；不相关文档改动不失效。全量后局部修复只补失败及直接依赖，账本组合“全量基线+修复后定向”，不宣称完整全量在最新源码重跑过；重大风险重新评估。
- 过滤示例：`dotnet test fps-backend/tests/UnityFps.Api.Tests/UnityFps.Api.Tests.csproj --filter "FullyQualifiedName~RoomApiTests|FullyQualifiedName~ServerInstanceApiTests"`；按实际受影响 fixture 调整，有 restore 需求先处理依赖，不能假定 `--no-restore` 永远可用。不要 `--no-build` 跑旧测试程序集。
- Unity 使用完整 fixture 名或经验证的列表入口；空摘要不代表没跑、也不代表成功。domain reload 后先核对已落盘 runId/runner/编辑器状态，确认该 run 没有完成且没有正在运行才重发，禁止仅因静态字段清空启动重复全量。
- MySQL 仅使用明确配置的专用 `_test` 数据库；固定 Skip 用例需改为可显式启用的专项入口并实际执行，缺条件标阻塞真实 DB 门；不碰用户开发库、不猜凭据。
- 首次全量预留至多 90 分钟的排期预算（历史耗时待实测，并非通过保证），后续依据 ledger 的 p95+余量决定。余下时间不足“预计运行+20分钟收尾”不启动。测试期间不编辑其依赖文件；可整理报告或只读审计素材。

## E. 无人值守、BLOCKER 与 Context Checkpoint

### 状态机与自动取任务

状态：TODO / RUNNING / IMPLEMENTED_VERIFY_PENDING / PASS / BLOCKED / READY_FOR_AUDIT / AUDIT_PASS。只有 PASS 满足强依赖的验证门；独立子路径可使用已明确冻结的契约，不能把未通过逻辑接到生产链。

每完成卡/安全切片，更新状态并扫描最高优先级可执行卡，立即继续；不要生成一份长报告后等待人工 review。只在窗口结束、无法继续的系统级 BLOCKER、必须审计的阶段边界或无可用新 Session 能力时停止实施。接口局部阻塞不阻塞所有人；暂停的是依赖分支。

BLOCKER 条目：问题/影响卡、可复现步骤、错误摘要、已尝试≤3种方法及结果、不能继续的理由、当前安全边界、精确未完成文件、下一可执行卡。禁止在日志措辞里反复尝试同一动作。编译失败、鉴权削弱、代际错清等不能假标完成；纯外观优化可直接归档。

Unity 桥超时先停止发命令并诊断，不连续堆请求、不切换另一桥冲击编辑器；domain reload 静默等待；不强杀/重开编辑器、不删 Temp/Library 来恢复，不在编辑态 Instantiate 骨骼 FBX。后端或文档任务可继续。

### Context Checkpoint 与新 Session

- 每个卡/安全切片只追加简短状态；明显功能批次、模块门、复杂 BLOCKER 必建 checkpoint。建议每 60–90 分钟一个，最迟一个执行 Session 约 120 分钟活动工作后在安全边界换新；未完成卡拆成接口/纯逻辑/适配切片，不靠无限压缩撑完整夜。
- 若宿主能给上下文占用，达到约 50% 时不再开复杂卡，约 65% 前交接；这些是调度阈值，不假装能读不到的 token 计数。不能读占用时用上述时间/任务边界。
- 单份 `Docs/交接/<窗口ID>-CF-状态.md` 建议 ≤150 行/约 2500 中文字；另用 `任务账本.json` 或简表保存完整队列/测试引用，不能把整个原始日志塞进 checkpoint。
- 只保留：项目状态、完成任务、真实变更文件/系统、测试摘要、关键已修问题、未解决问题、失败尝试、下一步明确入口；不传思考过程。旧 checkpoint 归档引用，不全文串接。
- **有已验证 Session 管理能力**：宿主在 checkpoint 落盘后结束旧执行 Session，用同一用户指定执行 Agent 的新 Session，只传本计划+当前状态路径+下一卡；不得 fork 全历史。旧 Session 退出后新 Session 才取得工作区写权。任务状态驱动调度，不需要人工逐卡转交。
- **没有该能力**：当前 Session 可使用宿主已提供的压缩/重置上下文能力并从磁盘重读状态，明确这不是全新独立审计上下文；到 120 分钟安全交接点仍无可用压缩/新 Session 能力则停止执行并报告 `SESSION_CAPABILITY_BLOCKED`。不能承诺仅靠一段 Prompt 自动生成新会话，也不擅自安装/编写跨产品调度器。

### 独立 Astra 审计与调度边界

本方案不要求执行 Agent 调用不同模型审计自己。G123 审计输入只含计划、差异/文件清单、测试账本、报告、BLOCKER；Astra 在独立上下文直接读实际代码，按风险抽核并出具 PASS 或下一轮必要修改卡。
