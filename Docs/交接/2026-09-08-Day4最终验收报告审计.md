## 2. 必须修复的问题

### P0-1：BodyHitbox 的中心补偿叠加了两次 0.9m

`PlayerNetworkAdapter.EnsureBodyHitbox` 先设置 `CapsuleCollider.center=(0,0.9,0)`，随后又把 `BodyHitbox` 变换原点放到玩家根节点世界坐标 `+0.9m`。因此胶囊实际世界中心约为根节点 `+1.8m`，不是注释声明的 `+0.9m`；高度 1.8m 的胶囊大致覆盖 0.9–2.7m，腿部/下躯干存在漏判。报告中的五次命中点位于 1.8–2.0m，只证明上半身能命中，不能证明胶囊对齐正确。

修复时二选一：BodyHitbox 原点对齐玩家根、Collider center 保持 0.9m；或 BodyHitbox 原点对齐根+0.9m、Collider center 归零。必须增加变换含非零烘焙偏移时的世界中心/上下端点测试。

### P0-2：切枪会免费恢复满弹，属于可直接利用的玩法漏洞

`Arsenal.EvaluateSwap` 每次切槽调用 `WeaponController.EquipDefinition`；后者调用 `Initialize -> RebuildResolvedStats`，每次都 `new WeaponRuntime(...)`。玩家射击后切到副武器再切回主武器，即恢复满弹与完整备弹，可绕过换弹和弹药经济。报告已在“已知限制”中承认该行为，但它会直接影响 FFA/TDM 公平性，不能留到发布后。

每个槽位/武器实例必须持有独立且持久的服务器权威运行时状态；切槽只切换当前引用，不得重建弹药。配件导致弹匣容量变化时需要显式迁移/钳制当前弹药，不得隐式补满。新增回归：主枪开火→切副枪→切回主枪，弹匣/备弹不变；换弹中切枪不会赠送弹药；客户端同步仍以服务器状态为准。

### P0-3：Day4 明文要求的 3/4 客户端生命周期矩阵未执行

两客户端中管理员退出后比赛自然结束，不能证明 3/4 人时管理员退出后其余玩家继续、leader 正确转移、连续退出不重复结算、最后一人才释放实例。原 Day4 计划把 2/3/4 客户端矩阵列为完成条件，报告也明确标记 `PARTIAL`，因此不能以“机制已具备”替代实机结果。

只补跑 3 人和 4 人场景，不重复双客户端 Gate B。至少覆盖：管理员主动退出后其余玩家仍在线且能移动/射击；leader 转移；普通成员强杀；连续退出；最后一人退出后 Ready/0；同一实例被下一房间复用且无幽灵成员/重复结算。

### P1-1：退出保护使用对象引用，不是真正的连接代际

`LeaveTransactionCoordinator` 以 `ReferenceEquals(roomNow, roomAtBegin)` 判断旧事务是否被新会话替代；但 `AccountSession.ApplyRoom` 每次都创建新的 `RoomSessionState`。后续 CF 等待房间轮询只要刷新同一个房间的成员数/队长信息，就会改变对象引用，导致正常退出被误判为 superseded，跳过停连接、清上下文和导航。

应改为显式、单调的连接/房间会话 generation：真正 create/join/reconnect 成功时递增，同一会话的房间快照刷新不递增。协调器捕获 generation 并在完成前比较。测试必须覆盖“同房间元数据刷新仍完成退出”和“新连接代际替换时旧事务零副作用”。这是进入 CF 等待房间阶段前的结构性门禁。

### P1-2：临时 harness 的 `production` 退出模式没有走生产退出事务

`Day4SmokeClientHarness` 的 production 分支只调用 `BeginLeaveTransaction()` 和 `CompleteLeaveTransaction()`，绕过 `LeaveTransactionCoordinator` 与后端 `LeaveRoomAsync`，因此不能用该模式证明生产退出链。残余矩阵中 production 模式必须触发与真实确认按钮相同的协调器/API 路径，并从日志证明 leave API、停连接、清上下文和导航的顺序。

### P1-3：现有客户端是测试包，不是发布候选

当前只有 `Builds/Day4Client/UnityFpsClient.exe` Development Build，且 `Day4SmokeClientHarness.cs` 无 `DEVELOPMENT_BUILD` 编译隔离，反射入口和命令行账号密码能力已编入包内；目录还含 `UnityFps_BurstDebugInformation_DoNotShip`。该包可以继续用于残余矩阵，但不能称为 Release/发布候选。

矩阵完成后删除临时 harness/build helper（或至少彻底从非 Development 编译剔除），再生成 Windows Release Client，并做一次无测试参数启动冒烟。当前 Client 程序集时间早于最后的命中盒改动，也需要最终重建保证源码/产物一致。

## 3. 需要在残余验收中确认的问题

- 报告承认运行中持续出现 “There are 2 audio listeners” 刷屏，这与 `[Invariants] ... audioListeners=1` 互相矛盾。残余矩阵必须记录告警出现的场景和两个对象；若发生在正常玩家流程，修正为任意时刻仅一个启用的 AudioListener。
- 高/低延迟玩家互不拖慢和 tick 波动后的收敛仍未验证。使用 FishNet/传输层的开发期延迟模拟或本地损伤代理，仅对一个客户端注入可控 RTT/抖动/少量丢包；验证低延迟客户端不被拖慢、高延迟客户端无持续硬拉回/双倍移速。不要为此改生产 tick 架构。
- `Logs/Day4` 当前没有报告所引用的逐客户端/服务器实机原始日志，只有脚本、测试摘要和后端结果。残余验收需按进程保存原始日志、启动参数（密码脱敏）、房间码/用户/连接事件时间线，使结论可复核。
