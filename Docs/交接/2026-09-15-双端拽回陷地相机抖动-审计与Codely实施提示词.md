## 2. 拽回：已确认的纠偏逻辑缺陷

`MovementPredictionCore.cs:343–378` 的 SmoothCorrectionLedger.ConsumeInFlightAfter 在求和 tick>ACK 后 `_entries.Clear()`。`PlayerNetworkAdapter.cs:699–717` 每次以新的历史快照误差重写 remaining，并不会继承上一次已扣除的历史总量。因此未确认的校正不能第一次被查询后就丢掉。

最小反例（本轮用 Python 算术复算，非 Unity 测试）：tick12 已施加 +0.1m；ACK10 原始误差 +0.1，扣除得到0并清账；紧接 ACK11，其预测快照同样早于tick12，原始误差仍+0.1。第二次查账返回0，于是又施加+0.1。正确结果两次都应是0，直到ACK追过tick12才可移除记录。上轮5例测试只验证一次查询，还断言“整体清账”，把实现错误固定成测试要求。

另外，None 分支没有根据当前ACK重新处理旧 remaining；需覆盖“误差进入阈值后仍继续消费旧纠偏”的情况。溢出只停用一次平滑、后续ACK又可能重新启用，也不等于已经要求硬重基。

直接表现链：Adapter 以固定tick预测 → Locomotor.ApplySmoothCorrection 临时禁用 CC 并直改模拟根 → 子相机同步位移。即便没有 SNAP，频繁平滑校正也可产生明显拽回，不能用 snaps=0 作为体验合格标准。

其他需要诊断而非猜测的来源：ServerTick 每tick Drain(1)，没输入就 Simulate(default)，会把地面速度清零；批次晚到或本机调度不均可产生额外空步，后来同clientTick的模拟状态已经不同。队列上限16，超限主动丢最旧；它和传输丢包是不同问题。不要直接改成每服务器tick跑3次完整dt（会使速度/时间超前），应明确输入时间轴与模拟预算后处理。

## 3. 陷地：不能只修倒地角度

`NetworkCombatAuthority.cs:697–739` 死亡关闭动画写者并把 TP_Model.localRotation 直接设为 Euler(85,0,0)，没有地面探测、接触高度补偿；恢复只还原旋转与动画开关。这是确定的死亡表现缺口，但不足以单独解释视频里长时间“上半身直立、下半身埋地”。

接手须分别记录玩家模拟根、TP_Model局部位姿、骨盆/脚骨世界高度、当前死亡状态、碰撞体/动画状态，在死亡前、死亡、重生后各采一次：区分根整体下降、TP节点偏移和骨骼姿态异常。核对 ObserversDied/ObserversRespawned 与 SyncVar 死亡状态的先后、漏应用、重复以及重生时完整恢复。

同查 `ServerLagCompensation.TryBeginRewind/EndRewind`：现在已先完整保存再写，不要重新宣称旧版“边保存边回溯”仍在。它仍写真实根CC及BodyHitbox的Transform，需要验证致死发生在回溯作用域内时的恢复，以及连续射击/重生后世界与局部位姿。不可信注释称“世界坐标恢复顺序无关”：父子恢复仍必须父先子后，当前遍历是否稳定须测试保障。优先保持查询碰撞体与视觉姿态职责独立，不让回溯改动尸体或相机。

## 4. 相机：固定tick阶梯 + 校正 + 近距碰撞差异

离线 Locomotor.Update 每渲染帧 Simulate(Time.deltaTime)；联网 Adapter.RunOwnerPrediction 用固定dt。CameraPivot 是玩家根的子节点，FPCameraRig主要更新FOV与本人死亡视角，并没有Owner位置的渲染插值。高渲染帧率下固定tick位移天然呈阶梯，纠偏还直接打到同一根。

`Locomotor.SetSimulationMode` 只改枚举；RemoteProxy 的根 CharacterController 未禁用。Owner 碰撞的是插值后的远端位置，DS 碰撞的是权威位置，近距离更容易产生预测分叉，与用户“越靠近越明显”吻合，但仍需定向数据确认强度。不要擅自把所有玩家穿透当作修复。

双开CPU/GPU竞争、焦点切换、无上限帧率和每渲染帧提交开火都可能放大问题。Adapter.HandleOwnerCombatRequests 在FireHeld时每帧发RPC，DS同一tick有多条reject，是额外负载线索，不是移动丢包证明。runInBackground已开；没有帧时/利用率数据，不能断言机器性能不足。视频120fps是录制频率，不是游戏实际帧率；不要把视觉抖动称为已启用Motion Blur。

## 5. 可直接交给 Codely 的实施提示词

1. **先修纠偏台账**：为连续ACK保留仍在途的校正记录，只剪枝已被ACK覆盖的条目；正确处理None、硬对位、死亡/重生、溢出。也可改成完整状态回滚重放+视觉偏移衰减，但必须交代状态完整性、碰撞与输入副作用，避免重复开火/后坐/事件。禁止仅调大SNAP阈值或加大相机阻尼掩盖分叉。
2. **补有限诊断并检查时间轴**：每进程独立日志，记录buildId/pid/conn/object/match、单调时间；每1–2秒汇总移动生成/提交/服务器收到/消费、ACK、queueDepth、空步数、DroppedBacklog/Future/Stale、DroppedSteps、RTT、dt分布、前后台状态。Stale含冗余重传去重，不能当丢包。校正记录xyz及根/预测/权威位置，硬对位区分原因。启动脚本已存在唯一日志功能（启动客户端.cmd → Tools/Client/Start-LocalClient.ps1），先复用并核对实际入口，别重复实现；本次未发现可用独立客户端日志。
3. **修死亡/重生的完整表现状态**：先通过上述根/模型/骨骼坐标区分具体下沉来源；解决倒地支点与地面穿插，恢复位置/旋转/动画/碰撞体的原状态，幂等处理重复事件。死亡视觉不写Owner模拟根、不得破坏伤害查询；避免只整体抬高活人模型或硬编码所有地图统一高度。追查录像中持续到重生后的埋地。
4. **分离Owner模拟与渲染位置**：让相机位置/第一人称表现按渲染帧平滑，保持鼠标旋转响应；检查Cinemachine更新时序，确保一个位置写者。死亡/重生/传送/接管时清历史，不从旧位置穿场插值。视觉偏移不得反向改变服务器瞄准、枪口判定或玩家碰撞根；相机瞄准与权威射线语义要明确。
5. **处理近距阻挡一致性**：核实远端插值CC参与Owner碰撞的影响；保持既有玩家阻挡设计，设计明确的预测碰撞代理/权威修正路径。若无法在保持玩法下修复，报告具体权衡，不默认切成玩家互穿。移动/伤害碰撞职责分离，墙体阻挡不能回归。
