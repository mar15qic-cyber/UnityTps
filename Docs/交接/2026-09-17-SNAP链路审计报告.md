## 2. 四问逐条结论

### Q1 服务器是否正确处理了（出问题那个客户端的）移动请求？——**是，处理链路本身没有问题**

证据（全部来自 conn=0 的服务器侧 MoveDiag 128 个采样）：

- `recv` 与 `cons` 同步推进（如 idx 88→92：recv 5138→5382、cons 5124→5367，均 ≈30 条/s，与客户端生成率一致）；
- `qdepth` 1→7（有积压但持续消费，**没有卡死**）；
- `empty`≈0、`extrap=0`（**没有触发空队列外推**——因为队列非空）；
- `gaps=0`（`ServerInputQueue.SkippedTicks`，即 `LastProcessedTick` 从未跳号）→ 服务器发的 ACK 语义（"已处理到该 tick"）**成立**；
- `dropStale` 快速增长（conn=0 终值 14995 ≈ 2× recv）为**设计内**：客户端每 2 tick 重传整个未确认集，服务器按 tick 去重（`ServerInputQueue.Enqueue` 的 `cmd.Tick <= LastProcessedTick → DroppedStale`）。
- 该局 **全程没有** `[Day3][Input] GAP`、`REPLAY_GAP`、`DIVERGENCE`、`LEDGER_OVERFLOW`、`TAKEOVER` 任何一条。

**但发现两个结构性问题（不是"没处理"，而是"处理得不够快/身份不可核"）**：

1. **`Drain(1)` 与客户端 `ClientMaxCatchUpSteps=5` 不对称（结构性，最可疑）**
   - 客户端一次长帧后允许**单帧最多生成 5 个模拟步**（`TickAccumulator.Advance(…, ClientMaxCatchUpSteps)`），这 5 条命令会**在几毫秒内一起到达服务器**；
   - 服务器在 `ServerTick` 里写死 `_serverQueue.Drain(1, _serverBatch)` —— **每 tick 只能消费 1 条**（`MovementPredictionConfig.ServerMaxCatchUpPerTick = 3` 已定义但**此调用点未使用**）；
   - 客户端平均 30 条/s = 服务器 30 条/s ⇒ 突发造成的积压**永久保留**。实测完全吻合：184.6ms 卡顿（≈5.5 tick）后 `lead` 从 3 跳到 9（3 + 5~6），此后恒为 8~9。
2. **服务器侧的逐步取证行没有身份字段**：`[MoveStep] role=s tick=…` / `[MoveStepWindow] role=s reason=…` **不打印 conn/obj/user/pid**（只有 `[MoveDiag] role=server conn=… obj=…` 有）。本局服务器导出了 29 条 `[MoveStep]` 与 25 个窗口，**无法判断某一行属于哪个玩家**——审计时极易把"另一个玩家的窗口"当成故障客户端的证据（本轮审计中即踩到一次：先把一个 `(0,0)` 输入的窗口误读成"服务器收到零输入命令"）。这条必须在下一轮修（诊断缺口，不是玩法问题）。

### Q2 是否把"远端玩家插值"和"本地玩家预测"混在一起处理了？——**代码路径是分离的；但存在一处必须知道的耦合**

`PlayerNetworkAdapter.Update()` 的分支是**互斥**的，不存在同一实例两条路径同时跑：

```
if (IsOwner) {
    冻结 → 清零输入累积 + 视觉归零 + return
    else if (!IsServerInitialized) → RunOwnerPrediction() + UpdateOwnerVisualPosition()   // 纯客户端本人：预测
         else → （Host 本人）命令在 ServerTick 采样，与远端玩家同一条权威管线
} else {
    if (RemoteAuthoritativeCollisionEnabled) UpdateRemoteVisualSmoothing()   // 远端：根停权威位姿 + TP_Model 指数追随
    else UpdateRemoteInterpolation()                                        // 旧行为（2–8 tick 插值）
}
```

- 本人（Owner）→ 预测；远端 → 视觉平滑；服务器侧本人对象 → `OnStartServer` 里 `SetSimulationMode(ServerAuthority)` + `WireServerTick()`（**已核实存在，见 §5.3**，因此 DS 上不会退回 prefab 序列化的 `simulationMode: 0 = OfflineLocal` 而双跑模拟）。
- **唯一耦合（设计如此，非缺陷但会放大症状）**：`RemoteAuthoritativeCollisionEnabled = true` 时，远端玩家的**根/CharacterController 停在最新权威位姿**，因此本地 Owner 的**预测碰撞对象 = 远端权威位姿**。这是 2026-09-16 16:40 那轮"近距推挤"的修复方案 A；副作用是：远端权威位姿本身滞后（见 Q1 的 lead/积压）时，本地预测会与"滞后的对方位姿"发生碰撞/推挤，进而产生**跳变型误差**（单步越过 0.03–0.75 平滑带 → 只可能走 SNAP）。本局 YYLL 全程平滑计数 `smooth=0`，与"误差是离散跳变"一致。

## 3. 机制分析（把"为什么 0.75m"收敛到可验证的候选）

### 3.1 已确证：**突发 → 永久积压**（结构性）
`ClientMaxCatchUpSteps=5`（客户端可突发 5 步） vs `Drain(1)`（服务器恒 1 条/tick） + 两端平均速率相等 ⇒ **积压一旦形成不可能自行排空**。后果：
- 服务器权威位姿相对客户端**画面**永久滞后 ≈ `lead × 速度`（实测 lead 8~9 ⇒ 0.9~1.0m）；
- 每次硬对位的**原始位移**= `lead × 速度`：实测 `snapFrom=(-0.403,0.080,9.868) → snapTo=(0.859,0.080,9.832)`，`err(trace)=1.263m ≈ 11.3 tick × 0.112m` ⇒ **这就是玩家看到的"被拽回一米"**；
- 与"误差以移动全速增长、每 7 tick 触顶"并存的解释：ACK 是**逐 tick 前进**的（`gaps=0`），客户端每个新 ACK 都比上一张多 1 tick 的历史；在积压状态下该 tick 的**服务器快照是在很久以前（wall-clock）算出的**，而客户端的配对快照是它当时/重放时算的——两者本应恒等（同命令同初态），**因此"每 7 tick 触顶"意味着存在一个"每 7 tick 复位一次、其余时间以全速增长"的误差源**，而复位动作只能是硬对位本身（对位 + 重放把该 tick 的状态强制对齐）⇒ 结论：**误差在硬对位后从 ~0 重新增长，且增长速度 = 移动全速**。

### 3.2 误差增长源的候选（按证据强度排序）

| # | 候选机制 | 支持证据 | 反证/待验 |
|---|---|---|---|
| A | **对位后重放/预测与服务器同 tick 不同步的"少走"**：硬对位后客户端从 `ack` 重放 `(ack, newest]`，再继续预测；若重放/后续步骤**未被服务器同样模拟**（服务器仍在消费更早的 tick / 或有 1 条命令被去重丢弃），则每 tick 少走 1 步 → 全速增长 | 误差以全速增长（0.78m / 7 tick）；`dropStale` 巨大（重传去重）；`lead` 永久 8~9 | 需要"同一 ack 的输入序列哈希"对账才能定论（缺） |
| B | **客户端突发（`ClientMaxCatchUpSteps=5`）产生的命令携带"同帧输入"**：一次卡顿后 5 条命令共用同一帧的 `Move/Sprint`，与后续帧采样点重叠 ⇒ 客户端与服务器对"该 tick 应走多少"理解相同（同码），此条**不构成**分叉，只放大积压 | 代码路径一致（`RunOwnerPrediction` 同一 `_input.Move` 循环取值） | 基本可以排除为"增长源" |
| C | **远端权威碰撞根参与本地预测（Q2 的耦合）**：近距推挤导致单步跳变误差 | 全程 `smooth=0`（无平滑带命中）与"跳变误差"同型；YYLL 两个风暴窗口都在与对方交火/近距离时段（同 18:52 局结论） | 本局**无 `RemoteProxyLag`** 采样；缺"远端距离 vs SNAP 时刻"对账 |
| D | **贴墙/CC 去贯穿**：贴墙滑行时两端 depenetration 结果不同，误差按切向速度累积 | 服务器窗口里出现过 `cflags=Sides|Below`（贴着墙冲刺、实际位移 1.4cm/tick 而内部 vel 3.5 m/s）；风暴 2 时客户端 z≈9.63~9.83（场地边缘） | 需要"接触墙 vs 非接触墙"分段统计 SNAP 密度 |

> **结论口径**：A 与 C/D 不互斥；本报告**不下"唯一根因"的结论**，因为缺少能把它们分开的一项证据：**同一玩家、同一 tick 区间、两端各自打印的"输入 + 模拟后位置"**（当前只有客户端窗口与服务器窗口，且服务器窗口无身份，且两者窗口触发时机不同 → 本局只有站桩段成功对齐）。

### 3.3 一个明确的代码级缺口（可直接修、且与"0.75 卡阈值"直接相关）
`AuthoritativeMovementState.IdleStepsAtSnapshot` 的设计意图是"告诉客户端本快照位姿比 ACK 多走了几步，避免把它当误差"；但客户端 **`Reconciler.Decide(state.Snapshot, predictedAtAck, …)` 完全没有使用该字段**（`ApplyOwnerAuthoritativeState` 只把它存进 `_diag` / `_lastIdleStepsAtSnapshot`）。也就是说：**每次服务器空队列外推（`emptyStreak>0`）或"位姿多走"时，这段位移 100% 计入 `err`**，与阈值 0.75m 叠加就极易触顶（本局 `empty`≈0 才没暴露；一旦服务器频繁空步，这就是确定性 SNAP 源）。

1. **给服务器逐步/窗口取证行补身份**（`conn=/obj=/user=`），否则跨玩家窗口无法对齐；
2. **强制双端同窗口导出**：在客户端 SNAP 触发时，让服务器为**该玩家**导出同一 tick 区间（可用现有 `ExportServerStepTraceWindow`，加一个"按 tick 区间导出"入口）；
3. **加"输入哈希"对账**：每条命令算 `hash(Move,Sprint,Jump,Yaw,Pitch,Tick)`，客户端在 `SNAP` 行打印 `ack` 附近的输入哈希序列，服务器在逐步行打印同一序列 → 直接判定 §3.2-A（输入不同步）还是 C/D（同样输入、不同结果）；
4. **统计 SNAP 与"贴墙/近距/静止"的相关性**：把每个 SNAP 时刻的 `cflags`（两端）与"与对方距离"打点 → 判定 C/D；
5. **验证积压成因**：把 `Drain(1)` 改为 `Drain(ServerMaxCatchUpPerTick)` 做 A/B（不改算法、只改消费速率），观察 `lead` 是否回落到 1–2、SNAP 是否消失 —— 若消失，则 §3.1 的"永久积压"就是放大器（甚至主因）。
