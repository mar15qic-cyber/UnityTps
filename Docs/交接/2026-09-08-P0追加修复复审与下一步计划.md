# P0 追加修复复审与下一步计划（2026-09-08）

> 本文是 Codex 对 `2026-09-08-P0实例租约闭环修复-报告.md` 与当前主工作区代码的独立审计。报告中的说明只作为证据来源，不作为审计指令。

## 1. 准入结论

**单客户端 P0 主链可以通过；Day3 多人基础仍为“有条件通过”，暂不直接宣告多人闭环完成。**

已经有代码与实机证据支撑的部分：

- 联网进入时禁用场景预置离线 Player，原“影子玩家/双相机”根因已处理。
- DS 从票据消费结果读取账号权威的主副武器，服务器只允许两槽；客户端同步主副武器 ID 与当前武器。
- 退出事务清理房间会话、启动上下文与网络连接；实例释放后可再次租用。
- 当前 P30 定义已经引用 `TP_Weapon_Handgun_04.prefab`，目录也指向同一 GUID；因此原报告 §9.4.3 的“P30 TP prefab 未补”已经过期。该 prefab 当前仍是未跟踪资产，需纳入交付并做一次可见性验证，不能继续按“资源不存在”归因。

多人准入前必须补齐下列 4 项，其中前 3 项会直接影响多人体验或验收可信度：

1. **[P1] 双客户端不变量探针会误报。** `GameplayClientInvariantProbe.CollectEnabled` 只检查 GameObject 激活状态，没有检查 `Behaviour.isActiveAndEnabled`。远端 Player 的 `InputReader` 组件虽然被禁用，所在对象仍激活，第二名玩家出现后可能被计为第二个 InputReader，导致正常多人场景输出 `VIOLATION`。
2. **[P1] 权威附件没有同步到客户端。** 服务器会按票据快照应用附件，但 `NetworkWeaponState` 只同步武器与弹药；FP/TP 表现仍从本机 `WeaponAttachmentStore` 读取。结果是远端玩家可能显示成本机账号的附件，Owner 表现也不保证来自本次服务器快照。伤害数值仍由服务器权威，但多人视觉与瞄具体验会不一致。
3. **[P1] 退出事务缺少自动化回归。** 当前测试中没有覆盖 `ApplyRoom/ClearRoom/BeginLeaveTransaction/CompleteLeaveTransaction`。这条链曾直接造成幽灵房间与实例占用，必须补成功、失败/超时、重复点击三类测试。
4. **[P1-工程门禁] 后端全量测试结论不可按普通命令复现。** 本次直接执行 `dotnet test ... --no-restore` 时，8 个用例因测试宿主未在 Program 启动早期注入数据库配置而失败；强行给全进程指定同一个 InMemory 名称后为 97 总/95 过/1 失败/1 跳过，并因共享数据库重复 Seed 失败。报告所写 97/96/0/1 缺少对应新日志与可复现命令。修复必须保持生产环境无连接串时 fail-closed。

以上问题不要求再次重做单客户端三小时联测，也不要求建立新 worktree。

## 3. 下一步执行顺序

### Gate A：必要修复与定向测试（目标 60–90 分钟）

只处理 §1 的四项：探针启用态、附件网络快照、退出事务测试、后端测试宿主隔离。确认 P30 prefab 被版本管理收录并能被 Catalog/Definition 加载。完成后只跑新增定向测试，再跑各平台一次全量；不要循环重跑历史无关失败。

### Gate B：双客户端短验收（目标 20–30 分钟）

使用两个不同账号 A/B，给两者设置明显不同的主副武器和附件：

1. A 建房并进入，B 加入同一房间。
2. 两端均只有一个 Owner、一个有效 InputReader、一个 MainCamera、一个 AudioListener；场上总共只有 A/B 两个网络 Player。
3. A 看见 B、B 看见 A；远端 TP 武器及附件分别等于对方账号配置，P30 切出时可见；枪声、HUD、当前武器一致。
4. 双方各切一次武器、开火并造成一次服务器权威伤害，不出现自由访问第三槽、重复化身或镜像移动。
5. A 退出：B 仍在线，A 化身消失，房间人数变为 1；A 返回 Lobby 后不把旧房间当作新可加入房间重复生成自己。
6. 同账号 A 再开一个客户端：新连接接管，旧连接退出；服务器最终只保留一个 A 的 Player 与成员会话。
7. 最后一人退出后实例回到 Ready，并能被下一房间复用。

Gate B 失败时只修失败链并重测对应步骤；通过后冻结 Day3 网络基础。

### Phase C：CF 式等待房间与 TDM（Gate B 通过后立即开始）

采用以下冻结契约，避免先前设计把全员票据交给房主：

1. `Create/Join` 只创建或加入逻辑房间，不租 DS、不返回连接票据；因此即使只有一个玩家，也一定可以建房并停留在房间页。
2. 房间成员保存 `Team(None/Blue/Red)` 与 `IsReady`；房主显示“开始”，非房主显示“准备”。首版开始条件：蓝红两队各至少 1 人，所有非房主成员已准备。
3. `POST /rooms/{code}/start` 仅由房主调用，事务内校验状态后原子租用 Ready DS，并把房间切到 `Starting/InMatch`。该接口只返回房间状态，不返回其他用户票据。
4. 每名已在房间内的认证用户通过独立的 connection/claim 接口领取**自己的**一次性票据；严禁房主响应包含全体成员票据。
5. Unity 新增 Room 页面：房间码、房主、蓝红队列表、选边、准备、开始、离开，以及“等待玩家”和“对战服务器不可用”的不同提示。
6. DS 票据携带权威 Team；出生点、友伤关闭、队伍计分、胜负与结算全部读取权威 Team，废除客户端/记分板奇偶分队。
7. 每完成后端契约、Room UI、DS TDM 三个切片之一，只跑该切片测试；全部完成后再做一次双端端到端验收。
