## 1. Executive Summary

### 1.1 Confirmed Code Defects（静态可证）

| ID | 严重度 | 位置 | 缺陷（静态可证） |
|---|---|---|---|
| **D1** | **Critical** | `PlayerNetworkAdapter.ApplyOwnerAuthoritativeState` | **Snap 判定使用 raw error，忽略 in-flight 平滑校正**：`Reconciler.Decide(...)` 判定 `Snap` 后**先** `HardSnapTo` 返回，`inFlight = _correctionLedger.ConsumeInFlightAfter(ack)` / `corrected = raw − inFlight` 只在非 Snap 路径执行 ⇒ 本应落入 0.03–0.75 平滑带的误差被提前判为 Hard Snap。且 `_diag.LastErrorMeters = correction.magnitude`（raw）⇒ **历史日志的 `err=0.753~0.808` 是 raw，不是真实残余误差**。 |
| **D2** | High | `BuildAuthoritativeState` / `Reconciler` | **`IdleStepsAtSnapshot` 生产但不被任何 Reconcile 逻辑消费**（仅存 `_lastIdleStepsAtSnapshot` + 日志）：服务器在**空队列外推/空命令**时"位姿比 ACK 多走 k 步"（k ≤ `ServerInputExtrapolationMaxTicks=8`；冲刺 8×0.112≈0.9m），客户端仍用 `predicted@LastClientTick` 与它比较 ⇒ 该位移 100% 计入误差。外推路径下 `Snapshot.Tick = LastProcessedTick + k ≠ LastClientTick`（`ServerInputExtrapolation.Decide` 构造的 tick）。 |
| **D3** | High | `MovementCommand` / `_inputEpoch` | **输入 epoch 不是线上契约**：`_inputEpoch` 在 `ResetOwnerPredictionState`/死亡/重生时自增，但 `MovementCommand`（Move/Sprint/Jump/YawDelta/PitchDelta/Tick）与 `AuthoritativeMovementState` **均无 epoch 字段**；服务器 `ServerInputQueue.Enqueue` 只按 tick 判定。⇒ 死亡瞬间"已发出但未确认"的旧命令（tick > `LastProcessedTick`）在重生后会被当作**新 epoch 的输入**消费（客户端此时已 `_buffer.Clear()` 并从 `ack` 重新生成同号 tick）。可达性：只要死亡时 lead>0（有积压，本局实测 lead 3→9）即成立。 |
| **D4** | Medium | `WeaponRecoilState` ↔ `Locomotor.Simulate` | **`Simulate` 依赖的 RecoilDebt 的"演化"由渲染帧率决定**：`WeaponController.Update`（`Time.deltaTime`）→ `_recoil.Tick(dt, …)` 逐帧恢复债务，而债务**消费**发生在固定 tick 的 `Simulate`（`ConsumeRecoilCompensation` 影响**身体 yaw**）。两端帧率不同（实测客户端 min/avg 2.1/2.5ms，服务器 22.3ms）⇒ 同 tick 的 yaw 消耗不可复现。`RecoilDebt` 虽在快照内，但只在重基/死亡边界恢复，**不保证逐 tick 一致**。 |
| **D5** | Low | `ResetOwnerPredictionState` | `_ticksSinceSend`（L57）未复位（`_hostSourceTick` 亦未复位，Host-only）⇒ 会话/接管边界后发送相位残留（功能无害，但证明"重置函数不完整"）。 |

### 1.2 Structural Risks（架构风险，静态可证其存在，但不足以证明历史 SNAP 由它触发）

| ID | 严重度 | 风险 |
|---|---|---|
| **R1** | **High** | **服务器输入队列无追赶能力**：`ServerTick` 恒 `Drain(1, …)`（`ServerMaxCatchUpPerTick=3` 定义但此调用点未使用）。客户端 `ClientMaxCatchUpSteps=5`（单帧最多 5 步）⇒ 一次卡顿即可产生 +5~6 的突发；两端平均速率都是 30/s ⇒ **积压一旦形成没有任何代码路径能追回**（只有 `ServerMaxPendingCommands=16` 上限）。lead 永久抬升 = 权威位姿相对画面永久滞后 lead×速度。 |
| **R2** | **High** | **无世界（环境）回溯**：预测只覆盖"本角色 + 输入"；玩家模拟所依赖的 Physics World（其他玩家根 CC、动态碰撞体、门）在服务器消费 tick N 时处于**比客户端当时更晚**的世界状态；`ServerLagCompensation` 只对 **hitbox colliders**（含根 CC）做射击窗口内的回溯（`TryBeginRewind` 移动的是注册碰撞体），**与移动模拟无关**。"输入确定性 ≠ 世界确定性"。 |
| **R3** | **High** | **玩家-玩家阻挡仅由根 CC 承担，而两端面对的对方位姿不同**：`BodyHitbox` 是 trigger（`isTrigger=true`，不阻挡），唯一位移阻挡=根 `CharacterController`。Owner 客户端撞的是远端根的 **NT 插值位姿（`SetInterpolation(1)` + RTT/2）**，服务器撞的是**当前权威位姿**。近距推挤/贴墙时同一 tick 的 `CollisionFlags`、去贯穿结果可不同 ⇒ 跳变型误差（越过 0.03–0.75 平滑带，只能走 Snap）。 |
| **R4** | Medium | **`WireServerTick()` 无幂等保护**：`if (TimeManager != null) TimeManager.OnTick += ServerTick;` 无 `_wired` 旗标，解绑只在 `OnStopServer`/`OnDestroy`。若同一实例被重复 `OnStartServer`（接管/重生成/网络重启场景），将**双重订阅** ⇒ 服务器每 tick 对同一玩家消费 2 条命令 + 发 2 张快照（等价于把客户端时间轴压缩一半）。FishNet 是否会对同一实例重复回调未在源码中证明 ⇒ 归为风险而非缺陷。 |
| **R5** | Medium | **`_localTick = max(replayed, newest)`**（`HardSnapTo`）：若 `ack+1..newest` 出现命令缺口，重放于缺口 `break`（`replayed`），但 `_localTick` 仍取 `newest` ⇒ 后续预测建立在"实际只模拟到 replayed"的物理状态上却声明已到 newest。**静态可达性分析**：当前三条不变量（`TryStore` 拒绝同 tick + `++_localTick` 单调生成；`PruneUpTo` 只删 ≤ ack；`InvalidatePredictedAbove` 只动 `_predicted` 不动 `_commands`；容量 128 ≫ lead）保证命令**连续** ⇒ **当前不可达（见 §6.3 证明）**；但代码**无断言/无守卫**，一旦引入丢命令/压缩/跳号路径即静默违反。 |
| **R6** | Medium | **快照 `Pitch` 的来源两端不对称**：`Locomotor.PitchProvider` 在客户端读表现层相机（`FPMouseLook`），服务器读 `_remotePitch`（由 `ApplyRemotePitch` 用**同一债务消费公式**在服务器积分）。⇒ 快照含一个"两端不同源"的字段（已知 pitchGap 1–6° 的代码根据）。 |

| `GaitPhase` | Locomotor | 是 | ✅ | ✅ | ✅ | ✅ |

## 5. Tick / ACK / Snapshot Audit（时间语义）

### 5.1 四个字段的静态定义

| 字段 | 写入者 | 语义（严格定义） |
|---|---|---|
| `ServerTick` | `TimeManager.Tick` | 服务器全局模拟 tick（30Hz 墙钟推进）。客户端仅用于 `EstimateServerTick()`（射击回溯窗口估算），**不参与 reconciliation**。 |
| `LastClientTick` | `_serverQueue.LastProcessedTick` | **服务器已消费（已 Simulate）的最大客户端输入 tick**。ACK 门与配对查询的唯一键。 |
| `Snapshot.Tick` | `Locomotor._lastCommand.Tick` | 快照位姿对应的"逻辑输入 tick"。正常路径 == `LastProcessedTick`；**外推/空命令路径 = `LastProcessedTick + k`**（`ServerInputExtrapolation.Decide` 构造 `queue.LastProcessedTick + ConsecutiveEmptyTicks`）。 |
| `IdleStepsAtSnapshot` | `ConsecutiveEmptyTicks` | 快照位姿相对 `LastClientTick` 多推进的步数（= k）。**当前无消费者**（D2）。 |

### 5.2 各服务器路径下的 `Snapshot.Tick` vs `LastClientTick`

| 路径 | 模拟内容 | `LastClientTick` | `Snapshot.Tick` | 一致？ |
|---|---|---|---|---|
| 正常 `Drain(1)` | 该命令 | cmd.Tick | cmd.Tick | ✅ |
| `Drain` 多条（当前调用点不产生） | 末条命令 | 末条 cmd.Tick | 末条 cmd.Tick | ✅（若将来启用 catch-up） |
| 队列空 + 外推 | 最后已知输入（新构造 tick） | 保持不变 | `LastProcessedTick + k` | ❌ **k>0 时不一致** |
| 队列空 + 超外推上限 | `default`（空命令，tick=0） | 保持不变 | `_lastCommand.Tick`=**0** | ❌ 快照 tick 退化为 0（`Locomotor.Simulate` 会执行 `_lastCommand = default`⇒Tick=0） |
| 冻结（`MovementFrozen`） | 不模拟（`Clear()` 且跳过） | 保持不变 | 上次值 | 位姿不推进 ✅（Snapshot 内容=上一 tick 的位置） |
| 死亡 | 同上（`Dead=true` 走客户端清历史路径） | 保持不变 | 上次值 | ✅（客户端只用 `Dead` 位） |
| 重生 | 由客户端 Reset 后新命令驱动 | 新命令 tick | 同 | ✅（客户端走 `_ownerWasDead` 路径，不做配对） |
| `Queue.Clear()` 后第一条输入之前 | 空命令路径 | 保留旧值 | 0（首条）或旧值 | ⚠ 见 §6.2 |

**结论**：`Snapshot.Position` 代表的时刻 = `Snapshot.Tick`（而不是必然 `LastClientTick`）。客户端只按 `LastClientTick` 取配对快照 ⇒ **外推/空命令/首条输入前存在语义错配**（D2 的根因）；正常路径下两者相等，故该错配**只在特定路径发生**——这与"平时正常、特定情况炸"的形态一致。

### 5.3 `_localTick` 全生命周期（唯一递增点 + 全部改写点）

| 场景 | 赋值 | 语义是否成立 |
|---|---|---|
| `RunOwnerPrediction` 每步 | `++_localTick` | ✅ |
| `ResetOwnerPredictionState` | `= 0` | ✅（同时清 buffer/门/台账） |
| `ApplyOwnerAuthoritativeState` 死亡 | `= state.LastClientTick` | ✅（死亡冻结期无新输入） |
| `HardSnapTo` | `= max(replayed, newest)`（无 buffer 时 `= ack`） | ✅ 在"命令连续"不变量下 `replayed==newest`（§6.3 证明）⇒ 等于"真实完成模拟的最大 tick"；**依赖隐式不变量，无断言**（R5） |

**未发现**"逻辑 tick 与实际模拟 tick 脱节"的**可达**路径（当前不变量下）；但脱节一旦发生（R5）就会**静默持续**（后续 tick 全部建立在旧状态上）。

### 5.4 `_inputEpoch` 审计

- 递增点：`ResetOwnerPredictionState`、死亡（首次）、重生。
- 消费点：**仅诊断**（`MoveStep`/`MoveStepWindow` 的 `epoch=`、`MoveDiag` 的 `epoch=`、LEAD 告警文案）。
- **不上线**：`MovementCommand`、`AuthoritativeMovementState` 均无 epoch 字段 ⇒ 服务器无法区分 epoch ⇒ **D3**（旧 epoch 输入可进入新 epoch）。

## 6. PredictionBuffer / Queue Audit

### 6.1 PredictionBuffer

- 三容器：`_commands`(tick→cmd)、`_predicted`(tick→snapshot)、`_tickOrder`(FIFO)；`TryStore` 拒绝同 tick（防重复模拟）；`EvictOldest` 容量 128（**当前 lead ≤ 16 ⇒ 不可达**，故"容量淘汰→HistoryMissing"在正常负荷下不发生）。
- **`_commands` 与 `_predicted` 允许不同步**（设计）：`InvalidatePredictedAbove` 只删 `_predicted` ⇒ 出现"command 存在但 predicted 不存在"的合法状态（重放缺口后的 (replayed,newest]）。此时后续 ACK 若落在该区间：`TryGetPredictedAndPrune` 失败 ⇒ **HistoryMissing 硬对位**（合理，但会造成一次额外 Snap）。
- `TryGetPredictedAndPrune` **原子顺序正确**（先取后删）✅；`PruneUpTo(ack)` 在查询失败时**仍然剪枝**（删 ≤ack）⇒ 后续 `HardSnapTo` 的 Replay（ack+1…newest）不受影响 ✅。
- `OldestTick/NewestTick` 在 `PruneUpTo`/`EvictOldest` 中维护；`Clear()` 归零 ✅。`NewestTick` 只在 `TryStore` 递增 ✅（不会因剪枝回退）⇒ `_localTick` 与 `NewestTick` 不会互相倒退（避免 `TryStore` 静默拒绝）。

### 6.2 ServerInputQueue（含边界）

- `Enqueue` 边界：首包未来 tick>32 拒（`DroppedFuture`）；已处理则 `tick ≤ LastProcessedTick` 拒（`DroppedStale`，**含冗余重传**）；同批重复拒（`DroppedStale`）；超 16 丢最旧（`DroppedBacklog`）；**无 epoch 校验（D3）**。
- `Drain(maxCatchUp,out)`：按最小 tick 升序；`LastDrainGap` 统计跳号；`SkippedTicks += gap`；`ConsecutiveEmptyTicks` 由是否消费决定。**当前唯一调用点 `Drain(1,…)`** ⇒ 结构上限 1 条/tick（R1）；`ServerMaxCatchUpPerTick=3` 属**未接线的配置**（非 dead field：它定义了意图，但没有调用点——判定为"未完成的重构/遗留"）。
- **`Clear()` 语义判定**：只清 `_pending`，**保留 `LastProcessedTick` 与 `_hasProcessed`**（同时重置 `ConsecutiveEmptyTicks`/`LastConsumedCommand`）。
  - 静态判断：这是**设计要求**（tick 必须跨冻结/死亡单调，否则解冻后旧 tick 会被当作新输入），因为服务器侧唯一的幂等键就是 tick；**但它把"跨会话/跨 epoch 复用同一实例"变成不安全**：若同一实例被用于新连接（当前每次都新建实例 ⇒ X4 排除），新客户端的低 tick 会被全部 `DroppedStale` ⇒ 该玩家永久无法移动。⇒ 归为 [Structural Risk]（当前不可达，但无任何会话/epoch 标识保护）。

### 6.3 命令连续性证明（R5 可达性的静态判定）

目标：证明 `HardSnapTo` 的重放循环 `for tick = ack+1 … newest { if (!TryGetCommand(tick)) break; }` 在当前代码下**不会提前 break**（即不会出现 `replayed < newest`）。

1. 命令**生成**：`uint tick = ++_localTick`（`RunOwnerPrediction`）⇒ 严格 +1，无跳号；
2. 命令**入缓冲**：`TryStore` 仅在"同 tick 已存在"时拒绝 ⇒ 不会覆盖，也不会产生空号；
3. 命令**被剪枝**：只有 `PruneUpTo(ackedTick)`（删 `≤ ack`）与 `EvictOldest()`（容量 128）会删命令；前者删除的都在 `ack` 之下（重放从 `ack+1` 起），后者需要 `_commands.Count ≥ 128`，而 `Count ≈ lead ≤ ServerMaxPendingCommands=16`（服务器侧同步上限）⇒ 不可达；
4. `InvalidatePredictedAbove` **只动 `_predicted`**，不动 `_commands`；
5. 会话/接管重置统一走 `ResetOwnerPredictionState`（`_buffer.Clear()` + `_localTick=0`）⇒ 不会留下"半清空"的命令区间。

⇒ **当前不变量下 `replayed == newest` 恒成立，R5 不可达**（归入"结构脆弱但有隐式不变量保护"）；一旦引入"压缩命令/跳号/丢命令，但保留后续 tick"的任何改动，该路径会静默变成**永久性状态脱节**。建议（§15）加显式断言（`replayed != newest` 时 **必须**把 `_localTick` 设为 `replayed`，或直接重基到 `ack`）。

## 7. Reconcile / HardSnap / Replay Audit

### 7.1 判定链的静态顺序缺陷（D1，Critical）

```csharp
var decision = Reconciler.Decide(state.Snapshot, predictedAtAck, out var correction);   // ① raw error
if (decision.Action == ReconcileAction.Snap) { Debug.Log(...); HardSnapTo(Snap); return; } // ② raw ≥ 0.75 → 立即硬对位
…
Vector3 inFlight  = _correctionLedger.ConsumeInFlightAfter(state.LastClientTick);          // ③ 只在非 Snap 路径才做
Vector3 corrected = correction - inFlight;                                                  // ④
_diag.LastErrorMeters = correction.magnitude;                                               // ⑤ 记录的也是 raw
```

**最小数学示例（静态可证）**：`raw = 0.78m`，`inFlight = 0.20m` ⇒ `corrected = 0.58m`。
`0.58m < ReconcileSnapMeters(0.75)` ⇒ 按设计应走 **Smooth**（0.03–0.75 带内），但 ② 已在 raw 上判 Snap ⇒ 实际走硬对位。
⇒ **该路径不是"误差真的大"，而是"误差被在途修正量系统性夸大"**。且由于 ③ 每次都在 Snap 时被跳过、`HardSnapTo` 又执行 `Ledger.Invalidate()`，**在途量每次都从零重新累积**，使该放大效应在"误差贴近阈值"的状态下**可反复重现**。

**与历史日志形态的一致性（仅作为"形态吻合"，不作为根因判定）**：历史 `SNAP err=0.753~0.808`（全部略高于 0.75）与"平滑带从不命中（`smooth=0`）"两者，正是 D1 的预期表现；但历史 `err` 是 raw（G3），**无法反推 corrected 是否真的低于阈值**。

### 7.2 `IdleStepsAtSnapshot` 的时序错配（D2，High）

- 设计意图（字段注释）：告诉客户端"本快照位姿比 ACK 多推进 k 步"，避免把延迟当分叉。
- 实际消费：`_lastIdleStepsAtSnapshot = state.IdleStepsAtSnapshot`（只赋值）、`MoveDiag`/`MoveStep` 打印；**`Reconciler.Decide` 不接收该参数**。
- 后果：外推（≤8 tick）或空命令期间的位移全部进入 `err` ⇒ 冲刺下 k=7 时 ≈0.78m ⇒ **单张快照即可触发 Snap**（无需任何真实分叉）。

| `_ticksSinceSend/_inputEpoch/_snapCount/诊断` | ❌（设计：诊断/相位） | — |

### 7.4 冻结（菜单/聊天/记分板）→ 外推 → 虚假 Snap 的静态场景推演

1. 玩家开菜单 ⇒ `GameplayInputGate.InputBlocked=true` ⇒ `LocalMovementFrozen=true`（**仅客户端**）⇒ 客户端不再 `RunOwnerPrediction`/`SendUnackedCommands`（`Update` 在冻结分支提前 return）；
2. 服务器的 `MovementFrozen` 只看 `MatchLifecycle.InputFrozen` 与 `IsDead` ⇒ **不冻结** ⇒ 继续 `ServerTick` ⇒ 队列走空 ⇒ `ConsecutiveEmptyTicks` 增长 ⇒ **按最后已知输入外推 ≤8 tick**（角色继续跑 0.27s）后再空命令刹停；
3. 期间服务器持续 `TargetAuthoritativeState` ⇒ 快照的 `Snapshot.Tick = LastClientTick + k`，`IdleStepsAtSnapshot=k>0`；
4. 客户端仍在接收 RPC（`ApplyOwnerAuthoritativeState` 不检查冻结）⇒ `_gate` 前进 ⇒ 与 `predicted@LastClientTick`（开菜单前预测的旧快照）比较 ⇒ **误差 ≈ k × 步长**（冲刺 k=7 ⇒ 0.78m）⇒ raw ≥ 0.75 ⇒ **Hard Snap**（且 `err` 恰落在 0.75~0.81 区间）；
5. 菜单关闭后，`_localTick` 已因 `HardSnapTo` 前移，客户端继续预测 ⇒ 若玩家再次开关菜单，循环重现。

> 该场景**完全由静态代码路径推出**（不依赖任何运行时猜测）：单向冻结 + 外推 + `IdleStepsAtSnapshot` 未消费 + Snap 用 raw。它解释了"单边（只有开菜单的那个客户端）+ 一次性可复现 + 反复出现"的形态；**但它不能解释"持续数分钟、每 7 tick 一次、与菜单无关"的风暴**（那种风暴要求误差持续被重新制造 ⇒ §8 的物理世界分歧）。

### 8.3 `ServerLagCompensation` 与移动的关系（区分清楚）

- 注册内容：`RegisterPlayer(transform, GetComponentsInChildren<Collider>(true))` ⇒ **包含根 CharacterController**（`CharacterController : Collider`）。
- `TryBeginRewind(tick)`：把注册碰撞体移到历史位姿；`EndRewind()` 恢复。作用域=**射击判定**（`ServerFireRequest` 内 try/finally），与移动模拟无时间重叠（同线程顺序执行）。

## 13. Root-Cause Candidates（基于当前静态源码）

> 规则：不指定唯一根因。每个候选给出"静态证据 / 能解释什么 / 不能解释什么"。

### Candidate A：**"外推/空命令位移"被当作误差**（D2）
- **静态证据**：`IdleStepsAtSnapshot` 无消费者；外推路径 `Snapshot.Tick = LastProcessedTick + k`；客户端固定用 `LastClientTick` 取配对快照。
- **能解释**：单边（只有队列会走空的客户端）、误差恰在阈值上方（冲刺 k≈7 ⇒ 0.78m）、`smooth=0`（raw 直接过阈值）、可反复出现（每次开菜单/卡顿/批次间隙）。
- **不能解释**：本局 conn=0 的 `empty/extrap` 采样多为 0（G2 口径限制使"整局是否外推"无法从日志反证）；也不能解释"持续数分钟、每 7 tick 一次"的规律性。

### Candidate B：**物理世界时间不一致（远端权威位姿 + 无世界回溯）**（R2+R3，配合 D1）
- **静态证据**：`RemoteAuthoritativeCollisionEnabled=true`；远端根=NT 插值位姿（RTT/2+1tick 滞后）；服务器模拟同 tick 时面对的是"当前"世界；`BodyHitbox` 为 trigger ⇒ 唯一接触面=根 CC；无环境 rewind。
- **能解释**：误差以**移动全速**增长（接触面上"一端被挡住/另一端没有"= 一整个 step 的差）；单边性（只有处于推挤/贴墙关系的一方反复被拉回——与上一轮日志"追击方/被追方不对称"一致）；持续性（只要两人保持接触关系，误差每 tick 重建）。
- **不能解释**：为何 `snapFrom→snapTo` 的原始位移恰为"lead×速度"量级；也无法从静态证明历史 SNAP 必由此触发（需 G4 的输入签名与世界位姿对账）。

### Candidate C：**校正路径选择缺陷放大并维持 Snap 风暴**（D1）
- **静态证据**：Snap 判定在 in-flight 扣除之前；`err` 记录 raw；Snap 时 `Ledger.Invalidate()`。
- **能解释**：为什么"误差一旦贴近 0.75 就永远走 Snap 而从不进平滑带"（`smooth=0`）、为什么 `err` 全部挤在 0.753–0.808、为什么"一旦开始就停不下来"（每次 Snap 重置台账，放大条件重新成立）。
- **不能解释**：它**不是**误差的产生源（不产生位移差）；无 correct 值（G3）⇒ 无法量化其贡献。

### Candidate D：**积压不可回收 + 相位错配**（R1，配合 D4/世界滞后）
- **静态证据**：`Drain(1)`；客户端可突发 5 步；两端速率相等；`ServerMaxCatchUpPerTick` 未接线。
- **能解释**：lead 一旦跃升就永不回落（历史实测 3→9）；硬对位的"原始位移"= lead×速度（玩家感知的"被拽回一米"）；世界滞后的持续存在。
- **不能解释**：tick 配对意义上的误差为何会持续（ACK 逐 tick 前进、配对同 tick，理论上应恒等）⇒ **必须与 A/B/C 组合**才能形成完整解释。

### Candidate E：**死亡/重生 epoch 污染**（D3）
- **静态证据**：无 epoch 上线；`Clear()` 保留 `LastProcessedTick`；客户端重生后从 `ack` 重新生成同号 tick。
- **能解释**：重生后短时（k=失效命令条数）的输入错配 → 一次或数次 Snap（瞬态）。
- **不能解释**：非重生时段的持续风暴（本局风暴窗口与死亡时刻不重合）。
