## 3. 必须修复的发现

### F01 [P1] 击杀归属晚于致死回调，且未造成伤害的命中仍登记

**位置**：`NetworkCombatAuthority.cs:274–292/397`，`WeaponController.cs:400–416`，`DamageableTarget.cs:51–59`，`MatchLifecycle.cs:716`（路径前缀 `Assets/_Project/Scripts/Gameplay/`，前两网络文件位于 `Network/`）。

调用顺序为 `TryFire → ResolveHitscan* → ApplyDamage → OnDied → HandleServerDied/ConsumeKillerOf`，之后才 `OnShotFired → HandleServerShot → RegisterHit`。首发致死时注册表尚无射手；A 先伤害、B 致死时死亡回调仍可能读到 A。死亡处理清表后，本次开火事件又把已死目标登记回去。同时 `RegisterHit` 只要求 `Target != null`，友军/无敌/旧生命拒绝伤害但保留 Target 的结果也可污染击杀和助攻来源。

**修复方向**：让伤害事务携带已验证射手，只有实际可结算伤害在死亡事件前登记；按生命代际清理。霰弹枪需逐受害目标归因，不能只登记聚合主结果。现有资格纯函数测试不覆盖调用顺序。

### F02 [P1] 两条手写迁移无法被 AppDbContext 发现

**位置**：`fps-backend/src/UnityFps.Api/Data/Migrations/20260917103000_AddServerInstanceMapId.cs:10`、`20260917112000_AddUserTokenVersion.cs:11`；`Program.cs:183`。

两类仅标注 `[Migration]`，没有 `[DbContext(typeof(AppDbContext))]`，也没有提供该属性的 Designer partial。本轮执行 `GetMigrations()` 确认列表停在 `20260915133417_AddProtocolIdColumns`。全新库/未手工修补库会缺少 `ServerInstance.MapId`、`UserAccount.TokenVersion`，地图租用或认证查询失败。

交接报告 §2.6 已记录发现缺列后手工 ALTER；§2.7.3 和 CODELY 后来归因为“启动链没有 Migrate”，与当前 `Program.cs:183` 直接冲突。正确归因是迁移发现缺失，不能继续要求所有环境手工补历史。

**修复方向**：修迁移元数据，保持原 migration ID；分别验证空库和已手工补录库，不重复加列；修正文档。

### F03 [P1] 热更新差量下载没有组装完整的新版本目录

**位置**：`UI/HotUpdate/HotUpdateManifest.cs:81–95`，`HotUpdateBootstrap.cs:92–123`。

计划按旧清单 hash 跳过未变化文件，但下载器只把变化文件写到新的 `HotFiles/<remote.version>/`，随后整个 loader root 切到新目录。v1 有 bootstrap、career、地图，v2 只改 career 时，新目录没有 bootstrap 和地图；Lua 会混入内置旧脚本，map_04 无法入场。若只提高版本号、所有内容相同，计划返回 UpToDate，却指向未创建的新目录，冷启动也可能失去已安装包。

**修复方向**：新版本完整物化（复用前验证磁盘文件、复制或安全共享不可变内容）后才切根；不能只信 installed.json 的 hash 字段。

### F04 [P1] 断网/坏 manifest 的早返回没有恢复已安装根目录

**位置**：`HotUpdateBootstrap.cs:65–76`。

两条分支只把日志标为 `fallback-installed` 后 `Finish`，未调用 `ApplyInstalledRoot()`。新进程的 `HotFilesRoot` 初值为 null，已有热更包仍回到内置脚本，已安装热更地图不可见。历史“断服务仍可用”的同进程结果可能保留静态 root，不能覆盖冷启动。

**修复方向**：所有失败出口共用已安装版本恢复与完整性检查；冷启动、静态状态为空时验证。

### F05 [P1] 热更新的“原子提交/不可变目录”保证没有成立

**位置**：`HotUpdateBootstrap.cs:100–120`，`Tools/HotUpdate/Publish-HotUpdate.ps1:75` 起制包/部署段。

下载文件直接覆盖目标版本目录，指针使用 `File.WriteAllText`。发布脚本允许删除并重发同一版本。已装 v2 又发布不同内容的 v2 时，前几个文件已覆盖、后一个校验失败，虽然不写新指针，旧 v2 目录已经混合；进程在写 installed.json 时退出也可能留下截断指针。新建版本路径也没有“临时指针→原子替换”的步骤。

**修复方向**：禁止同版本不同内容重发；临时目录完整验证后发布；安装指针与服务器 manifest 均采用临时文件原子替换；保留可验证的上一个完整版本。

### F06 [P2] 发布手册的回滚操作被客户端降级门拒绝

**位置**：`HotUpdateManifest.cs:76–77`、`Publish-HotUpdate.ps1` 尾部、9 月 17 日热更报告 §4。

手册指示覆盖旧 manifest 回滚，但已装更高版本的客户端固定返回 `DowngradeRejected`，继续运行问题版本。本轮生产决策探针确认。

**修复方向**：保留防意外降级，回滚采用“新发布版本号承载上一版内容”；同步脚本、手册与验证用例。不要无条件关闭降级保护。

### F07 [P1] 多地图启动不幂等，覆盖状态文件会丢失旧进程归属

**位置**：`Tools/Server/Start-LocalServer.ps1:74–120/253/351`。

`Start-MapDsInstances` 每次无条件起四个进程，不读旧 map-servers 状态、不验证端口/PID/构建身份。主 DS 已存在的重跑分支仍调用它；随后以新 PID 覆盖状态文件。端口冲突的新进程即使失败，旧健康进程也可能变成停止脚本不再掌握的实例。9 月 19 日交接记录过多次启动后残留进程，当前源码仍有这一路径。

**修复方向**：逐实例发现、身份核验、复用或明确失败；仅成功启动/验证的记录合并落盘；失败返回非零，停止工具保持精确进程归属。

### F08 [P1] 主 DS 已运行会绕过后端恢复，CheckOnly 也可能起进程

**位置**：`Start-LocalServer.ps1:203–269`。

后端健康失败且端口空闲时只置 `backendAction='start'`；发现托管 DS 后在 255 行退出，真正启动后端的 269 行永不到达。同时 `CheckOnly` 门位于这一提前退出分支之后，`-CheckOnly -AllMaps` 遇主 DS 已运行会调用实际的 `Start-MapDsInstances`。

**修复方向**：先完成无副作用的状态规划，CheckOnly 在任何启动动作前返回；执行模式恢复并验证后端后，再收敛全部 DS。

### F09 [P1] 五个 DS 共用同一个结算补偿文件，存在覆盖丢单

**位置**：`Network/DedicatedServerBootstrap.cs:43/362/415`，`Network/MatchResultPendingStore.cs:22/90–98`；地图启动参数 `Start-LocalServer.ps1:90–96`。

每个进程都默认使用同一产品的 `Application.persistentDataPath/match-result-pending.json`，启动器未设置实例隔离目录。每个实例只持自己的内存 List，并使用同名 `.tmp` 覆盖整个文件。A、B 在后端不可达时分别保存结算，后写者可覆盖前者；同时写则竞争临时文件。单进程“主线程单写者”前提已被新增多地图部署破坏。

**修复方向**：目录至少按稳定 instanceId 隔离，并绑定服务环境；对旧共享文件提供一次性迁移/人工核对策略。保存失败不能仍声明“已落盘”。

### F10 [P2] DS 在 MonoBehaviour 字段初始化器调用 Unity API，9 项测试持续失败

**位置**：`DedicatedServerBootstrap.cs:43`、`MatchResultPendingStore.cs:22`。

本轮完整复跑再次得到 `get_persistentDataPath is not allowed ... constructor`，并带出 GuardOnly 变 None 的断言失败。它是生产类初始化方式违反生命周期约束，不宜描述为无需处理的“测试环境伪影”；本轮不据此断言所有 DS 构建均无法启动。

**修复方向**：在明确主线程生命周期阶段、有效 options 可用后创建带显式目录的 store，与 F09 一起修；测试注入隔离临时目录，不能通过忽略日志掩盖异常。

### F11 [P1] 复合受击胶囊肩颈接缝只点接触，存在可命中宽度骤缩

**位置**：`PlayerNetworkAdapter.cs:213–226/260–264`；`Tests/EditMode/BodyHitboxAlignmentTests.cs`。

躯干 centerY=.70、height=1.40、r=.26，顶部 y=1.40；头 centerY=1.60、height=.40、r=.15，底部也为 y=1.40。胶囊顶/底为球冠，两个极点相切不等于有限体积重叠。横射 y=1.40、x=.10（z 对齐中心）会漏过两体；y=1.39 时可命中半宽仅约 .071m，远小于躯干标定半宽。当前端点纵向测试只能证明上下极值相接。

**修复方向**：以真实姿态四向扫描确定肩颈过渡的有限重叠及宽度；不要盲目扩大整个人体回到旧“空气命中”。补二维射线覆盖和连续复活后的几何测试。可见蒙皮轮廓仍列实机待验。

### F12 [P1] 重生补弹只重置服务端，Owner 本地开火运行时仍可能空仓

**位置**：`NetworkCombatAuthority.cs:505–515`、`WeaponController.cs:226–235/306–311/350–356`、`NetworkWeaponState.cs:197–210/283`。

`ServerResetAmmoToLoadoutDefault` 只在服务端重生调用。`_currentAmmo/_reserveAmmo` 为 HUD 提供权威数值，却没有 OnChange 回写 Owner 的 Runtime 或其按枪缓存。客户端空仓死亡后，HUD 可显示满弹，但本地 `TryFire` 仍被 `TryConsumeRound` 拒绝；服务器仍接收 FireHeld 请求并开火，Owner 又被 ObserversFire 排除，于是本地动画/音效/后坐可能缺失。现有 RespawnAmmo 测试只断言单个服务端 controller 与事件。

**修复方向**：以权威生命/弹药快照重置 Owner 预测态和两槽缓存，处理回包先后，避免普通弹药同步抹掉尚未确认的本地预测。补双端空仓重生测试。

### F13 [P1] 射击后坐与压枪债务两端仍不同源，位置预测通过不代表弹道一致

**位置**：`WeaponController.cs:159/228/410`，`WeaponRecoilState.cs:55–59/OnShot`，`Locomotor.cs:138–142`，`PlayerNetworkAdapter.ApplyRemotePitch`；9 月 16 日 yaw 报告 §1.4、9 月 17 日 SNAP 报告 §4。

各 controller 使用默认 `new WeaponRecoilState()`，seed=0 时各自 `new System.Random()`；债务恢复在渲染 Update，yaw 消费却发生于固定模拟/重放。客户端与 DS 的帧率、随机序列和接受发次均可不同，且开火协议不携带同源 shot seed/完整瞄准状态。历史实机已记录残余 pitchGap，本轮源码未发现完成该专项闭环的改动。

**修复方向**：先定义同源发次、随机种子、瞄准采样时刻与债务演化模型，再统一 tick 化或将纯表现与权威瞄准分开；不得仅扩大 SNAP 阈值掩盖。需要协议改动时递增版本并同批双端验证。

### F14 [P2] 冻结期丢包门不能隔离重生之后才到达的旧输入

**位置**：`PlayerNetworkAdapter.cs:940–955/98–99`，`Movement/MovementSimulationTypes.cs:14–34`。

`_inputEpoch` 只是本地诊断，MovementCommand 没有 life/session epoch。服务端仅在“收到时仍 Frozen”拒收。死亡前在途批次延迟至复活后到达，冻结门已开；tick 仍落未来窗口时会作为新生命输入消费。v5 的递增仅用于生命 SyncVar，没有落实报告延期的输入 epoch。

**修复方向**：协议携带服务端可校验的输入代际；丢弃旧代际并清空队列，Owner 重生基线一致推进。用定向延迟/乱序例证明，而非仅测试 Frozen=true 的分支。

### F15 [P1] 同账号并发登录可产生两个同时有效的 token

**位置**：`fps-backend/src/UnityFps.Api/Services/AuthService.cs:34–47`、`Data/AppDbContext.cs:35–45`、`Program.cs:87–106`。

读取用户后在内存执行 `TokenVersion++`，无原子数据库增量、行锁事务或该字段的并发令牌。两个请求都读 v，再分别保存 v+1 并签发 tv=v+1；两个 token 都通过后续验证。现有单活测试只覆盖串行再次登录。

**修复方向**：使用可重试的数据库原子更新/事务，签发的版本必须对应本次已提交登录；以两个独立 DbContext 的真实关系库并发测试证明只有最后一次有效。

### F16 [P2] 构建新鲜度门遗漏资产等输入，坏时间戳也可能判 OK

**位置**：`Tools/BuildStatus.ps1:41–49/75/87–97/126`。

只比较 `_Project` 三目录 `.cs` 的 mtime，遗漏 prefab、场景、ScriptableObject、asmdef、Packages、ProjectSettings、XLua 源码/生成绑定；反而把仅编辑器测试变更计入双端。manifest 存在但 builtAtUtc 无法解析时 `$built` 为 null，不进入 STALE 分支；“运行中 DS”仅取最新日志，没有证明对应进程仍活着，也未覆盖四个地图日志。

**修复方向**：构建时写全输入集合的内容摘要，按 Client/DS/热更包区分；manifest 字段缺失失败关闭；运行态结合 PID、进程路径、启动时间与各实例清单核验。mtime 可保留为辅助提示。

### F17 [P2] 热更地图加载失败清了本地房间，却向调用者返回入场成功

**位置**：`UI/LobbyPresenter.cs:466–467/527–542`、`Pages/LobbyPresenter.WaitingRoom.cs:157` 起。

bundle 文件存在但损坏时，`LoadArenaAsync` 清 launch/context、清 Room、回大厅后正常 return。`EnterBattleAsync` 随即返回 true，轮询结束；后端成员/已发票据未走对称失败清理，用户本地也失去返回房间上下文，只能依赖控制面超时清理。

**修复方向**：加载返回显式结果；失败保留可恢复房间会话或完成相应后端失败/离开事务，不能仅清本地；重试须重新取票并防旧代际回包。

### F18 [P2] 热更新版本路径未校验，文件路径消毒覆盖不到根目录

**位置**：`HotUpdateBootstrap.cs:100/164–168`，`HotUpdateManifest.cs:113`。

`remote.version`/installed.version 直接参与 Path.Combine；只有 file.path 被消毒。包含 `../` 或绝对路径的版本字符串会把目标目录移出 HotFiles，且比较器允许非数字版本。此项是导入清单边界缺陷；未宣称现场服务遭攻击。

**修复方向**：版本限定合法单段、严格解析；最终规范化路径必须仍位于预期根；所有项在下载/写盘前整体验证。保留拒绝诊断，测试不得真的向根外写文件。

### F19 [P1] 半自动武器的联网请求按 FireHeld 连续提交

**位置**：`PlayerNetworkAdapter.cs:821–826` 对比 `WeaponController.cs:234–235` 与 `NetworkCombatAuthority.cs:59–105`。

本地武器按 FireMode 区分 FirePressed/FireHeld，但联网 adapter 一律 FireHeld 每帧请求；服务器只校验死活、去重、冷却和弹药，没有一次按下只接受一发的规则。长按半自动手枪可在服务器按 RPM 连续射击，本地却只表现一发，放大 F12/F13 的发次分叉。这是沿用旧实现的真实链路缺口，不宣称由本轮复合命中盒提交引入。

**修复方向**：统一输入语义与服务端约束；按已接受 shot 序号驱动表现/随机状态，保证冷却拒绝不会重复登记。补半自动长按、自动长按、松开再按的双端矩阵。
