## 3. P0：枪模隐形的确定链路

### 3.1 同一 Renderer 被两个管理器保存

旧链：`Presentation/Camera/FPCameraRig.cs:60–100`（执行序-40）死亡时遍历整个CameraPivot子树，保存原先enabled的Renderer并禁用；复活恢复为true。

新链：`Gameplay/Network/NetworkCombatAuthority.cs:820–875`（常规Update默认序）调用Owner的 `FPWeaponRig.ApplyDeathState`；后者在 `Presentation/Animation/FPWeaponRig.cs:180–240`调用原先给镜内遮罩使用的 `SetScopedViewmodelHidden(true)`，把当前Renderer.enabled逐个存入字典。复活延迟一帧将字典值写回。

常规Update顺序的反例：

| 时点 | Renderer.enabled | 相机保存值 | Rig保存值 |
|---|---|---|---|
| 活着 | true | — | — |
| 相机处理死亡 | false | true | — |
| Rig处理死亡 | false | true | **false** |
| 相机处理复活 | true | 已恢复 | false |
| Rig复活协程下一帧 | **false** | — | 清空 |

这是具体的状态覆盖，不是笼统的“可能没加载模型”。RPC提前触发时顺序可以不同，因此也不能用某一次正常复活否定。当前日志hiddenRenderers=8/14、复活恢复8/14只能证明**相机写回过**，不能证明下一帧Rig没有再次关闭。

只影响“死时当前枪”也符合：Rig缓存当前_activeView的Renderer；未被同样污染的另一把枪可显示，之后持它死亡又被污染。

### 3.2 还必须合并 ADS 隐藏原因

`Presentation/HUD/OpticAdsView.cs:201–213`也调用同一个SetScopedViewmodelHidden(bool)。现在死亡和镜内隐藏共享一个bool及一张Renderer快照：退出ADS可能释放死亡隐藏；复活可能释放镜内隐藏。仅删除相机那段循环能够切断本次主要链路，但不完成这些重叠状态的正确性。

### 3.3 Codely 修改方案

1. **FP可见性唯一写者交给FPWeaponRig或其专用可见性组件。** FPCameraRig只管相机位置/Dutch/FOV，不再直接保存恢复FP Renderer。保留当前有效的FP Idle重建逻辑，禁止回滚到停用整个Animancer的旧方案。
2. 使用明确的隐藏原因，例如Death、ScopeOverlay、RespawnPreparing，最终可见性由所有原因合成；各系统只能增加/释放自己的原因。适配现有IsScopedViewmodelHidden的语义，不把“任意隐藏”继续误当“镜内隐藏”。
3. Renderer基线在受控注册/视图创建时确定，不能把其他系统的临时隐藏读成作者原始状态；不得一律enabled=true，否则原本关闭的网格/附件会被错误打开。动态附件/池化视图注册到当前可见性状态，切枪时持续继承死亡原因。
4. 替换无保护的ShowViewmodelNextFrame：携带生命周期generation/视图身份，离开场景、重新死亡、切枪或Disable时取消过期恢复；恢复只释放自己的RespawnPreparing/Death原因，不释放ScopeOverlay。不要通过多加几帧等待解决逻辑竞态。
5. 死亡入口与TP_Model查找解耦：当前ApplyOwnerFpDeathState(true)在TP幂等闸之前，Reset里的FP恢复又在wasActive检查之前；TP缺失/回调重复也不能令FP反复缓存或重复排队协程。FP应有自己的幂等状态。
6. 核实FPWeaponMotion实际挂点与当前 `_activeView.TryGetComponent` 入口是否相符；只有命中了实际实例才能声称运行态缓存被清理。本项是实施检查，不把现有反射方法“能查到”当完整对象链证明。

## 4. P1：激光残留是持续写者绕过了隐藏

`Gameplay/Weapon/LaserSightBeam.cs:109–133`每个LateUpdate只判断Ads01；腰射条件满足就 `_line.enabled=true`。死亡新逻辑刻意保留视图GameObject激活，因此OnDisable不会被调用。FPCameraRig/FPWeaponRig关LineRenderer之后，下一LateUpdate又将其打开。复活枪体因为第3节保持false，激光组件仍更新，便出现视频中的“无枪红线”。

方案：保留LaserSightBeam作为LineRenderer的最终写者，但它必须读取共享的有效视图可见性/生命周期闸门：活着、当前有效FP视图、非Death/RespawnPreparing/ScopeOverlay隐藏、并满足既有ADS出束规则时才允许开线。没有有效Owner/视图上下文时不应默认出束。Gameplay组件不得倒向引用Presentation，可用接口、显式SetPresentationVisible注入或既有Gameplay状态源。

死亡边界立即关线，死亡后每帧维持关闭；新装配激光、池化再激活也先应用闸门，防首帧闪线。恢复只放行当前有效视图，保留器件轴向、配件精度buff、换弹随枪摆动等既有语义。不要仅把LineRenderer塞进一次性Renderer列表，也不要为修激光停掉整个武器GameObject。

## 5. P1：聊天退出只清数据，没有真正卸载

### 5.1 完整链

- `LobbyPresenter.WaitingRoom.cs:106`将聊天挂到整个Canvas。
- `ChatHudView.TryMount:69–76`建Canvas直接子物体ChatHud，并全场FindFirst复用旧实例。
- `LeaveWaitingRoomAsync:318–326`确实调用了StopAndClear；**不能归因成“退房忘记调用停止”。**
- `ChatController.StopAndClear:82–99`只设_running=false、清历史/草稿、解RPC订阅、清静态Instance；不Close、不Disable、不Destroy，不解绑View的SendRequested/Closed/ChannelChanged。
- `LobbyPresenter.Navigate:80–120`只ClearBody；Canvas下ChatHud不在bodyObjects列表内，所以大厅和登录页继承残留窗口。
- `ChatHudView.Update:206起`仍处理Enter，没有“当前是否有房间/此页面是否允许聊天”的闸门。清历史甚至会令ENTER提示重新出现；展开窗口也未被关闭。
- `LobbyPresenter.Logout:532`只清token/session并导航，未清理Chat。没有房间后Hud仍能抢焦点。

### 5.2 同链附带回归

再次入房时EnsureRunning在Instance=null下，通过TryMount找回旧View/旧Controller，又执行三次事件 `+=`。旧View事件从未解绑，于是同一Controller可能收到重复SendRequested，生成不同clientMessageId，服务端去重也无法合并。此为代码可达缺陷，本轮不声称用户已观察到重复消息。

StopAndClear在Instance==null时直接return，静态ChatRoomSession有机会不清；OnDestroy只有Instance==this才解订阅，对多实例/替换不够稳健。HTTP仅用destroyCancellationToken，Stop不销毁便不取消请求；仅按roomCode判断迟到结果也不能区分退出后重进同一房间的新一代会话。

### 5.3 Codely 修改方案

1. StopAndClear成为幂等的房间会话退出入口：无Instance也清ChatRoomSession；有实例则停止收发、取消会话请求、解绑所有View/RPC事件、清pending发送、关闭输入与IME、释放聊天焦点，然后立即SetActive(false)并Destroy聊天根（避免Destroy帧尾前被再次找到）。清静态Instance时核对引用身份。
2. 区分“退出房间/登出”和“仍在同一房间、切场景返房”。后者销毁/解绑UI但保留ChatRoomSession历史，前者清历史/草稿/游标。不要在每次OnDestroy无条件清房间历史。
3. 在房间生命周期变化和Logout/SessionExpired/异常退房/Gameplay主动退出路径统一调用退出入口；AccountSession已有Changed事件，可订阅鉴别Room为空或用户身份变化。页面导航增加允许显示上下文的兜底，但不要使留房切场景误删历史。
4. TryMount/EnsureRunning限定目标Canvas与房间会话generation；不允许任意画布的旧Hud当作成功挂载。反复调用只保留一套UI、一份事件订阅。无有效登录/房间上下文不能创建可交互聊天。
5. 每次会话采用独立取消源与generation，Fetch/Send回包同时核对generation和roomCode，退出重进同一房也拒绝旧响应；Stop清理RPC pending草稿计时，避免复活旧草稿/错误提示。
6. 停止后的Enter不应打开聊天或设置GameplayInputGate.ChatFocused；大厅/登录鼠标保持页面管理，不被聊天残留抢走。当前409作为转换期诊断保留；正确取消不再产生持续的无上下文HTTP轮询。

## 7. 必须能抓住本次失败的定向回归

现有FPCameraRigDeathViewTests单测相机恢复Renderer，恰好不能覆盖“相机恢复后Rig下一帧又关掉”。不能再只测各组件独立函数均成功。

1. **死亡双写时序反例**：真实层级同时有FPCameraRig、FPWeaponRig和至少一个原本关闭Renderer，分别模拟相机先/Rig先；复活下一帧及再后若干帧，作者可见网格必须显示、作者隐藏网格继续隐藏。
2. **多原因组合**：Death与ScopeOverlay同时存在，释放任一不影响另一；复活准备完成才允许显现。含ADS中死、按住ADS复活。
3. **池化与异步**：M4死→复活→切手枪→死→复活→切回M4，另测复活下一帧前再次死/切枪/退出，旧协程不得恢复错误视图。
4. **实际LateUpdate激光**：死亡后跑若干帧，而不是只断言死亡入口关过线；光束每帧都必须关闭。隐藏期间换配件/激活缓存枪不能闪线，正常活着腰射仍可出束。
5. **聊天完整对象生命周期**：展开/收起分别退房，进入大厅再登录页，多帧后没有活动ChatHud、Enter不抢焦点；反复进入退出三次后只一份SendRequested订阅、单次发送仅调用一次API。
