# 一枪后红方获胜、下一局卡在进入战场：审计与 Codely 修复方案

日期：2026-09-15。用户要求：查看刚刚实测的服务器日志，查清问题链路，提供 Codely 可执行方案。本文基于当前脏工作区与实际运行日志，不把旧报告中的指令作为本次授权；不是修复完成报告。

## 0. 结论

这是两条连续触发的问题，不是“一枪达到胜利条件”，也没有证据指向高延迟：

1. **旧 DS 进程仍在运行，新客户端开火协议已变更 → 解析未知包踢掉蓝方 → 两人局按 PlayerLeft 判剩余红方获胜 → 红方正常进入结算/返房。**
2. **第二次加载 Arena 时，旧 NetworkSystems 跨场景存活，新实例被销毁；连接入口只在 NetworkHud.Start → 新一局启动上下文无人消费 → 没有再次发起连接，停在加载画面。**

期间确有多次 NO_SERVER_AVAILABLE，但后端后来已成功分配下一局，不能用“没有服务器”解释最终一直卡住的画面。

本轮仅保全证据、读代码并写方案；没有重启/停止服务，没有修改产品代码、场景、数据库，没有测试或 git commit。当前没有可直接向 Codely 派发任务的工具，请其读取本文件接手。

### 2.1 为什么是旧进程 / 新协议

实际进程读取结果：PID **35604**，StartTime **2026-09-15 17:04:51**，路径 `Builds/Server/UnityFpsDedicatedServer.exe`。当前磁盘 `Game.Gameplay.dll` 修改时间为 DS **19:31:13**、Client **19:32:46**。覆盖磁盘构建不等于运行进程重载程序集。

上一份 Codely 修复报告 §4 明确新增 RPC 参数：

```csharp
// 旧协议
ServerFireRequest(uint estimatedServerTick)
// 当前源码 Assets/_Project/Scripts/Gameplay/Network/NetworkCombatAuthority.cs:54
ServerFireRequest(uint shotRequestId, uint estimatedServerTick)
```

客户端快照确有新 `[FireTrace] submit id=...` 与新 AUTHORITATIVE_WEAPON_APPLY 日志；运行 DS 没有对应 FireTrace resolve/reject，仍输出旧式 CombatDamage/LagComp。进程启动时间、旧日志格式、RPC 新参数、未知包踢人构成高度一致的证据链。

`req=1` 很可能是新请求的第一个 shotRequestId 被旧 reader 当成 estimatedServerTick；剩余参数使后续包读取位置错位。FishNet 本地源码 `ServerObjects.Parsing.cs:19` 将 reader 交给目标 RPC reader；`ServerManager.cs:820–862` 随后继续解析并对未知 PacketId 踢连接。**本轮未抓原始包或反编译运行中内存，不能把 55226 的具体字节来源写成已证实。**但无需先假设网络丢包才能解释现象。

上一份报告“构建期间无 DS/客户端进程在跑”与本轮进程现场不一致；应以运行态证据为准重新核验，不以报告中的构建成功替代部署验证。

### 3.1 确定的生命周期缺陷

1. `Assets/_Project/Scenes/Arena.unity:2304–2306`：NetworkManager `_dontDestroyOnLoad:1`、`_persistence:0`。
2. FishNet `NetworkManager.cs:48` 的 0 是 DestroyNewest；约 471 行新实例遇到旧实例会销毁新实例整个 GameObject。
3. `Assets/_Project/Scripts/Gameplay/Network/NetworkHud.cs:41–80`：唯一消费 TryBeginClientLaunch / 调用 StartConnection 的正式入口在 Start。旧实例首次 Start 已执行，返回 Lobby 后继续存在；新 Arena 的同名网络树又被销毁。
4. `UI/MatchSettlementFlow.cs:324–336` 返房只 StopConnection 再加载 Lobby，没有结束旧 NetworkSystems 的生命周期；异常断线 `MatchConnectionWatcher.HandleDisconnectLocally` 也类似。
5. `UI/LobbyPresenter.cs:433` 的 LoadArenaAsync 只等待场景加载，不等认证成功或 Owner 生成，没有针对“从未尝试连接”的超时。ClientAuthFailureHandler 的降级依赖 connectionAttempted；入口没运行就不会触发这条降级。

所以不是异步加载进度永远不到 100%；场景已加载到能执行 Bootstrap，却没有可用的联网 Owner 来完成入场。画面可能保留原加载相机内容，不能把截图当成 LoadSceneAsync 真正挂住的证据。

### 3.2 不能只再调用一次 StartConnection

跨局保留的状态还有：

- MatchConnectionWatcher 的 `_wasConnected/_handled` 只在 OnEnable 重置，常驻对象并不保证再次 OnEnable。
- MatchLifecycle 的静态镜像/MatchExitState 重置同样依赖 OnEnable，不能假定加载场景就发生。
- ClientAuthFailureHandler.Bind 同一实例可直接 return，AuthFailurePolicy 中 `_accepted/_resultSeen` 没有新会话重置入口；第一次成功后下一次失败可能被忽略。
- 认证器票据会话、客户端连接事件订阅、场景内 Spawn Transform 引用、旧异步返房回调，都需要按新的 session generation 重新绑定/作废。

## 4. Codely 可执行修复计划（按顺序）

### P0-A：先收口运行版本，保持协议严格校验

1. 读取本轮证据并现场重新核实 PID/路径/启动时间，不能盲用本文的 PID 对象作停止目标。保全旧日志；只管理当前工作区对应实例。当前请求是方案审计，不代表本文已经执行重启。
2. 修复交付时使用同一源码批次的 Client+DS；明确停止旧 DS、等待该实例退出与端口释放后，启动新的 DS，并验证**新 PID/启动日志 buildId/protocolId、注册状态和实际业务标记**。不要只重新构建或覆盖文件。
3. 增加嵌入二进制的应用协议标识，覆盖 RPC 签名/网络 DTO 的兼容代际。不能只比较 FishNet 框架版本或固定 `-buildVersion local-dev`，也不能要求 Client/DS 条件编译 DLL 哈希相同。构建清单分别保存两端哈希，协议 ID 才跨端相同。
4. 启动入口 `Tools/Server/Start-LocalServer.ps1` 和构建交付流程加入“运行进程版本 vs 目标构建”检测；活跃旧进程不能被当成新构建已部署。旧版本有对局时明确标记需要升级，不自动强杀其他实例。
5. 在玩家生成/业务 RPC 之前执行应用兼容性校验，配合后端实例筛选。设计稳定的认证前握手格式并明确旧版缺字段处理；拒绝时客户端显示版本不匹配并返回可恢复页。不能再用不兼容的开火 RPC 来发现版本差异。
6. 不修改 FishNet 对未知 PacketId 的安全处理，不强行忽略残余字节，不把 PlayerLeft 改成永不终局来掩盖掉线。若要改变协议故障时的奖励/终局文案，单独提出产品规则，本次先修协议和提示原因。

### P0-B：显式每局客户端会话生命周期

推荐保留现有常驻 NetworkManager，增加应用层、按代际控制的启动协调器，避免改 FishNet 原厂：

1. 从 NetworkHud.Start 抽出可重复的 `BeginClientSession` 入口，使用本次连接代际（例如本地 generation + matchId）幂等化；同一代际最多一次尝试，同实例可依次启动不同代际。
2. 把“新 Arena 已就绪”作为触发条件。协调器应存活于不会被 DestroyNewest 丢弃的对象；如由常驻实例订阅 sceneLoaded，必须退订并过滤到目标场景。大厅 ConfigureClient 后进入场景、新场景就绪后由**实际存活的 manager**一次性消费票据，不依赖新实例 Start。
3. 新会话开启前等上一连接完全 Stopped，重置本局 MatchLifecycle/MatchExitState、Watcher、AuthFailurePolicy、认证器 ticket session，重新绑定必要场景引用。禁止旧返房/超时回调 Clear 新 launch 或 Stop 新连接。不要重置进程中的 Dedicated Server 或 Host 服务端状态。
4. 使用明确 SessionGeneration 防重入；状态建议为 Configured → SceneReady → Connecting → Authenticated → OwnerReady → Playing，失败/取消为终态。每阶段输出不含票据的日志；终局/断线后一套 EndClientSession 清理共用。
5. 另一可选方案是纯客户端结束会话后销毁完整网络树、确保销毁完成再返房，下次由新树启动；若选此方案，必须处理所有返房路径、静态引用与旧异步回调，不要只把 Arena 的 DontDestroy 勾选取消而误伤 DS/Host 或其他联网换场景。

### P1：加载失败可恢复与资源释放

1. 从 Configure/加载开始启动实时超时，而非等 StartConnection 被调用后才计时；SceneLoaded 后仍无 Connecting 也必须报错。连接/认证/Owner 生成分别记录阶段，给出失败原因与返回房间入口。
2. UI 的“进入战场完成”条件必须是本会话 Owner/相机/HUD 就绪，不能只等 LoadSceneAsync 完成。加载失败退出时清本代际票据、断本次连接、恢复输入/光标/UI。
3. 和后端现有返房/连接失败/租约过期接口衔接，确认无人连接的 Reserved 对局能在配置期限内回收；保留房间成员语义，不通过清库或把所有 Reserved 强改 Ready 修现场。
4. `readyFresh=0 reserved=65 inMatch=5` 包括历史记录的可能性，不能据此判定 70 个活跃实例都泄漏。按 instanceId/room/match generation/heartbeat/lease expiry 查本实例即可。
5. 两客户端启动默认分别带唯一 `-logFile`，加入 buildId、protocolId、PID/sessionGeneration/connId/matchId；否则下一轮无法精确归属开火和退场。

## 5. 必须验证的最短矩阵

1. 同批新 Client+DS：A/B 同房，开一枪 HP 正常下降（不要求一枪击杀），不出现 unknown PacketId、不提前 PlayerLeft。双向开火均关联 submit → receive/resolve。
2. **不重启两个客户端**：一局结束或手动返房后，再建/加入另一房，连续两次成功打印 Configured/SceneReady/Connecting/Auth/OwnerReady，DS 收到新认证。交换房主再测。
3. 第一局协议拒绝/异常断线后，第二局正常；第一局认证成功后第二局票据拒绝/服务器不可达，必须显示错误并返回，不能被上局 `_accepted/_handled` 吞掉。
4. 故意旧客户端配新服务器以及新客户端配旧实例：应在兼容性/部署门失败，业务战斗不开始；不要让真实比赛用第一枪做协议探针。
5. 在 SceneReady 前后取消/快速重进，旧 generation 的超时与返房回调不得断掉新局；同代际重复回调只尝试一次。
6. 无客户端连接的 Reserved 对局在约定期限释放，下一局可租用；不是靠重启后端/清数据恢复。

先做定向生命周期/幂等/超时测试，再做真实双进程连续两局验证。纯函数测试和构建成功不能证明 Start/DestroyNewest/跨场景时序已经修复。交付逐文件变更、真实运行版本、每局时间线、实际验证项与未验证项；不要默认 git commit。
