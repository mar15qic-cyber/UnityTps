### 0.1 必须达到的效果

1. **构图**：满 ADS 后眼睛靠近瞄具，镜窗足够大，清晰观察目标；镜框围住分划，枪体主要在下方。不能仍是远处的小镜框，也不能只把世界画面放大而枪镜大小不变。保留实体镜身，不以隐藏枪模加整屏黑圈作为成功交付。
2. **瞄准**：分划中心代表射击瞄准方向；稳定、无遮挡、无散布测试中，指向哪里就命中哪里。分划、镜窗光轴、世界目标投影必须统一。
3. **同一发一致**：伤害、命中特效、曳光依据同一发的最终权威结果。曳光从可见枪口自然发出，朝实际终点收敛，不允许平行偏移、不允许穿过已命中的近墙继续延伸。
4. **合理例外可解释**：保留既有后坐和散布；散布开启时弹着可偏离分划，但曳光必须跟随该发真实散布结果。枪口被掩体挡住时必须打掩体，不能为“准星必中”取消防穿墙。无敌、友军、已死对象可命中但不扣血，不应伪造伤害反馈。
5. **各模式一致**：离线、Host、Owner 客户端、DS 权威和观察者在相同规则下解释同一发射击；网络延迟允许预测暂态，但确认后不能持续显示错误落点、重复命中或重复扣血。

## 1. 证据链与问题等级

所有源码路径相对项目根，行号为本次基线，实施后可能变化。

### A1 / P1：光轴眼点对中没有实现眼距、轴向和构图校准（代码确证）

`Assets/_Project/Scripts/Presentation/Camera/FPWeaponMotion.cs:394–408`：瞄具分支读取 eyeWorld，转换到根/父坐标后只求 x/y 平移；z 在常规 LPFP 路径直接取 0，旋转保留 identity，然后提前 return。它并没有把完整眼点移动到相机，也没有依据光轴方向求解旋转。机瞄分支原本使用作者相机节点的深度补偿不会在此分支执行。

因此：光轴屏幕误差接近零，也不代表镜窗尺寸、眼距或轴向正确。该缺口能解释图一“镜框远且小”的现象，但截图具体用了哪个 prefab / 瞄具、运行时眼距多大仍需测量，不能声称已实机复现。

`Gameplay/Weapon/AttachmentCalibration.cs:39–44` 的光轴行只有 eyePointLocal，没有光轴方向、镜窗中心/边界、独立眼距/构图参数。

`Editor/OpticAimCalibrationWindow.cs:105–115` 的默认数据为按 tier 写死的眼点（红点 0.10/0.040、全息 0.12/0.045、低倍 0.14/0.050、高倍 0.16/0.055）；`Resources/AttachmentCalibration.asset:736–781` 当前 15 行正是此类默认值。9 月 17 日报告也明确写了“当前为 tier 缺省眼点，逐枪微调未完成”。

校准窗口 `:402–408` 只测眼点的屏幕中心误差；`Tests/EditMode/OpticAimCoverageTests.cs` 只锁定行存在与 eye.x > 0，均不能证明构图与弹着合格。

### A2 / P1：1x 分划和实体镜身不共享投影验证（实现确证；本图分划缺失原因待实机）

`Presentation/HUD/OpticAdsView.cs:105–108,181–194,345起`：1x 分划是拉伸至画布的 UI 中心图形，并非从真实镜窗光轴投影产生。`FPWeaponMotion` 则独立移动镜身。两者没有完整的镜窗投影/轴向误差约束。

满 ADS 冻结解后仍会应用视觉后坐（FPWeaponMotion :304–353）；需要验证镜窗运动时分划是否留在可视窗口内。截图一没有清晰可辨的分划，但仅凭截图不能断言是 bootstrap 失效、绑定错误、profile 缺失、遮挡还是截帧状态；实施阶段记录这些状态后定位。

### A3 / P1：伤害射线与曳光线平行而非汇聚（代码直接证明）

`Presentation/Weapon/WeaponView.cs:107–130`：

- start = 当前 FP muzzle.position。
- direction = shot.FiredDirection。
- length = Dot(shot.Result.Point - start, direction)，钳制到 4.25m。
- end = start + direction * length。
- LateUpdate 在约 45ms 存续期每帧把整条线重新放到当前动画枪口。

伤害候选线起点是 AimOrigin（WeaponController :108,400），并不是这个 FP muzzle；两起点有高度/侧向差。把方向复制过来只能得到平行线，不能保证经过实际命中点。点积只改变长度，不消除垂直方向偏差。枪口动画还会在开火后移动这条线。

`WeaponView.cs:218起` 将曳光放 FirstPersonView 层；正式玩家 prefab `Prefabs/Player/Player_Day2_Rebuilt.prefab:733,917` 世界相机 FOV=60、FP 相机 FOV=45（运行世界 ADS FOV另由 PlayerAimState 驱动）。**即使把 end 简单换成 Result.Point，同一世界坐标经两个不同投影也可能屏幕不重合。** 不能用单行改终点宣布完成。

附：代码注释写 overlay far clip=5m，但当前 prefab :916 是 10m；必须记录实际运行值，不能沿用注释做证据。

### A4 / P1：本地预测与服务器终点无闭环，散布也未见同步入口（代码确证）

`Gameplay/Weapon/WeaponController.cs:402–447`：仅 IsServerInitialized 走 ResolveHitscanTwoStage；离线/客户端预测走单段 ResolveHitscan。近墙下候选和最终结算天然可能不同。

`Gameplay/Network/NetworkCombatAuthority.cs:275–307`：ObserversShot 广播 origin/direction/hitPoint/hit，没有请求 id 与完整结果；OnRemoteShot 在当前项目 Scripts 内检索只发现定义和 Invoke，没有订阅者。Owner WeaponView 仍消费本地 OnShotFired，本地弹孔/曳光未根据服务器最终遮挡点校正。现有日志里的 shotRequestId 没有进入该表现确认消息。

`WeaponController.cs:161,353–356,421,492–505`：散布使用独立 System.Random；生产 Scripts 中只找到 SetRandomSeed 定义，没有调用。ApplyDeterministicRecoilSeed 是另一套后坐随机，不能据此推断散布已同步。两端各自采样不能保证同发同方向，且靠统一种子仍不能解决拒发/少发造成的流错位。

`NetworkCombatAuthority.cs:37–60` 请求只传 shotRequestId / estimatedServerTick；日志打印本地瞄准并不等于传输了该快照。服务器按其权威状态开火。快速转向时的输入 tick / 射击 tick 对齐属于待动态验证项，不能凭静态代码声称已发生偏差或直接信任客户端 ray。

### A5 / P2：逻辑枪口与可见枪口是两种坐标语义（确证）

`Gameplay/Combat/TwoStageHitResolver.cs:24–29,62–67`：逻辑枪口固定为玩家根 + 上 1.4m + 前 0.6m；不逐枪、不按 FP 动画确定。身体到逻辑枪口的防伸墙段也参与最终裁决。不能把 FP Muzzle 直接当服务器权威来源；但当前近墙/俯仰/不同枪长的视觉与遮挡一致性需明确检验，必要时用服务器可信武器配置改进逻辑枪口。

### A6 / P2：倍率镜还需验证镜内/镜外投影（静态风险，未认定本图根因）

`Presentation/Camera/PhysicalScopeView.cs:87–109,303–324,362–372`：倍率>1.01 的镜走独立 RT，scope 相机继承世界相机位姿；镜片/分划却在 FP 空间显示。FOV 根据世界距离下的镜片半视角计算，没有显式使用 FP 相机的实际投影倍率。世界/FP FOV 不同、光轴偏转时，不能直接宣称屏幕上的有效倍率恒等于配置倍率。

另：BuildScopeMask :327 起明确剔除 FirstPersonView，因此当前 FP 层曳光不会自然出现在 RT 内。必须决定镜内世界曳光和枪口近端特效的分工，避免倍率镜里没有弹道或双重弹道。RT 构建失败时现有 overlay 回退不应当作符合本次实体镜目标的成功结果。

## 2. 修复方案与顺序

### S0：先拿到最小真实样本

记录图一对应 weaponId / opticId / tier / magnification / calibration key、prefab、分支、Ads01、FPS、viewport、世界/FP/RT 相机位姿与投影矩阵、镜窗中心/边界、眼距。记录 HUD 实例绑定 Owner、profile 和 HandlingOpticId。

建立同一平面靶的 5m、25m、100m 样本，拍修复前画面。无此数据，不把截图归因到某一特定枪镜组合。历史报告可参考，禁止“目录行都存在所以校准已完成”。

### S1：先做一把正式 LPFP 枪 + 图一瞄具的完整 ADS 样板

扩展或明确光学姿态数据：真实镜窗中心、光轴朝向（或前后两点）、目标眼距、必要的逐枪构图覆盖。明确所有数据属于挂点坐标还是最终附件几何坐标，避免安装偏移、旋转和比例只应用给网格而光学数据没有跟随。

在现有 FPWeaponMotion 单一姿态写入链上求解完整 ADS 姿态。复用已有后坐隔离和稳定冻结策略，不能让每帧求解追逐后坐形成反馈抖动。支持同 opticId 校准更新失效和换枪/换装/复活重建。不能新增第二个独立枪根写入者来互相覆盖。

眼距与 FP 投影协同决定镜窗尺寸；世界 FOV / 倍率 / 输入灵敏度分别负责各自语义，不要为了大镜窗全局缩世界 FOV，也不要全局放大枪或缩手臂。检查 near clip、手臂穿镜、换弹、ADS 过渡。

校准 UI 同时展示眼点误差、轴向误差、镜窗占比、距眼、射击候选点投影。镜框和 UI 分划应由同一瞄准语义约束，明确处理后坐和过渡时分划可见区域，不能只画一个永远可见的中心红点掩盖对位错误。

### S2：统一每发射击事实与预测/确认

保持服务器伤害权威，保留相机候选→枪口验证→身体防伸墙。提炼同源几何查询，使本地预测与离线能采用同样的遮挡规则，同时严格分开预测和 ApplyDamage，保证伤害只结算一次。

建立可追踪的 shot id（关联 Owner/生命代际/武器与请求）和该发快照：开火 tick、射前瞄准、实际散布方向（霰弹逐 pellet）、逻辑枪口、候选点、最终点/法线/命中对象/遮挡裁决、accepted/rejected。网络具体结构由实施者适配，不能只新增无人消费的事件。

服务器确认必须真正被 Owner/观察者消费：预测视觉按同发去重/纠偏/撤销，拒发不得留下永久弹孔或命中标记。可选逐 shot 确定性散布降低预测差异，但必须处理请求拒绝和乱序，不能只设置一次随机种子。快速转向检验输入与开火 tick；若有偏差按项目权威输入链修正，禁止照单全收客户端落点。

### S3：修曳光投影与生命周期

优先用世界空间最终路径表现飞行段，FP 层保留枪口火光/短接合段；或采用等效、可验证的跨相机投影转换。必须让可见枪口起点、世界段和终点在最终合成画面中连续；近端与远端不能重复渲染，RT 内也要正确显示。

若保留 overlay 线段，先将真实终点通过世界相机投影得到屏幕位置，再在 FP 投影中求对应方向与合适深度，处理点在背后、超近命中、无命中远点、不同宽高比。不要把世界点直接塞入不同 FOV 的 overlay 相机。倍率镜要在 RT/镜片映射下单独验证，而非套普通 world→screen 公式。

每发轨迹固定于该发快照；短暂贴枪口的火光允许跟枪，已发出的飞行曳光不能继续被后坐拖着走。连发支持多发独立生命周期；霰弹不能拿主方向配另一个 pellet 的终点充当“全部一致”。保留合理限长/寿命，但短可见段应沿该发最终轨迹，不代表必须画一根完整百米长线。

### S4：推广、验证与报告

先让样板达到画面与弹着目标，再推广到所有正式可安装组合（从兼容目录枚举，不创建 LPW 实验任务）。覆盖红点、全息、中倍、高倍和内置狙击。实机权限不足时交付可编译代码与待验收清单，不伪造实机 PASS。
