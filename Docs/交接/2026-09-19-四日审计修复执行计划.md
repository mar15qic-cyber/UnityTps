## 2. B1：修复迁移发现与登录并发

### B1.1 迁移发现（F02）

目标文件：两条 `20260917*.cs` 迁移、`AppDbContextModelSnapshot.cs`（仅在核对后确有差异时）、后端迁移测试与交接说明。

1. 给手写迁移补齐对应 AppDbContext 的关联元数据，或用标准工具生成正确 partial。**保留既有迁移 ID**，避免已手工补历史的开发库二次加列。
2. 用 `GetMigrations()` 验证至少包含 `20260917103000_AddServerInstanceMapId` 和 `20260917112000_AddUserTokenVersion`；对模型快照与实体列类型做一致性检查。
3. 使用明确的独立 `_test` 数据库验证三种起点：空库；只到 AddProtocolIdColumns 的旧库；两列和历史已手工补齐的库。不得在个人开发库上通过 Drop/Recreate 掩盖问题。
4. 列已存在但历史缺失的异常库不应自动粗暴补历史：先验证列类型/默认值/约束，提供一次性修复步骤并留备份。
5. 更正“启动没有 Migrate”结论，说明 `Program.cs` 已调用 MigrateAsync，缺陷来自迁移发现。

验收：上述三种正常起点均成功；认证、地图租用、服务注册查询无缺列 500；迁移重复运行无新增 DDL。InMemory 全绿只能作为业务回归，不可替代该验收。

### B1.2 单活登录（F15）

目标文件：`AuthService.cs`、必要的用户并发配置与 `UserSessionSingleActiveTests.cs`。

选择一种关系库原子方案：事务锁定并更新版本，或原子增量后可靠取得本次版本并签发。异常重试必须重新读取状态，不能重用旧被跟踪实体。兼顾现有 `EnableRetryOnFailure` 执行策略，避免直接增加不兼容的事务。

验收：两个独立请求同步通过密码验证后并发登录，只允许最终提交版本对应 token 有效；先后登录旧 token 401；注册与未重登 token 的既有语义保持。记录最后有效的定义，不以两个响应到达浏览器的顺序替代数据库提交顺序。

## 3. B2：DS 生命周期、多实例与持久补偿

目标文件：`DedicatedServerBootstrap.cs`、`DedicatedServerOptions.cs`（如增加目录参数）、`MatchResultPendingStore.cs`、`Tools/Server/Start-LocalServer.ps1`、`Stop-LocalServer.ps1` 与对应测试。

### B2.1 初始化和补偿隔离（F09/F10）

1. store 构造函数只接受确定的目录/文件路径；不在 MonoBehaviour 字段初始化器读取 Unity API 或磁盘。
2. options 就绪后在主线程初始化，路径建议为 `<persistent>/server-results/<environment>/<instanceId>/`。实例 ID 必须经过路径校验且稳定，不使用每次随机 PID 作为唯一持久键。
3. 每个实例原子保存自己的队列，返回明确保存结果；磁盘满/权限错误时保留内存待重试并输出“未持久化”，不能打印“已落盘”。
4. 旧共享 `match-result-pending.json` 需要一次性迁移策略：备份、按已知来源归属或人工核对，避免五个实例分别重放同一旧文件。不要把状态冲突自动等同所有数据都已成功结算。
5. 测试通过依赖注入使用临时目录，停止时释放依赖；保留 GuardOnly/FullStartup 的原安全语义。

验收：9 项 DS 既有失败必须真正通过，不能新增 LogAssert 忽略来消除红字。至少两个独立实例并发积压、退出、重启后全部请求保留，后端恢复恰好一次结算；模拟保存失败可见且可恢复。

### B2.2 启动器收敛（F07/F08）

将脚本组织为“读取状态→生成操作计划→CheckOnly 返回→执行→验证→保存”六步。

- 所有实例（arena 与 map01..04）采用一致的 PID/路径/端口/启动时间/buildId 检查；健康实例复用，端口被外部进程占用明确报错。
- 后端失活而 DS 存活：先恢复控制面及正确 key，再验证 DS 注册/心跳；不能提前成功返回。
- 不删除仍运行实例的日志，不覆盖未接管的旧记录。新实例启动失败保持已有健康记录；只回滚本次确实启动的进程。
- CheckOnly 不允许创建进程、删运行日志或改进程状态文件。
- MAP_DS_READY 必须代表当前进程存活且端口/注册检查通过；未注册/已退出返回非零。

验收矩阵：冷启动；连续启动 3 次进程数量不变；只缺后端；只缺某地图；某地图端口被占；旧构建；错误 key；CheckOnly+AllMaps；停止后所有已托管进程退出。使用隔离端口/替身进程进行自动测试，正式运行栈验证由实施轮按授权执行。

## 4. B3：伤害、击杀和助攻同一事务（F01）

目标文件：`CombatResolver.cs`、`DamageableTarget.cs`、`NetworkCombatAuthority.cs`、`MatchLifecycle.cs`、`WeaponController.cs` 及真实事件顺序测试。

建议引入显式伤害上下文（射手、目标生命代际、请求/发次、伤害值），让“可结算校验→登记真实伤害来源→扣血→死亡计分→表现事件”顺序可检查。

必须处理：

1. 只有实际接受的伤害登记来源，友军、保护期、跨生命、死体、零伤害都不能覆盖上一有效伤害者。
2. 致死前登记，而非 OnShotFired 后补登记；死亡后不得重新把已消费目标放回注册表。
3. 霰弹逐目标累计伤害与助攻；一发命中多目标时分别归属，每个死亡只结算一次。
4. 重生清理上一生命归属；环境伤害保留现有 DeathOnly 口径；未认证假人零正式计分。

必备反例：满血一发致死；A 伤害+B 补刀；A 击伤后 B 向无敌目标射击；友军挡枪；上一生命死亡后的迟到事件；一发霰弹杀两人；TDM 最后一分只结束一次。测试必须调用真实伤害与死亡事件链，不能只测 `MatchKillAttributionPolicy.Evaluate` 的布尔组合。

## 5. B4：热更与地图入场完整闭环

目标文件：`HotUpdateManifest.cs`、`HotUpdateBootstrap.cs`、`HotSceneLoader.cs`、`Publish-HotUpdate.ps1`、`LobbyPresenter.cs`、等待房间页、安装器文件系统测试与 SOP。

### B4.1 安装事务（F03/F04/F05/F18）

推荐流程：

1. 入口先解析并验证已安装指针，明确 root 为已验证目录或 null。
2. 验证远端版本单段格式、最低客户端版本、路径规范、重复路径、hash 与 size 范围；所有规范化最终路径都必须落在指定根下。
3. 新建本次 staging 目录；未变化文件从有效旧包校验后复制/复用，缺失或 hash 不符则重下；变化文件下载校验后放入 staging。
4. 对目标 manifest 的**全部文件**复验，保证目录完整；相同 version 不同内容拒绝，不能覆盖当前使用包。
5. 原子发布完整目录，再以临时文件原子替换 installed.json；旧指针/旧包保留到新版本启动成功的明确边界。
6. 网络失败、空/坏 manifest、最低版本不符、断点失败的所有返回路径使用统一 fallback 逻辑，不仅更改 Result.Kind。
7. 仅版本号改变但内容相同：明确选择保留已装完整版本或物化新目录，禁止指向不存在的目录。

必备测试：v1→v2 仅修改 Lua 且地图不变；仅地图变化；同内容版本递增；删除本地单文件后再检查；冷启动断网；冷启动坏 manifest；下载中断；写指针前/中断模拟；同版本异内容；非法版本路径；一项校验失败时旧版本文件逐个 hash 不变。不得以只有纯决策单测代替安装器真实临时文件系统测试。

### B4.2 发布与回滚（F06）

发布脚本拒绝覆盖已存在版本的不同内容；自动版本生成需考虑已有 release，避免未部署时反复复用同号目录。推荐回滚为 `vN+1` 清单承载 `vN-1` 内容，继续满足客户端单调版本门。服务器也先完整放置版本目录，最后原子换 manifest。

验收：已安装坏版的客户端按回滚 SOP 重启，实际 Lua 页面与 bundle hash 恢复至目标内容，而非只显示服务器 manifest 已变化。

### B4.3 地图加载失败（F17）

`LoadArenaAsync` 返回结构化成功/失败结果，`EnterBattleAsync` 只在加载确实成功时结束等待循环。失败路径保留可重新取票的 Room 状态，或执行明确的失败退出事务；旧代际返回不得清理新会话。清理后 UI 可重试、可返回房间、不会无限“正在进入”。

必备测试：文件存在但不是有效 bundle；bundle 无目标场景；用户切页/离开时加载完成；超时；失败后第二次成功；票据被新 detail 替换；验证后端成员/租约最终状态与 UI 一致。

## 6. B5：战斗输入与预测的一致性专项

该批次涉及手感及可能的 wire 变化，实施前先在设计小节写清选定模型，再开始编码，避免同时保留两套“临时权威”。

### B5.1 半自动/自动开火（F19）

Owner 依据 FireMode 产生意图，服务端验证模式、发次与冷却；半自动一次 press 只结算一发，自动持续 held 按服务器节奏结算。请求去重与实际接受 shot 序列分开，不把每渲染帧拒绝请求当成弹药/后坐推进。明确 ServerRpc 需要携带的边沿/序号及重放策略。

### B5.2 后坐与瞄准（F13）

给出并实现如下不变量：同一个已接受 shotId 对应唯一 seed/shotIndex；两端从同一权威起点推进必要的瞄准状态；重放与正常路径使用同一 tick 步长；视觉相机反馈不能反向污染模拟 yaw/pitch。

可选方案需比较后择一：服务端确认发次并重放本地预测后坐，或显式传输并验证瞄准输入并将视觉后坐与命中方向拆分。不能只给随机数设一个常量，因为两端发次/被拒绝请求不同仍会分叉。明确 ADS、切枪、换弹和压枪消费时刻。

### B5.3 Owner 重生补弹（F12）

服务端重生形成可识别的新生命基线；Owner 应同时重置当前 Runtime、两槽缓存、必要的动作/后坐状态，然后恢复第一人称表现。允许 SyncVar/RPC 不同到达顺序，但每生命只初始化一次；持续战斗的普通回包不能反复补满或覆盖未确认发次。

反例：两槽均消耗弹药，当前槽空仓死亡；不切枪立即重生开火；切副槽再切回；重生通知重复/提前；服务器已补弹但客户端基线延迟。必须验证 HUD、本地弹药、服务端弹药、动作音效、真实伤害一致。

### B5.4 输入生命代际（F14）

MovementCommand/批次带已确认代际，服务器按本玩家生命/会话检验；新基线清队列并告知 Owner。把“旧批次在复活后到达”“新代际包先于确认”“丢失重生通知”列为明确状态迁移。epoch 不能只用于日志。

### B5.5 协议与验收

涉及 RPC 参数、同步字段或 DTO 形状时，从当前 `fps-net-v5` 统一递增到一个明确版本；同一批次完成序列化读写、认证兼容门、构建清单与 Client/DS 重建。无需 wire 变化的修复不要为了日志任意改协议。

验收：30/60/144 FPS 客户端、DS 固定 tick；0/50/150ms 延迟及少量丢包/乱序；连续射击与反向压枪；长帧追赶；菜单停留；重生。对账字段包括 conn/object、生命代际、input tick、shotId、accepted/rejected、seed/index、权威/预测 yaw/pitch、弹药。失败不靠扩大容差收口。

## 7. B6：几何标定与死亡复活表现（F11）
