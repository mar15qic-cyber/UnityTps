## 2. P0：进程存活但实例被旧房间状态卡成 Reserved

用户看到的“当前没有可用的对战服务器”不是人数下限。`RoomService.CreateAsync` 只会租用“心跳新鲜、状态为 Ready、容量足够”的实例；没有符合项便返回 `NO_SERVER_AVAILABLE`。

现场证据：

- `Builds/Server/UnityFpsDedicatedServer.exe` 正在运行，后端 `http://127.0.0.1:5080/health` 也正常；
- `Logs/Day3Smoke/server.log` 证明该实例曾 `DS_READY`、`REGISTERED state=Ready`，并成功承载多个客户端；
- 最后一名玩家离开后，后端释放房间和实例，但 DS 的 `ServerHeartbeatTracker` 没有收到/消费“remainingPlayers=0, instanceState=Ready”结果，本地仍持有旧 roomCode；
- 随后日志出现 `REGISTERED state=Ready` 后再次 `REGISTERED state=Reserved`，最终形成进程在线但不可租用的僵尸实例；
- 因此任何人数（包括一个人）创建房间都会失败。

必要修复：掉线上报端点成功响应必须返回 `roomCode / remainingPlayers / instanceState`；Unity 控制面客户端必须解析该响应。只有后端明确返回 `Ready` 且剩余人数为 0 时，tracker 才清除旧绑定并恢复 Ready。不得把普通 404/409 猜成 Ready。

## 3. 房间 UI 与玩法方向

当前实现不是漏画了一个页面，而是原基线采用“个人击杀竞赛（FFA）+ 创建/加入成功后直接进入 Arena”。用户现在明确要求 CF 式双队房间与选边，这会把玩法基线改为团队死亡竞赛，不能只加两个 UI 框：

- 建房后应进入 Room 页面而不是立刻加载 Arena；
- 一个玩家可以创建房间并停留等待其他玩家，建房本身不应要求比赛已经具备开局人数；
- 房间成员需要权威的队伍、准备状态、房主身份；
- 玩家可选边，服务器要限制人数差，不能只在客户端改显示；
- 开局、出生点、友伤、团队比分、终局和结算胜负都必须读取同一个权威 team 字段；
- 当前 FFA 单榜可以保留为另一模式，但 TDM 不能再用动态 playerId 奇偶分队。

为避免房间等待阶段占住稀缺 DS，推荐把“创建逻辑房间”和“租用 Dedicated Server”拆开：创建房间无需 Ready 实例；房主点击开始、且开局条件满足时才原子租用实例并给成员签发票据。若暂不做延迟租用，至少也要保证本地开发栈自动维持一个健康 Ready 实例，但这只是临时方案。

建议首版规则：8 人上限、4v4、友伤关闭、两队人数差不超过 1；单人允许建房和等待，但正式 TDM 至少两队各一人才允许开始。

## 5. 追加实机审计：退出后重进出现“影子玩家”、双相机与配装错位

视频证据：`C:/Users/陈琪/Videos/NVIDIA/Desktop/Desktop 2026.09.08 - 00.56.35.02.mp4`（88.37 秒，1920×1080/120fps）。录像中能持续看到近身重复人物/武器表现，移动时两者同步；用户同时确认画面枪模为初始 Glock17、HUD 与枪声为 FNSCAR，账号配装实际为 FNSCAR + P30。

### 5.1 结论与问题链路

这组现象不是单一相机参数错误，而是三个确定缺口叠加；当前仍不能进入最终联测：

1. **P0：在线 Arena 同时存在离线预置 Player 与 FishNet 生成 Player。** `Arena.unity` 内保留了一个 `Player_Day2_Rebuilt` 场景实例，根节点启用；同场景 `PlayerSpawner` 又把同一个 prefab 配为联网玩家生成物。场景实例额外挂了 `GameplayLoadoutBootstrap`，其 `Awake` 无条件执行 `NetworkObject.SetIsNetworked(false)`、强制根对象/Arsenal/WeaponController 启用，却从未在 `NetworkLaunchContext.HasPendingClientLaunch` 或 Dedicated Server 模式下关闭这名离线玩家。因此联网进入时，一名本地离线玩家和一名 Owner 网络玩家同时读取同一套 Input System：二者同步移动，形成“影子”；两套 `CameraPivot`、Camera/AudioListener、HUD/武器也会竞争，造成视角错误和混合表现。
2. **P0：网络生成 Player 没有收到服务器权威账号配装。** `GameplayLoadoutBootstrap` 只作为 `Arena.unity` 的 AddedComponent 挂在场景预置玩家上，不在 `Player_Day2_Rebuilt.prefab` 中。预置玩家被 `AccountSession.Loadout` 配成 FNSCAR + P30；网络生成玩家仍使用 prefab 序列化的 10 槽调试 Arsenal，首槽为 `Day2_ServicePistol`（画面所见初始 Glock17）。这会让“预置玩家的 FNSCAR HUD/声音”和“网络玩家的 Glock 枪模”同时出现，也解释了数字键/滚轮仍可切出账号未装备的武器。更严重的是，票据消费契约 `JoinTicketConsumeDto/TicketConsumeResult` 当前只返回身份，不返回配装；Dedicated Server 无法按账号权威初始化网络玩家，不能仅靠本地客户端修表现。
3. **P1：主动退出没有可靠清除房间成员资格。** `StartOnlineRoomAsync` 校验成功后没有调用 `session.ApplyRoom(connection.room)`，项目中 `ApplyRoom` 当前没有任何调用点。于是退出菜单的 `FireLeaveRoomApi` 在 `app.Session?.Room == null` 时直接返回；并且 UI 同帧调用 `ConfirmLeave()`，后者停连接并切 Lobby，leave 本来也是未等待的 fire-and-forget。这使原房间仍以 1/8 出现在列表。后端 `RoomService.TryJoinOnceAsync` 明确支持“alreadyMember 同房重进补发新票据”，并有 `RoomSameRoomRejoinTests` 固化该行为，所以点击自己的残留房间能够再次进入是现有重连设计的直接结果，不是房间凭空复制。
4. **P1（防御缺口）：DS 认证表按 ClientId 去重，但没有按 UserId 保证单活。** 若同账号确实从另一连接重入，`JoinTicketAuthenticator` 会把两个 ClientId 都加入 `AcceptedUsers`。即使本次录像的第二个人形主要由“预置 + 网络生成”造成，这个缺口未来仍会制造同账号双化身、结算身份冲突与旧连接断开误清成员，需要在本轮一并补上明确的“新连接接管旧连接”或“拒绝新连接”策略；推荐新连接接管，且掉线清理继续使用 sessionId/代际保护，不能让旧连接的迟到 disconnect 删除新会话。

### 5.2 修复后的硬验收条件

- 在线客户端和 Dedicated Server 加载 Arena 时，场景预置离线 Player 必须在任何输入、相机、音频和武器 `Start/Update` 发生前被禁用；离线模式仍保留该 Player，行为不回归。
- 每个客户端进程恰有一个启用的本地 `InputReader`、一个主 Camera、一个 AudioListener、一个 Owner HUD；每个已认证 UserId 在 DS 上恰有一个活动玩家对象。
- 账号 1234 的网络玩家在服务器、Owner HUD、第一人称枪模、第三人称枪模、枪声与伤害定义六处均为 FNSCAR；副武器为 P30；只能在这两个合法槽位间切换。
- 主动退出必须等待“后端 leave 成功或有界超时”后再回 Lobby，并在本地 finally 清理 Room/NetworkLaunchContext；随后房间列表不再出现该用户已退出的单人房，实例可恢复 Ready。
- 保留真正掉线后的同房重连能力，但不得同时保留同 UserId 两条活动连接/两个玩家对象。
