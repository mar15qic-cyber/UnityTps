## 2. 两个玩家互相看不到：确定的 Owner/Remote 渲染层缺陷

证据链：

1. `Assets/_Project/Prefabs/Player/Player_Day2_Rebuilt.prefab:1131` 附近的 TP_Model，以及大量子节点都被覆盖为 layer 8。
2. `ProjectSettings/TagManager.asset` 中 layer 8 为 `LocalPlayerBody`，layer 9 为 `FirstPersonView`。
3. 同 prefab 主相机 `m_CullingMask`（约 737–739 行）为 `4294966527`，恰好排除 layer 8 和 layer 9。
4. `PlayerNetworkAdapter.OnStartClient`（约 166–206 行）对远端仅关闭本地相机/输入并绑定动画，没有把远端 TP_Model 改到可见层。约 198 行注释反而误以为 layer 8 对别人可见。
5. TP 武器的 `TPWeaponMeshSwapper` 从身体继承层；实体镜还主动排除 LocalPlayerBody。因此同样可能看不到远端武器/镜中敌人。

**相机的层过滤是本进程全局按 layer 位判断，不知道哪个对象是“自己”。** 所有玩家都用同一个 LocalPlayerBody 层，主相机会把自己的和远端的身体一起剔除。录像中 Scene 有人、Game 看不到，与此链路一致。

修复目标：按实例 Owner/Remote 区分视觉层；本地自己的第三人称身体仍对第一人称相机隐藏，远端身体/TP 武器/附件对主相机与倍镜可见。不能仅把主相机 layer 8 全打开，否则又会看到自己的身体挡镜。不要递归改视觉层时误改伤害 hitbox、移动碰撞体或服务器命中掩码。对象池复用/Owner 变化时也要恢复正确层。

## 3. 碰撞晃动：确定存在冲突机制，实际占比需修后实机确认

已确认代码事实：

- 玩家根 CharacterController 在 Default 层；`EnsureBodyHitbox` 又在 TP_Model 下创建默认非 trigger 的 CapsuleCollider，并将它置为玩家根层（`PlayerNetworkAdapter.cs:143–160`）。这是可阻挡移动的实体碰撞体，不是仅用于射线命中的分离查询层。
- `ProjectSettings/DynamicsManager.asset:20` 的碰撞矩阵全开；在所查移动/网络代码中没有玩家移动体与伤害体之间的过滤。
- `Locomotor.SetSimulationMode` 只是改枚举，RemoteProxy 跳过 Simulate，但 CharacterController 没有因此变成非阻挡代理。
- 客户端本地预测会撞到插值后的远端碰撞体，服务器则按自己的当前玩家位置逐玩家 tick 模拟，二者并非相同的碰撞场景。
- 平滑纠正路径在 Simulate/记录预测后直接 `transform.position += step`（PlayerNetworkAdapter 约 399–410 行），与 CharacterController.Move 的碰撞处理不在同一入口。

合理因果链：双方贴近 → 客户端碰撞位置与服务器权威位置不同，并受到额外 BodyHitbox 阻挡 → 权威纠正把根拉回 → 下一次 Move 再推出 → 可见抖动；直接改物理根的平滑校正可能放大该问题。**这不是已实测证明的唯一原因**，旧 DS/新客户端也是干扰变量。

修复目标：分离移动阻挡与射击判定，明确玩家间阻挡策略；客户端远端代理不能作为与服务器状态不一致的额外刚性碰撞源。保留墙/地面碰撞和有效受击检测，不能全关 Collider 或全局忽略 Default 层。若使用 trigger hitbox，必须同步核对 CombatResolver 的 QueryTriggerInteraction；如果改变玩家之间是否能穿过，须明确报告玩法变化，不能暗改。校正优先让模拟根与视觉平滑职责分开，或至少通过一致的移动/快照入口更新，避免继续直接来回推拉物理根。不要靠增大 SNAP 阈值、减少上报频率掩盖错误。

## 4. 等待房间全体消息对方收不到：确定的 JSON null 契约错误

直接代码链：

- 后端 `Features/Contracts.cs:140` 定义 `ChatMessageDto.SenderUserId` 为 `long?`。
- `RoomChatService.SendSystem` 写系统消息时传 null；入房/开局等都正常产生系统消息。
- 客户端 `AccountContracts.cs:65–72` 却定义 `public long senderUserId`；注释称“JsonUtility 归 0/null”，已与实际解析器不符。
- `ApiClient.cs:181` 实际使用 `JsonConvert.DeserializeObject<T>`。默认 Newtonsoft 无法把 JSON null 转为不可空 Int64；一条系统消息即可导致整批 ChatFeed 解析失败，被转换成 InvalidJson。
- `ChatController.FetchHttpAsync` 对失败直接静默 return，游标不推进，下一轮还取同一批。
- 发消息的 POST 响应是一条普通用户消息，senderUserId 非 null；SendHttpAsync 将其直接 PushIfNew。因此发送者能看到自己的回显，其他客户端却被批量拉取中的系统消息卡住。

应修复 nullable 契约和展示层转换（系统消息无用户身份是正常语义），不要伪造真实账号 ID，不要通过删掉系统消息规避。增加有界/节流的拉取失败诊断：房间、HTTP 状态/错误码、cursor，禁止记录 token。后端重启导致 cursor 越界也不能永远静默失败；恢复必须保持房间身份隔离。等待房间 HTTP 拉取不应被残留的战斗菜单状态无限阻止。

这是静态契约审计结论，本轮未运行 JSON 探针或聊天测试；当前编辑器日志读取被拒绝，因此没有声称抓到了用户这次请求的客户端 InvalidJson 日志。
