## 结论与证据范围

**存在应在朋友外网体验测试前处理的问题。** 本轮确认 5 项 P1、3 项 P2。这里 P1 表示会影响预期正常网络下的核心对战正确性，或构成服务器权威绕过；P2 表示特定生命周期/异常输入下的缺陷。未发现足够证据可定为 P0 的问题，也不代表整个公网部署已经过安全审计。

现有回溯有实质防护：有限历史、严格时间窗、同生命代际插值、缺历史目标临时禁用、两遍保存/回写、同步查询后 finally 恢复。不能据此认为端到端时间语义、武器事件重放与弱网恢复已经正确。

验证分三层：

1. **实际源代码逻辑复现**：独立 .NET 9 夹具直接链接当前 `MovementPredictionCore.cs`、`MovementSimulationTypes.cs`、`ObserverTimeline.cs`、`WeaponRuntime.cs`，验证队列、时间政策、缓冲及冷却。全部复现断言通过，结果在 `results.txt`。通过表示成功复现缺陷，并非产品测试通过。
2. **静态调用链确认**：核对 Adapter、CombatAuthority、Locomotor、WeaponController、RecoilState 的接线与重生路径。涉及 Unity 物理、真实 RPC 到达次序的结果仍需集成验证。
3. **明确未执行**：Unity 编译、现有 EditMode 测试重跑、真实 UDP 弱网、跨机器/公网实测。夹具的 Unity 数学占位类型不模拟物理或 FishNet；不能冒充这些验证。

## P1-01：200ms 补偿政策与“正常 B：150ms RTT”目标冲突

定位：`ObserverTimeline.cs:22,48–54,130–138`；`NetworkCombatAuthority.cs:68–72,133–148`；`Docs/29-公网邀请测试部署与验收.md` §5。

30Hz 稳态时 `_interval=1/30`，显示延迟为 `2.1/30=70ms`。显示时钟从收到的服务器 tick 起算，不补偿下行传输时间；射击携带该显示时间，再经过上行与服务器调度。因此请求处理时的历史年龄约为：

`下行延迟 + 显示缓冲 + 上行延迟 + 额外排队 ≈ RTT + 70ms + 排队`

`ShotTimingPolicy` 对历史年龄超过 200ms 的请求直接返回 InvalidTime，`ProcessTimedShots` 随即拒射；不是仅取消补偿后仍正常开火。输入等待期间还会用更晚的服务器 tick 再次判断时间窗。

源代码政策复现：80ms RTT → 150ms 历史年龄，接受；150ms RTT → 220ms，拒绝；250ms RTT → 320ms，拒绝。真实服务器 tick 离散化与帧相位会改变边界发次比例，但不改变预算冲突。前一份公网报告已承认这一风险；本次将它量化为与正常 B 验收目标的直接冲突。

影响：正常玩家本地枪声/后坐/耗弹已经发生，服务器大量拒绝伤害并回送弹药；体感为射击无效及弹药回补。

建议：先确定支持的 RTT 与显示缓冲预算，明确“能否开火”和“最多补偿多旧目标”的产品政策，再同步调整准入、历史与测试目标。不要只扩大历史保留余量，也不要无限增大补偿窗口。必须统计每发真实 history age、等待时间和拒绝原因。

## P1-02：单个远端姿态断流后，射击时间不再对应实际显示的位置

定位：`ObserverTimeline.cs:76–89`；`PlayerNetworkAdapter.cs:1104,1797–1801,1822–1832`；`NetworkCombatAuthority.cs:68–72`。

远端姿态 RPC 使用 Unreliable，Owner ACK 使用默认可靠通道。公共时钟还可由其他玩家继续推进。某一目标丢包时，其 `TimestampedPoseBuffer.Evaluate` 会钳制到最后可用姿态，并正确设置 `ActualTick` 和 `Starved`；但调用方没有消费这两个字段。射击始终上报公共 `PresentedTick`。

可复现例：目标最新样本 tick=100，Owner/其他玩家已推动公共时钟到 101.90。画面显示的是 tick=100 的目标，射击却请求服务器回溯到 101.90。再持续丢几帧，差值继续增大。目标横移时就会出现瞄准模型未命中，或射向模型外却在服务器命中。

这不是笼统的“网络延迟”：设计承诺的“实际显示时间”没有与每个目标真正使用的样本时间对齐。多个目标还可能同时停在不同 tick，一个公共时间本身无法表达这些分歧。

建议：明确统一渲染时间线的缺样本政策，或设计服务器可验证的逐目标时间语义；记录目标 ActualTick/Starved 与本发 DisplayTick 的差值。不能直接信任客户端任意指定某目标的历史位置，也不能只把公共时钟换成任意一个目标的 tick。

## P1-03：射击按到达时的冷却结算，正常抖动会吞掉合法发次

定位：`NetworkCombatAuthority.cs:124–148,180–185`；`WeaponController.cs:227–233,480–489`；`WeaponRuntime.cs:32–44`。

客户端每个本地成功 shot 发一条可靠请求，但服务器 `ProcessTimedShots` 在同一次回调中循环处理整个到达队列。第一发开启冷却后，第二发因 `CanAttemptFire=false` 直接被 NotReady 拒绝。冷却仅在 `WeaponController.Update → Runtime.Tick(Time.deltaTime)` 推进，循环没有按射击历史间隔推进武器状态。

600 RPM 的两发本地相隔 100ms；只要第一发因抖动/可靠重传晚到，两发可能在同一个服务器 tick 被处理。即使两发均在补偿窗口内、输入与生命代际合法，仍只能接受第一发。并不需要 200ms 以上的长断网。

实际 WeaponRuntime 复现确认“第一发消耗并设 100ms 冷却，未推进 Runtime.Tick 的第二发被拒绝”；同回调处理路径由静态代码确认。现有弹药确认会纠正数量，但不能补回被丢弃的合法伤害。

建议：使用受服务器约束的射击模拟时间验证发射间隔，并覆盖武器切换、装填、死亡和队列上限。不能为了保留发次简单取消冷却，也不宜让松开扳机后的过期队列无限排队补射。

## P1-04：硬校正重放只包含移动，没有重建影响移动的射击后坐状态

定位：`PlayerNetworkAdapter.cs:1267–1304`；`Locomotor.cs:138–143,269–272`；`WeaponController.cs:231–232,554–559`；`WeaponRecoilState.cs:60–87,97–120,122–135`。

硬重基先把共享的后坐债务恢复到 ACK 快照，再仅逐条调用 `Locomotor.Simulate`。但后坐债务既被移动 yaw 输入消费，也会由 `WeaponRecoilState.OnShot` 增加、由武器 Update 的恢复逻辑改变；这些 ACK 之后的事件没有进入 MovementCommand 或重放日志。

确定性的反例：ACK 时 yaw 债务=0；随后本地射击产生 +2° 债务，再提交 -1° 压枪输入。原预测将 -1° 用于消费债务，身体不转；硬校正恢复到债务=0 后重放同一移动命令，因为没有重放中间那次射击，身体实际转 -1°。位置快照再完整，也无法恢复这一缺失的因果链。Pitch 债务共用同一对象，而当前移动重放也没有按原顺序重放 pitch 消费。

影响：持续开火/压枪与硬校正重叠时，重放不能保证朝向与后坐收敛，可能再次触发 yaw 分叉或改变视角/弹道关系。机制由代码可确认；本轮没有宣称已在实机复现校正风暴。现有 `PredictedReplayConvergenceTests` 的测试对象只有 Locomotor/CC，没有挂武器并交错 shot，因此不能覆盖此问题。

建议：把影响移动积分的后坐状态及 shot/恢复/输入消费纳入同一确定性时间线，或彻底解耦移动与表现后坐。重放中必须抑制真实伤害、耗弹、音效等副作用；不能直接重复调用完整 TryFire 作为修复。

## P1-05：移动准入没有服务器时间预算，可持续实现三倍模拟速度

定位：`MovementPredictionCore.cs:24,415–448,457–470`；`PlayerNetworkAdapter.cs:991–1024,1045–1087`。

未来输入窗口相对于 `LastProcessedTick` 检查，而该 tick 完全由客户端提交。服务器每 tick 最多消费 3 个命令；没有“累计已模拟时长不得超过本连接经过的服务器时长加有限追赶余额”的限制。

实际 ServerInputQueue 复现：连续 300 个服务器 tick，每 tick 提交 3 个递增输入，全部通过；10 秒墙钟时间消费 900 个固定 1/30 秒模拟步，即推进 30 秒移动，DroppedFuture=0。生命代际和 RequireOwnership 都不会阻止玩家针对自己的对象这样提交。

这是权威准入漏洞，不是指正常朋友客户端会自然三倍加速。把 catch-up 上限设为 3 只能限制瞬时工作量，不能限制客户端长期模拟速率。

建议：加以服务器时钟为依据的累计模拟预算，允许有界积压追赶，限制长期速率；区分瞬时合法 catch-up 与持续超速，加入服务端统计及拒绝政策。简单改回每 tick 只处理 1 条会重新制造合法积压无法恢复的问题。

## P2-06：移动 RPC 没有非有限值及批长度校验

定位：`PlayerNetworkAdapter.cs:1052–1087`；`MovementPredictionCore.cs:415–448`；`Locomotor.cs:134–143`。

EnqueueServerInputBatch 只判断 null、冻结和生命代际，随后遍历整个数组；客户端的“最多 12 条”不是服务端的载荷约束。队列入队不验证 Move/YawDelta/PitchDelta 的有限性。

实际源代码复现可将 Move.x=NaN、YawDelta=NaN、PitchDelta=Infinity 的合法 tick 命令入队并取出。Locomotor 随后直接将 yaw 用于 transform.Rotate。ClampMagnitude 无法作为 NaN 防护，构造器约束也不能替代对反序列化字段的校验。

可能造成玩家状态污染/Unity 报错及额外处理负担；本轮未证明可使整个 DS 崩溃。建议在服务器入口先整体验证批长、有限性、合法数值范围，再入队；必要时把长度防护前移到传输/反序列化限制。

## P2-07：首次 ACK=0 硬重基回拨 tick，却保留了同号旧输入

定位：`PlayerNetworkAdapter.cs:769–783,1177–1183,1291–1327`；`MovementPredictionCore.cs:TryStore`。

首次服务器快照尚未消费输入（ACK=0）时，客户端可能已经预测并缓存了若干命令。HardSnapTo 的 ACK=0 分支把 `_localTick` 设为 0，却不清理 `_buffer`；下一步重新生成 tick=1。TryStore 因同号旧命令存在返回 false，但 RunOwnerPrediction 忽略返回值，仍模拟新命令并覆盖其预测快照。

于是出现“上传的是旧输入，配对预测快照来自新输入”。夹具中旧 tick=1 为 +10°，重基后新 tick=1 为 -10°：新命令存储失败，缓冲中仍是 +10°。入场延迟、初次连接时移动转头更容易触发。

建议：初始重基的输入编号、历史、已在途命令需要统一处理；禁止同一会话/代际内用同号表示两个不同输入。仅本地清空后复用编号还不充分，因为旧输入可能已在可靠队列中。补真实初次握手时的预测先行用例。

## P2-08：重生失效函数只清旧视觉缓冲，新时间戳缓冲会继续显示旧生命

定位：`PlayerNetworkAdapter.cs:1797–1801,1816–1832,1898–1902,1921–1924`；`NetworkCombatAuthority.cs:576–582,1334–1336`。

实际纯客户端使用 `_timestampedPoses`。重生回调及死亡表现复位调用 InvalidateRemoteVisualSmoothing，但它只重置 `_remoteVisualBuffer` 与 `_remoteVisualValid`；新路径既不检查 `_remoteVisualValid`，也没有在此清空时间戳缓冲。

可靠重生通知/dead=false 先到、新生命的 Unreliable 姿态延迟或丢失时，下一帧新路径仍会从旧生命缓冲取样，把复活模型写回旧位置。直到收到新生命 pose，Push 才按 LifeEpoch 清旧数据。已有测试仅验证“新生命 pose 已 Push 后不跨代际插值”，没有覆盖新 pose 尚未收到的窗口。

建议：把可靠的生命代际基线接入新缓冲，在收到匹配新生命的姿态前明确隐藏/保持可信出生位姿；拒绝随后迟到的旧代际样本。验证两种通道的到达先后和新生命连续丢包。

## 其他已核查边界与待验风险

- 输入上传及 Owner 权威快照是可靠 RPC：当前 FishNet `RpcProcessor.cs:470–483` 默认 Reliable。不能把这里的输入丢包描述成会直接永久丢失 RPC；需关注可靠重传队头阻塞与恢复后的集中到达。
- 最旧 12 条的应用层重发形成有限在途窗口。独立、无丢包有序链路调度模型在 RTT 533/667ms 下出现历史淘汰和百余 tick 领先，400ms 的该相位模型未淘汰。模型没有运行 Adapter 的硬重基与物理，因此仅作为压力用例依据，**不据此断言真实客户端永久卡死或给出精确 RTT 临界值**。
- 近距离玩家碰撞的 Owner 重放使用本机当前远端碰撞代理，未回滚所有碰撞对象的历史；NT 插值压到 1 仍无法消除传输延迟。真实外网下贴身交错/推挤仍可能反复硬校正。本轮没有足够物理证据将其新增定为确定缺陷。
- 回溯恢复已有两遍保存与 finally，生命代际保护也存在；本轮未发现应把它们整体推倒重写的依据。依旧需要真实 collider 移动、异常抛出、击杀/重生并发时序测试。

## 进入朋友测试前的最小修复与验收顺序

1. 先处理 P1-01/02/03 的时间契约：网络预算、实际显示姿态与发次间隔。否则朋友反馈的“打不中”会混合三种不同原因。
2. 同时收口 P1-04/05 的重放完整性与服务器时间预算；补 P2-06/07/08 的入口和生命周期边界。
3. 用修复后的本机真实 UDP 弱网跑以下场景，再放给朋友做外网体验验收。朋友可以参与诊断型测试，但当前版本不宜被视为已具备体验验收基线。

| 场景 | 核验点 |
|---|---|
| RTT 80/150ms，±10/20ms 抖动，1% 丢包 | 合法射击拒绝比例、真实历史年龄；150ms 档不能整段无伤害 |
| 仅阻断某目标姿态 100–250ms，Owner ACK 保持 | 显示 ActualTick 与用于回溯的时间一致或明确受控降级；不能静默混用 |
| 600 RPM 两发，第一发延迟使两发集中到达，仍在合法时间窗 | 以合法发射间隔结算；不能因同一处理帧丢掉第二发，也不能加速射击 |
| 移动、持续开火、反向压枪，同时注入需硬校正的位置误差 | 重放后 yaw/后坐/位置收敛，不重放伤害与表现副作用 |
| 持续提交 90Hz 输入给 30Hz 服务器；另做一次合法积压追赶 | 前者不能三倍速度，后者能有界恢复 |
| 初始 ACK=0 前已预测 1–10 tick | 预测、缓存、上传同号命令内容一致；不能编号重用污染 |
| 重生通知先到，新生命 pose 丢 3–8 帧 | 不能把新生命模型重新显示到死亡位置 |
| RTT 250/500ms，断流 0.5/2/5 秒再恢复 | 队列有界，恢复后按 Docs/29 在 5 秒内继续推进或明确退出；单独统计 HistoryMissing/REPLAY_GAP |

本轮结论是“已找到需要修的边界”，不是“公网测试已通过”。产品代码保持原状，修复尚未实施。
