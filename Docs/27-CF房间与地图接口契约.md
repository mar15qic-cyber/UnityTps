## 1. 冻结标识符与词汇

| 标识符 | 类型与取值 | 语义与规则 |
|---|---|---|
| `roomCode` | 6 位大写字母数字（现有生成器不变） | 房间对外标识 |
| `roomVersion` | long，房间内单调递增，初始 1 | 房间可变状态版本。递增时机：设置变更、状态迁移（Waiting/Starting/InMatch/Returning）。成员 ready/选边不递增。客户端用它判断"快照已过期需重拉详情" |
| `matchId` | GUID（`N` 格式字符串），每次成功 start 生成 | 一场比赛的全局唯一身份；票据消费复核、终局上报、结算幂等、返房 ack 都携带它 |
| `matchGeneration` | int，房间内单调递增，初始 0；每次成功 start +1 | 房间内第几局。旧局回调/迟到消息按 `(roomCode, matchId, matchGeneration)` 丢弃 |
| `ConnectionGeneration` | long，客户端 AccountSession 本地计数 | 客户端"已建立的战斗连接"代际。**仅在新战斗连接启动时（start ack 的 connection 或 InMatch 补人/重连的 connection 写入 launch context 时）递增**；详情轮询/快照刷新不递增；退房 ClearRoom 不递增（现状语义保持） |
| `TeamId` | `"None"` \| `"Red"` \| `"Blue"` | TDM 队伍。KillRace 全员 `None`。DTO/DB 均为字符串 |
| `mode` | `"TDM"` \| `"KillRace"` | KillRace = 现有 FFA 击杀竞赛规则（回归路径，全员无队伍）；TDM = 新增团队死斗 |
| `mapId` | `"arena"`（首版唯一） | 地图目录稳定 ID，协议与 UI 禁止硬编码场景路径 |
| 房间状态 | `"Waiting"` \| `"Starting"` \| `"InMatch"` \| `"Returning"` \| `"Closed"` | 见 §3。旧值 `WaitingForPlayers`/`WaitingForServer` 迁移映射为 `Waiting`（§9） |

容量白名单：`maxPlayers ∈ {2,4,8,12,16}`；TDM 每队上限 = `maxPlayers / 2`。KillRace 名单上限 = `maxPlayers`。
规则白名单：TDM `killTarget ∈ {50,100,150}`（默认 100）、`timeLimitMinutes ∈ {5,10,15}`（默认 10）；KillRace `killTarget ∈ {10,20,30}`（默认 20）、`timeLimitMinutes ∈ {5,10}`（默认 10）。

## 2. 房间规则（沿 Docs/26 §2.1 冻结，接口化表述）

- 创建/加入仅进 Waiting；租用 DS 从 create/join 中移除，成为 start 的步骤（旧"创建即连 DS"迁移入口）。
- 准备：`isReady` 按成员存储。换队/设置变更/返房清空本人或全员准备。房主点击开始视为本人已准备（服务端在 start 时置 leader ready=true 再校验）。
- 开局条件（TDM）：双方每队至少 1 名成员；非房主全部 `isReady=true`；名单 ≤ 容量。KillRace：至少 2 人、非房主全部已准备。
- 设置变更仅 leader；白名单校验失败逐字段报错；成功后 `roomVersion+1`、全员 `isReady=false`。
- leader 离开：沿用现有确定性移交（`JoinedAtUtc` 最早 → `UserId` 最小），比赛不因此终止。leader 是管理身份，不是网络主机；网络主机永远是租用的 ServerInstance。
- 局中（InMatch）补人：非成员可 join，指定或自动分配未满队；Starting/Returning 拒绝新成员；InMatch 成员重进 = 重连补发票据。局中禁止换队。
- 心跳：成员在 Waiting/Starting/InMatch/Returning 期间以 `POST /api/rooms/heartbeat` 保活（间隔 15s）；服务端懒清理移除 `LastSeenUtc` 超过 60s 的成员（含触发 leader 移交；全部过期 → 房间删除）。

## 3. 生命周期状态机

```
Waiting --start(leader)--> Starting --roster已连/DS心跳InMatch--> InMatch
   ^                          |                                       |
   |                          |90s 超时                                |终局(§7)
   |                          v                                       v
   +------------------- Waiting <----45s 或全员 ack---- Returning
   最后一名成员离开(任意状态, 服务器掉线上报路径) → Closed（删房+释放实例）
```

- **Waiting**：不连接 DS、不存在票据。成员可 join/team/ready/settings/heartbeat/chat(HTTP)。join/team/ready 在本状态全量可用。
- **Starting**：start 成功后的冻结窗口（90 秒）。名单、队伍、地图、规则、`matchId` 快照锁定（`RoomMatchRoster` 行）。新 join 拒绝（`ROOM_STARTING`）；roster 成员 join/重进补发新票据（重连）。start 时无可用 DS → 409 `NO_SERVER_AVAILABLE`，**保持 Waiting 且保留全部准备**（允许重试）。90s 超时（懒判定）→ 回 Waiting、释放实例、清全员准备、`roomVersion+1`、系统消息 `START_TIMEOUT`。该 90s 必须大于 DS 侧 60s 加载门。
- **InMatch**：DS 权威。后端仅维护成员/心跳/补人 join 与聊天。DS 心跳 Reserved→InMatch 迁移房间状态（现有机制复用）。补人 join 成功 → 返回 `connection`（新票据），DS 负责队伍容量核验（Pending 连接计入名额）。
- **Returning**：终局已登记（TDM：DS 上报结果；KillRace：任一 roster 成员 return ack）。新 join 拒绝；roster 成员可重连取票（容忍迟到掉线者拉取结果页）。释放 DS（实例→Ready，`roomVersion+1`）。转 Waiting 条件（懒判定，入口：detail/heartbeat/list/return）：全员 ack 或终局登记后 45s；转出时清全员 `isReady`、`CurrentMatchId` 归档为 `LastMatchId`、`roomVersion+1`。
- **Closed**：仅"最后一名成员离开（服务器掉线上报路径 `allowReleaseDuringMatch`）"触发现有删除语义。玩家主动 leave 在 InMatch 的保留语义不变。

旧局隔离：所有成员变更、终局、结算、返房操作携带 `matchId`；与 `CurrentMatchId` 不符的请求返回 409 `ROOM_STATE_CONFLICT`，零副作用。旧局迟到断线上报按现有 `ReportPlayerDisconnectAsync` 的会话竞态保护拒绝。

## 4. 地图目录

首版仅一条（服务端常量白名单，客户端镜像只读目录；后续新地图只加目录项，不加房间逻辑）：

```json
{ "mapId": "arena", "displayName": "Arena", "sceneName": "Arena", "modes": ["TDM","KillRace"], "maxCapacity": 16, "spawnGroups": ["Red","Blue","FFA"] }
```

- start 时校验 `mapId ∈ 目录` 且 `mode ∈ 该地图 modes`；违规 422 `MAP_NOT_ALLOWED`/`MODE_INVALID`。
- `GET /api/maps`（无鉴权要求，跟随玩家 JWT 亦可）→ `MapCatalogDto[]`，供客户端 UI 渲染与白名单提示。

## 5. 玩家房间接口（JWT 鉴权，路由 `api/rooms`）

通用约定：错误体沿用现有 `ApiException` → `{errorCode, message}`；本文新增错误码见 §10。幂等语义逐接口标注。所有写接口在 Serializable 事务 + 执行策略重试框架内实现（沿用 RoomService 现有模式）。

### 5.1 `POST /api/rooms`（创建）
- 请求 `CreateRoomRequest`（扩展）：`{ maxPlayers=16, mode="TDM", mapId="arena", killTarget=100, timeLimitMinutes=10 }`（全部可选，逐字段白名单校验）。
- 响应 201 `RoomSnapshotDto`。**不再租实例、不再返回票据**。一人一房清理沿用（先按 leave 语义退出旧房）。
- 语义变化：响应从 `RoomConnectionDto` 改为 `RoomSnapshotDto`（§5.4）。旧客户端兼容不做（客户端随本契约同步发版）。

### 5.2 `POST /api/rooms/{code}/join`
- 请求体可选：`{ "teamId": "Red" }`（仅 InMatch 补人时指定队伍；缺省自动分配未满队，KillRace 忽略）。
- 状态分支：
  - Waiting：容量内加入 → 200 `RoomSnapshotDto`（无 connection）。房满 409 `ROOM_FULL`。
  - Starting：新成员 409 `ROOM_STARTING`；已是 roster 成员 → 补发新票据，200 `RoomSnapshotDto` + `connection`（重连）。
  - InMatch：新成员 = 补人（队满 409 `TEAM_FULL`）；roster 成员 = 重连票据。均返回 `RoomSnapshotDto` + `connection{serverAddress, serverPort, joinTicket, ticketExpiresAtUtc, matchId, matchGeneration}`。
  - Returning：新成员 409 `ROOM_STATE_CONFLICT`；roster 成员补发票据（拉结果页用）。
  - Closed/不存在：404 `ROOM_NOT_FOUND` / 409 `ROOM_CLOSED`。
- 已是成员且无需新票据（Waiting 重复点击）：幂等 200 快照，不触发一人一房清理（沿用现有保护）。

### 5.3 `GET /api/rooms`（列表）与 `GET /api/rooms/{code}`（详情）
- 列表：现有 `GameRoomDto` 扩展只读字段 `{status, mode, mapId, killTarget, timeLimitMinutes, roomVersion}`；懒清理职责扩展（§9）。
- 详情：`RoomSnapshotDto` = `{ room: GameRoomDto(扩展后), members: RoomMemberDto[], you: {userId, teamId, isReady}, connection?: ConnectionInfoDto }`。
  - `RoomMemberDto = { userId, username, teamId, isReady, isLeader, joinedAtUtc }`，按 teamId 再按 joinedAtUtc 排序。
  - `connection` 仅在请求方为成员且房间处于 **Starting/InMatch** 时出现（每次 GET 重取票，天然支持刷新页面后重连；v1.1 撤销限频：Starting 的取票是连接承载路径，Returning 已无需 DS 连接故不下发）。
- 轮询节奏（客户端契约）：Waiting 2s；Starting 1s；InMatch 由 DS 事件驱动 + 5s 兜底；Returning 1s。快照仅刷新，不推进 `ConnectionGeneration`。

### 5.4 `POST /api/rooms/{code}/team`、`/ready`、`/settings`
- `team {teamId}`：成员；仅 Waiting；目标队未满（TDM），KillRace 422 `TEAM_INVALID`；换队清本人 `isReady`；重复选同队幂等 200。
- `ready {isReady}`：成员；仅 Waiting；leader 也可标准备但开局条件只看非房主。
- `settings {...}`：仅 leader；仅 Waiting；逐字段白名单校验（422 `SETTING_INVALID` 带字段名）；成功 `roomVersion+1` + 全员清准备 + 系统消息。
- 三者均返回最新 `RoomSnapshotDto`，失败零副作用。

### 5.5 `POST /api/rooms/{code}/start`
- 仅 leader；仅 Waiting。校验：开局条件（§2）全通过 → 原子执行：生成 `matchId`、`matchGeneration+1`、写 `RoomMatchRoster` 快照、租用 DS（复用现有租用查询 + `Version` 令牌 + 归因日志）、房主 `isReady=true`、状态→Starting、`roomVersion+1`、为 roster 全员签发个人票据（TTL 90s 不变）。
- 响应 200 `StartMatchDto = { matchId, matchGeneration, roomVersion, mapId, mode, killTarget, timeLimitMinutes, connection{...同§5.2}, roster[{userId, teamId}] }`。
- 失败：409 `NO_SERVER_AVAILABLE`（保持 Waiting+准备）、409 `ROOM_NOT_READY`（含未准备/人数不足明细）、409 `ROOM_STATE_CONFLICT`（非 Waiting）。重复点击：第二个 start 在 Starting 状态 → 200 返回同一 `StartMatchDto`（幂等，不发新票不重租）。
- 系统消息：成功 `MATCH_STARTING`；无 DS `START_FAILED_NO_SERVER`。

### 5.6 `POST /api/rooms/heartbeat` 与 `POST /api/rooms/leave`
- heartbeat：由 no-op 升级为 Waiting/Starting/InMatch/Returning 全程成员保活（刷新 `LastSeenUtc`），204。非成员 204（无副作用，兼容）。
- leave：现有幂等语义不变；Starting 成员离开 = 移出 roster（不回填）；InMatch 沿用"个人 leave 保留房间"语义。

### 5.7 `POST /api/rooms/{code}/return`
- 请求 `{ matchId }`；roster 成员；状态 InMatch/Returning 且 `matchId == CurrentMatchId`。
- KillRace 路径：首个 ack 使房间 InMatch→Returning（幂等：重复 ack/他人 ack 均 200）。TDM 路径：通常已被 DS 终局上报先行转入 Returning，ack 仅记 `returnedAtUtc`。
- 返回 200 `{ status }`。客户端在 Returning 期间断开战斗连接（只退战斗，不退房：禁止调用 leave 路径），拉取结果（§7.3），等待 Waiting。

## 6. 战斗连接与票据（继承 + 扩展）

- 票据机制、消费复核、TTL 90s、`X-Server-Key` 控制面、断线上报语义**全部沿用现有实现**（`ServerInstanceService`/`ServerInstancesController`），本文不改其安全纪律。
- 扩展 1：消费复核的成员资格检查对 roster 补人语义自动成立（补人即成员）。
- 扩展 2：`JoinTicketConsumeDto` 增加 `matchId`、`matchGeneration`、`teamId`（从 roster/成员行带出，DS 用于队伍初始化与 Pending 名额）。字段可空 = 旧票据语义（KillRace roster 为 `None`）。
- 扩展 3：DS 心跳 Reserved→InMatch 同步房间状态不变；新增：心跳携带 `loadedRosterCount`（仅日志与 Starting 超时归因，不做状态权威）。
- 客户端：连接启动仅经 `RoomConnectionGate.TryValidate → WriteLaunchContext`；`start ack` 的 connection 与 join 重连/补人 connection 走同一链路并递增 `ConnectionGeneration`。

## 7. 终局、结算与返房

### 7.1 身份与幂等
- 终局身份 = `(roomCode, matchId, matchGeneration)`。所有终局路径以 `matchId` 幂等：重复上报/重复 ack/重复结算零副作用。
- 服务器统计来源原则：TDM 结果与奖励由 DS 上报驱动；KillRace 保持现有"客户端提交 + 服务端校验"路径（回归不动）。客户端胜负自报不得进入 TDM 结算。

### 7.2 TDM 权威终局（新增，`X-Server-Key`）
- `POST /api/server-instances/{instanceId}/match-result`：
  - 请求 `{ matchId, durationSeconds, winnerTeam|null(平局), players[{ userId, teamId, kills, deaths, assists, participationSeconds, rewardEligible, leftAtSeconds? }] }`。
  - 校验：实例绑定该房间、房间 InMatch、`matchId == CurrentMatchId`；违规 409 `ROOM_STATE_CONFLICT`/404。
  - 处理（幂等 by `matchId`，`RoomMatchResult` 行）：写结果 → 状态 InMatch→Returning → 释放实例 → `roomVersion+1` → 对 `rewardEligible=true` 玩家逐个套用现有奖励引擎（Profile/Wallet/Pass/成就，事务与锁顺序沿用 `MatchService`；每玩家按 `matchId+userId` 幂等）。
  - 资格：`rewardEligible` 由 DS 按 `MatchEligibility` 同口径给出（已生成+已认证）；终局前已退出/确认掉线者 false（后发的胜方奖励自然不发放）。补入者 `participationSeconds` 从其出生时刻计。
- `POST /api/matches`（现有玩家提交）扩展：请求增加可选 `matchId`、`teamId`。服务端校验：带 `matchId` 时必须等于提交者所在房间 `CurrentMatchId`，否则 409 `ROOM_STATE_CONFLICT`（防跨局伪造）；`MatchRecord` 落库带 `MatchId`。
- **旧 30 杀上限适配**：`ProgressionRules.ValidateMatchPayload` 改为模式感知——带 `matchId` 的提交（TDM/新版 KillRace）上限放宽为 `kills ≤ 200`、`duration ≤ 1200s`；无 `matchId` 的旧路径维持 `kills ≤ 30`、`≤ 900s` 不变。422 `MATCH_PAYLOAD_REJECTED` 语义不变，不做静默钳制。客户端 `MatchSettlementFlow.MaxKills` 同步改为模式感知（30 → 旧路径 30 / 新路径 200），防止合法 TDM 战绩被客户端拒发。

### 7.3 结果查询与返房
- `GET /api/rooms/{code}/match-result?matchId=` → `{ status: Pending|Final, matchId, winnerTeam, durationSeconds, players[{userId, username, teamId, kills, deaths, assists, rewardSummary?}] }`。
  - TDM：来自 `RoomMatchResult`；`rewardSummary` 为服务端已发放奖励快照。
  - KillRace：由 roster × 各自 `MatchRecord(matchId)` 聚合（未提交者缺席）；`winnerTeam=null`。
  - roster 成员仅可查 `CurrentMatchId`/`LastMatchId`；非成员 404。
- Returning→Waiting 迁移见 §3。返房后客户端留在原房间（不回大厅总页），准备清空，可立即再开局（复用或重租 DS）。

## 8. 聊天契约（HTTP 与 RPC 双传输，共享模型）

### 8.1 消息模型（两侧同构）
```
ChatMessageDto { seq: ulong, channel: "All"|"Team"|"System", senderUserId?: long, senderUsername?: string,
                 teamId?: TeamId, body: string, sentAtUtc, clientMessageId?: string }
```
- `seq`：每房间内单调递增（ulong，从 1）。HTTP 与 RPC 传输各自维护同一房间的同一条 seq 空间由服务端统一分配（见 §8.4 切换策略）。
- 客户端只发送 `{channel, body, clientMessageId}`；身份/队伍/时间/收件人全部服务端决定。`clientMessageId` = 客户端 UUID，用于端到端去重与本地乐观消息对账。

### 8.2 校验与限频（两传输同一套纯策略，`ChatPolicy`）
- 长度：`body` 按 **Unicode 标量字符数**（`grapheme` 不要求，按 code point 计）≤ 100；空/全空白拒绝。
- 拒绝换行（`\n` `\r`）与 C0/C1 控制字符；拒绝非法频道。422 `CHAT_REJECTED`（带原因码）。
- 不做富文本解析：存储与转发按纯文本，客户端渲染禁用 TMP 富文本标签（转义显示）。
- 限频：令牌桶按 `(userId, roomCode)`，容量 3、每 2s 回 1；超限 429 `CHAT_RATE_LIMITED` + `retryAfterSeconds`。RPC 路径同样执行（服务器侧同一策略实例）。
- 去重：服务端按 `(userId, clientMessageId)` 近 5 分钟窗口去重，重复返回原消息（200），不重发不计费。
- Team 频道：发送者 `teamId == None` → 422；投递仅同队成员。

### 8.3 历史与可见性
- 服务端每房间内存环形缓冲最近 100 条（**不落数据库**；进程重启清空属可接受）。
- 增量拉取（仅 Waiting/Returning HTTP）：`GET /api/rooms/{code}/chat?after={seq}` → `{ messages, cursor }`，`limit` 服务端封顶 50。游标非法（未来/负数）422 `CHAT_CURSOR_INVALID`。
- 新成员（含补人）只接收其加入之后的消息：服务端记录成员 `chatJoinSeq`，拉取下限 = max(after, chatJoinSeq)。
- 客户端可见历史上限 30 条（UI 层滚动窗口）；同一房间返房保留本地可见历史，离开房间清空；换队清空旧队聊与队伍草稿。
- System 消息由服务端内部构造（进入/离开、准备、设置变更、开始失败、倒计时、队伍获胜、返房、补人），客户端无法选择频道或伪造（无 System 发送路径）。

### 8.4 传输切换与去重
- Waiting/Returning：鉴权 HTTP（§8.2/§8.3）。Starting 短暂窗口：仍 HTTP（战斗连接未稳定）。
- InMatch 及 DS 未断开的结算窗口：仅 Owner RPC——`[ServerRpc(RequireOwnership=false)]` 上行，服务器注入身份/队伍后按收件人集合定向下发（FishNet Targeted/Observers 按连接过滤；**禁止全员广播后客户端隐藏 Team 消息**）。服务端身份来自票据消费建档（`JoinTicketAuthenticator.AcceptedUsers`），伪造频道/身份直接丢弃并记日志。
- 边界去重：客户端以 `clientMessageId` 全局去重；Starting→InMatch 切换瞬间 HTTP 拉取与 RPC 下发可能重叠，同 id 只显示一次。旧 `matchGeneration` 的 RPC 聊天消息在客户端按代际丢弃。
- 网络失败：HTTP 发送失败保留草稿与输入状态；RPC 失败（未连 DS）自动降级为本地排队，重连后不重放（丢弃并提示）。

## 11. 客户端契约要点（Q03/Q04/Q06/Q07 实施约束）

- 等待房间不触碰 `NetworkLaunchContext`；只有 `connection`（start ack / InMatch join）经 `RoomConnectionGate` 进入战斗。
- `ConnectionGeneration`：仅战斗连接启动递增；等待房间轮询走 `AccountSession.RefreshRoomSnapshot`（不递增，现状语义）。返房后的房间页面判定 = `session.Room != null`。
- 退战斗 ≠ 退房：Returning 路径禁止调用 `LeaveRoomAsync`/`ClearRoom`；`LeaveTransactionCoordinator` 的代际 supersede 语义保持——旧局退出事务不得清理新连接。
- 掉线回大厅（`MatchConnectionWatcher.HandleDisconnectLocally`）保留房间快照：DS 断开后回等待房间页并立即触发一次详情刷新；仅当详情 404/`ROOM_CLOSED` 才 `ClearRoom`。
- `GameplayInputGate` 新增独立聊天占用原因（不重构枚举）：`_chatFocused` 参与 `InputBlocked`；聊天关闭只释放该原因。光标所有权与 `GameplayMenuController` 协调，不新增平行光标管理器。
- 聊天 UI 挂接沿用 `MatchHudView.TryMount(canvas)` 运行时构建范式 + `DesignSystem` 主题；等待房间页与局内共用同一 `ChatPolicy`/消息模型。
- TDM HUD：红蓝总分/目标/倒计时/队标；战绩按队分组（K/D/A）。比分来源 = DS 权威事件（`MatchLifecycle` 事件镜像扩展），客户端不自算权威分。
- FFA/KillRace 回归入口：模式默认即可选 KillRace，规则链路（`MatchRules.TargetKills=20` 等）不改值，仅由房间设置注入后替代常量（常量保留为默认值）。

## 12. 开放项（v1.1 已定稿大部分；实施状态见括号）
