## 2. 案例时间线（每个案例 = 现象 → 证据 → 根因 → 修复 → 教训）

### 案例 1：校正风暴的三轮收敛（2026-09-16 01:07 → 13:07 → 16:40 三轮）

**现象（13:07 实测）**：YYLL 一局被硬校正 149 次，`local−ack` 恒定 32 tick（≈1.07s），服务器队列积压 9–10 条；每次误差冲到 0.75m 就触发 SNAP，约 7 tick（0.23s）再次冲顶——**误差增长速率 ≈ 移动全速（3.44 m/s 冲刺）**。

**证据与推理（第一轮）**：
- `CollectUnacked` 只发最旧 12 条 → 服务器每 tick 只消费 1 条 → 队列周期性变空。
- 队列空时服务器模拟 `Move=0` 的空命令：地面减速度 48 m/s²，**0.07s 内把权威角色从冲刺降到静止**，而客户端仍全速前进。
- 0.78m / 7tick ≈ 3.4 m/s —— 误差增长速率 = 移动速度，量化吻合。
- **教训**：锁定"误差以移动全速增长"这个签名，比盯着 SNAP 次数更能指向根因——增长速率 × 时间 ≈ 位移，反推的就是"有一端没在动"。

**修复（第一轮，13:07 批次）**：
1. 空队列按**最后已知输入**有界外推（上限 8 tick；跳跃/视角增量绝不重放；超限真停；冻结 Clear 作废外推源）——单 tick 仍只推进一步，不加速模拟时间。
2. 重放首步接地来源：快照恢复后 CC 刚瞬移、`isGrounded` 未重新解算 → 首步分支输入用快照 `Grounded`（一次性覆盖），后续步回到实际接触。
3. 输入 epoch（启动/冻结/死亡/重生/接管递增）+ 首个权威快照收敛入场领先（`LEAD_ALIGN`，lead>20 才动，会话一次）。
4. 服务器 pitch 与客户端 `FPMouseLook` 同源：**后坐债务先消费反向输入**再积分；快照携带基础俯仰；重生归零。

**验证（16:40 复测）**：lead 从 32 → 中位 5/10；服务器 gaps=0、extrap=0、队列 3–4 条；校正风暴在移动层面消失。

**教训**：①"锁步类预测"里，服务器空队列**不能**用空输入模拟——地面减速是瞬时把角色"刹停"的机制，等价于人为制造误差；②任何"领先/落后"要先证明它是否真的有害（确定性成立时领先只是延迟），不要为了消灭一个数字去改手感。

> **追更（2026-09-17，静态全量审计推翻上文的"有界外推"）：上面第一轮修复把空命令换成了外推，但两者都错在同一个更深的点——"服务器单方推进的位移"会被配对误差 100% 计入。**
>
> 外推路径下 `Snapshot.Tick = LastClientTick + k`，而客户端仍按 `LastClientTick` 取配对快照——k 步位移（冲刺 8 tick ≈0.9m）没有对应的配对口径；且菜单/聊天冻结时客户端已停止预测（不产输入），服务器却按最后已知输入外推前进：**每开一次菜单必产 0.75m+ 的虚假误差**（外推 8 tick + 超限后空命令减速滑行）。0.78m/7tick 的签名在"客户端在动"时被外推修掉了，但换到"客户端停了"的场景原样复发——修一个场景，造另一个场景。
>
> 正确语义是**两端同静**：空 tick 服务器保持位姿完全不模拟。瞬时到批间隙的 1–3 步位移（≤0.34m）落 0.03–0.75 平滑带由平滑收敛 + `Drain(3)` 有限追赶立即回填；真实长断流（>0.75m）仍按设计硬对位——那是不可预测的，修的是"无断流也 SNAP"的虚假路径。教训：**修"误差以移动全速增长"时，要审的是"哪一端在单方推进"，而不是急着让服务器也动起来——两端任何不对称的推进都会被配对口径计入误差。**

### 案例 2：硬校正占绝对多数、平滑校正从不触发（2026-09-16 16:40）

**现象**：YYLL 36 次 SNAP、平滑只 5 次；存活 MoveDiag 的 err 全部 ≤0.026m（<3cm 平滑阈值）——误差从 <3cm 直接跳到 ≥75cm。

**推理**：如果是渐进漂移（如持续 2–3° 的 yaw 差），误差会以 ~0.14–0.3 m/s 增长，在平滑带里停留 5 秒以上（160 个 ACK），平滑校正必然大量触发。**没有触发 = 误差是单步跳变**。`MovePhase=35`（CC.Move 自身反向 35 次）指向碰撞推挤：本地预测撞的是远端**插值代理**（2–8 tick 滞后 + RTT），服务器撞的是远端**权威**位姿——追击方（把对方往回顶）每 tick 被推出不同的量。

**为什么只有 YYLL（追击方）中招、1234（被追/死亡冻结）无感**：不对称在角色不在网络——被追方后撤时其插值代理离追击方**更近**，追击方被更早更狠地弹开；被追方与追击方的代理几乎不接触。同机同网也必然呈现一边倒。

**修复（方案A）**：远端 NT 插值压到 1，根/CC 停在最新权威位姿（与服务器同碰撞对象，残余差 ≈ RTT/2 ≈ 11cm，落回平滑带）；视觉平滑由 TP_Model 指数追随根（τ=0.07s，观感≈原 2-tick 插值）。基线（作者局部位姿）**每会话只捕一次**——死亡期间停写（倒地/贴地表现是 TP_Model 唯一写者），瞬移 >5m 直接对位，角色翻转/网络停止时复位。旧路径（插值根 + RTT 自适应 2–8 tick）保留为开关，供 A/B。

**教训**：①"平滑校正从不触发"本身就是诊断信息——它把误差的形状从"渐进"剪成"跳变"，直接排除一整类根因；②近距推挤的不对称性（追击方 vs 被追方）是这类问题的指纹，不要在网络层找对称解释。

### 案例 3：视角/身体 4.8° 永久夹角（用户实测"按 W 向左偏"）

**现象**：对墙按住 W+Shift，角色沿墙向左滑，最终滑出墙外坠地；日志 `yawLead=4.10°` 持续存在（用户看到 4.8°）。

**根因（C1 渲染视角 yaw 的扣减基准错误）**：C1 的设计 = 视角超前量 = "已积累、尚未提交给身体"的输入，让相机在 30Hz 身体台阶之上平滑。旧实现在每个 tick 用 **身体实际旋转**（`DeltaAngle(yawBefore, eulerAngles.y)`）扣减——但身体旋转 = 输入 − **被后坐补偿债务吃掉的部分**（压枪时鼠标反向输入先抵消后坐弹簧，不旋转身体）。于是"被吃掉的输入"永远留在超前量里：**压枪一次泄漏一点，累积成永久夹角**。相机歪 4.8°、身体没歪 → 按 W（沿身体前方）在屏幕上看就是斜着走。

**修复**：扣减基准改为**本 tick 提交的输入**（`cmd.YawDelta`）。压枪消费发生在提交点，超前量在提交后归零，只剩"帧间未提交"的部分——这才是 C1 要平滑的东西。

**教训**：①当一个"累积器 − 消费器"系统出现**净残留**时，先检查消费基准和累积基准是否是同一个量纲/同一个口径（这里差了一层后坐债务）；②用户的体感（"贴不住墙"）是最强的定位线索——视角与身体的夹角会让所有"沿视线走"的操作系统性偏移，而且**越压枪越歪**（复现条件自带）。

> **追更（2026-09-16 19:xx，用户实测"修完还偏"）：上面那次只修了一半。真根因是"钳制加在累积端"。**
>
> **现象**：同一症状在次日实机复现，且多了一条——"有一方打另一方完全不掉血"。
>
> **证据**：
> - `[MoveDiag] yawLead` 出现**整段冻住**的值：1.50（36s）/2.30（22s）/3.29（32s）/4.50（26s），以及**恰好 ±10.00**（=钳制值），清零点一律是 `REBASE DeathRespawn` 或冻结复位；
> - 90 发逐发对账（服务端 `[FireGeom] … cam o=… d=…` vs 同 id 客户端 submit 的 `aimD=`）：**|Δyaw| ≈ |yawLead|，30/30 命中，均值 3.6°、极值 13.5°**；
> - 角色不对称：一方 R 常驻 ±10° → 命中率 4.6%；另一方 R 仅 3–4.5° → 27%。这与用户"只有一方不掉血"的观察完全吻合。
>
> **根因（代数不变式）**：修复前是 `_viewYawDegrees = Clamp(_viewYawDegrees + lookYaw, ±10)`（**有损**）配合 `_viewYawDegrees -= cmd.YawDelta`（**无损**，扣完整未提交量）。设 `R = 超前量 − 未提交输入`：不饱和帧 `R' = (V+d) − (L+d) = R`（**严格不变**）；饱和帧 `R' = 10 − (L+d) = R − 超出量`（单向漂移）。→ R 是**粘滞随机游走**，只能靠死亡/重生复位清零。而服务器弹道沿**身体 yaw**（`ServerFireRequest` 只上传 tick 估算，方向由服务器自算），于是 R = 准心与弹道的**恒定夹角** → 走不直 + 打不中。
>
> **修复**：累积端**不做钳制**（`AccumulateViewYawLead`），钳制只保留在"写入视觉节点的显示角度"（`ResolveViewYawForDisplay`）——显示仍被 ±10° 兜底，但残差恒为 0。配置注释已写死"绝不可钳制累积量"。
>
> **教训**：①**"钳制一个用于累积的量"是经典陷阱**：只要钳制端与扣减端不是同一个（钳过的）量，就会产生不衰减的残差——正确做法是"累积无损、显示钳制"；②**回访失败要往"上次修的语义前提"上找**：上次修的是"扣减基准错"（真实存在），但没检查"累积本身是否有损"；两个错误可以同时存在且症状相同；③**"只修了一半"最典型的信号就是"症状减弱但形态不变"**（这里从 4.8° 变成"冻住的 1.5–10°"）；④用**逐发对账**（客户端声明瞄准 vs 服务器实际射线）代替"看画面像不像打中"，能把"手感"变成可量化的角度差。

### 案例 4：133.889m SNAP 与穿地无碰撞（用户主动触发）

**现象**：SNAP err=133.889m；`[MoveStep]` 显示 y −99→−130 自由落体、`cflags=None`（完全无碰撞）、速度 −66→−108 m/s；服务端快照同样在下落（早 ~50 tick），落地后两端落差 133m。

**定位**：这不是同步 bug——是用户主动测左偏、沿墙滑出地图坠入虚空。但暴露两个真问题：①CC **深穿碰撞体后凸体内无接触**（`cflags=None`），没有任何自愈，会无限坠到对局结束；②两端下落起点差 ~50 tick（同样的输入、不同的碰撞历史）→ SNAP 的 133m 只是把客户端拉到服务器的坠落深度。

**残余项**：服务器侧检测"长时间 airborne + 低于安全高度"→ 权威传送回安全点或判死重生（地图需要标定安全高度/最低点）；客户端随权威快照自然拉回。

**教训**：物理引擎的"深度穿插无接触"是静默失效——`cflags=None` 这类字段一旦在取证里出现，就是"物理层已经放弃"的信号，必须有游戏层的兜底（虚空判定/越界重生）。

### 案例 5：日志混写毁掉取证（两次踩坑）

**现象（16:40 局）**：两个客户端都直接双击 exe（无 `-logFile`）→ 共写默认 Player.log → 同一文件两次读取内容不同（第一次快照里的 36 条 REBASE 行，第二次快照消失）；YYLL 后半段日志永久丢失；审计只能靠行内 `pid=/conn=` 字段归属，且行与行会被拦腰拼接。

**修复（收口）**：
1. **唯一入口**：项目根 `启动客户端.cmd` → `Tools/Client/Start-LocalClient.ps1` → 每实例独立 `-logFile`（`Tools/Client/Logs/client-<stamp>-<id>.log`），启动行打印 `pid/protocol/buildId/CLIENT_LOG`。cmd 横幅明确 "SOLE client entry / DO NOT launch the exe directly"。
2. **防误用兜底**：`AppRoot` 启动时检测命令行无 `-logFile`（=直接双击 exe）→ 自建 `persistentDataPath/Logs/client-self-<pid>-<stamp>.log` 镜像全部日志（每行带时间戳+pid 前缀，首行写 pid/protocol/buildId），并打 `SELF_LOG_ENABLED` 提示改用唯一入口；启动器路径检测到 `-logFile` 自动跳过。
3. 复测流程固定：`启动联机服务器.cmd` → `启动客户端.cmd` ×2（YYLL/1234 各一）→ 测试 → 用启动器打印的 `CLIENT_LOG` 路径取证。

**教训**：①混写损坏发生在**写入端**，任何事后解析（哪怕按 pid 归属）都救不回被覆盖的行——取证必须在写入端保证隔离；②"日志行内带 pid/conn"是对混写最有韧性的格式设计（行被拼坏也能归属），值得作为所有多进程诊断的格式约定。

### 案例 6：取证基建（让"下一个问题"定位变快）

为定位本轮问题新增/修正的诊断，全部是**行内 key=value、可 grep、可跨端按 tick 对齐**：

- `[MoveDiag]`（每 2s/端）：`gen/sub/recv/cons/empty`（生成-上行-消费账本）、`lead=local−ack`（时间轴积压）、`epoch`（输入代际）、`snaps/rebase(Initial/HistoryMissing/Snap/Divergence/Overflow/DeathRespawn)`（校正来源分解）、`gaps/replayGap`（缺口）、`pullback=Move/Authority/Render`（回拉写者归因）、`pitch/pitchGap`（两端基础俯仰差）、`dt/long/bg/focus`（本机卡顿与失焦）。
- `[MoveStepWindow]`/`[MoveStep]`（异常点小窗口导出）：按 clientTick 对齐的两端单步全状态——input、接地（分支来源 S=快照/实际）、collisionFlags、速度/计费计时/步态/冲刺意图、后坐债务、profile hash、服务器附注（EMPTY/EXTRAP/REPLAY）。
- `[Pullback]`：写者链归因（MovePhase=碰撞推挤 / SmoothPhase=软纠偏 / AuthorityCorrection=重基+重放后净位移 / RenderPhase=相邻渲染帧视觉反向）。
- `[Day3][Reconcile] REBASE <kind>`：每次硬校正必留痕（含 idleSteps——服务器"无真实输入"步数）。

**设计原则**：①诊断行自带进程身份（pid/conn/obj/match），任何一行都能独立归属（对混写最有韧性）；②计数区分"区间累计"与"会话单调累计"（`snaps` 是区间、`rebase` 是会话——把区间当累计会得出错误结论）；③导出走"异常触发 + 节流"，不做逐帧刷屏。

### 案例 7：打中了却不掉血——命中归属不能靠"几何共面"假设（2026-09-16 19:xx）

**现象**：双人实机互射，一方几乎打不中（命中率 4.6%），另一方正常（27%）；用户描述"一方打另一方完全不掉血"。同时用户先问了两个关键问题："是请求没发到服务器，还是服务器吞掉了？"

**第一步·先回答"请求是否到达"（计数对齐，不要猜）**：
服务端 `[FireTrace]` 行 = 6228 reject + 248 resolve = **6476**，客户端 submit = 4573 + 1903 = **6476**——**逐 id 完全对齐**，不存在丢包/吞包。96% 被 `CanAttemptFire` 廉价闸（冷却/弹药/动作槽）拒掉：**这是设计行为**（`FireHeld` 时每帧提交一次请求，服务器只在自身武器冷却结束后接受）——"拒绝率高"和"打中不掉血"是两件事，必须先分开。

**证据（真正的"打中却不掉血"）**：
- 服务端绊线 `[CombatRay] HIT_NO_TARGET victimRootCollider=Player_Day2_Rebuilt(Clone) … hits=2` **触发 8 次**；
- `[FireGeom] reason=NO_TARGET decision=UseMuzzleHit finalCollider=Player_Day2_Rebuilt(Clone) finalTarget=null` 5 条——**枪口射线确实命中敌玩家碰撞体**（mzl dist=1.23/3.38/4.44m），却因归属失败零伤害；
- PlayMode 真实射线复现（CC r0.35/h1.8/skin0.08 + 同参数 trigger 胶囊，1096 组几何扫描）：

```
raycast hits=2
   BodyHitbox [CapsuleCollider] dist=4.6838
   Player     [CharacterController] dist=4.8961      ← 差 0.2123m（实测最大 0.2946m）
```

**根因**：归属回退假设"根 CharacterController 与 BodyHitbox **同体积共心**"，用 `±0.05m` 容差在同根其余命中里找可归属碰撞体。实测两段命中距离差 0.04–**0.29m**（skinWidth 量级，且**胶囊并不与 CC 共形**：同一几何下差量随入射角/高度变化）→ 最近命中落在根 CC 时，BodyHitbox 命中被 5cm 容差刷掉 → `target=null` → 零伤害。
附带事实：**CharacterController 必须真正 `Move()` 过才会进入 `Physics.RaycastNonAlloc` 的命中列表**（静止时查不到）——所以"编辑器静置复现不出、实机跑动才炸"。

**修复**：加第二层归属 `ResolveDescendantTarget`——命中的碰撞体在受害对象**祖先链**上（典型=玩家根 CC，`DamageableTarget` 挂在子节点 `TP_Model`）时，在**该命中对象自身子树内**找目标归因。**不变量**：搜索限定命中对象子树 + 射手根排除 → "不同根绝不归属"（身后另一个玩家不会被误伤）；5cm 那层保留为"几何共面时给出精确落点"的精度路径，不靠放大容差救。

**验证**：新增 4 例 EditMode 物理用例（根碰撞体命中必伤害 / 子 hitbox 父链不回退 / 无目标对象绝不跨根归属 / 射手自身不自伤）；**红测证明**——临时禁用第二层后复跑 `passed=2 failed=2`，还原后 27/27。

**教训**：①**归属条件要按"对象语义"写，不要按"几何巧合"写**：`hitbox` 与"可受击实体"是两回事，用"两段命中距离接近"来推断"它们属于同一个可受击对象"是把资产实现细节当成了契约；②诊断**必须先回答可计数的问题**（请求到达数 vs 处理数），再谈定位——否则会在错误的前提里深挖；③**多碰撞体形态的变化（skin width/trigger 化/分层）会静默破坏依赖几何的假设**：凡是"两个碰撞体应该重合"的注释，都应该配一条"实测差量"的断言或用例；④绊线日志要打印**能继续追的字段**（后来补了 `colliderType=`），否则只知道"失败了"、不知道"失败在什么形状上"。

### 案例 8：四个独立缺陷叠出一个"SNAP 风暴"——先修口径，再修推进（2026-09-17）

**现象**：无丢包、无碰撞推挤的对局仍频繁硬校正：一局 47 次 SNAP、err 全部挤在 0.753–0.808（恰好贴 0.75 阈值上方）、`smooth=0`（平滑带从不命中）、每约 7 tick 一次（=冲刺 0.112m/tick × 7 ≈ 0.78m 的节律）；叠加三个离散症状——开 ESC 菜单/聊天回来被拽回、本机一次长帧后 lead 3→9 永久抬升、死亡重生后短暂"输入无响应后瞬移"。

**定位方法（静态审计，不猜唯一根因）**：对预测/和解全链路做只读审计，按四类结论标注（Confirmed Defect / Structural Risk / Diagnostic Gap / Ruled Out），每个缺陷给出"能解释什么/不能解释什么"——最终锁定四个**互相独立**的缺陷，它们的叠加恰好复现全部症状形态：

**四个根因**：
1. **Snap 判定用 raw 误差（D1，Critical）**：`Reconciler.Decide` 在**扣除在途平滑量之前**判 0.75 阈值。raw 误差包含"配对快照之后已施加、尚未被任何快照计入"的平滑步进——本应平滑的 0.58m 被判硬对位；且 Snap 路径跳过台账消费、`HardSnapTo` 又 `Invalidate` 台账，在途量每次从零重积——**"从不进平滑带 + err 挤在阈值上方 + 一旦开始停不下来"正是这个放大器的数学签名**。修复：判定改 `corrected = raw − inFlight`（新 5 参重载，旧签名保留），err 诊断双口径（`err=`/`errRaw=`）。
2. **服务器空队列外推位移计入配对误差（D2，High）**：见案例 1 追更——外推的 k 步位姿没有配对口径，菜单冻结场景必产 0.75m+ 虚假误差。修复：空 tick hold。
3. **`Drain(1)` 无追赶（R1，High）**：`ServerMaxCatchUpPerTick=3` 定义了却从未接线；客户端单帧可突发 5 步，两端平均速率相同 ⇒ **积压一旦形成没有任何路径能追回**，lead 永久抬升 = 权威位姿相对画面永久滞后（硬对位位移恒为 lead×速度，"被拽回一米"的体感来源）。修复：`Drain(ServerMaxCatchUpPerTick)`。
4. **死亡窗口在途批次污染重生 epoch（D3，High）**：`MovementCommand` 无 epoch 字段，服务器只按 tick 幂等；死亡前"已发出未确认"的批次在重生后被当作新输入消费（客户端重生从 ack 重新生成同号 tick，旧命令先到先消费把新命令挤成 stale 静默丢弃——重生后短暂动不了再瞬移）。修复：冻结窗口（倒计时/死亡）拒收在途批次并计数（`dropFrozen=`），不动 wire 契约（epoch 上契约留协议 v5）。

**验证**：定向 EditMode 41 例新增全绿（含审计 §7.1 最小反例的接线锁：raw 0.78 − inFlight 0.20 = 0.58 必须 Smooth）；全量 852/861 零回归；协议不变 fps-net-v4，双端同批重建（DS f33328ca594f / Client ea87c6a7dc5d）。实机验收待用户（判据：菜单冻结无拽回、卡顿后 lead 自动回落、smooth 大量命中、`errRaw−err` 非零=在途量生效）。

**教训**：①**"err 恰好贴阈值 + 平滑带从不命中"要怀疑判定口径，而不是误差本身**——误差被系统性夸大时，第一件事是把判定量和真实残余量分开记（err/errRaw 双口径）；②**多缺陷叠加的症状是"任何单一解释都不完整"**：外推解释不了 7tick 节律、raw 判定解释不了菜单场景、Drain(1) 解释不了重生瞬移——静态审计的价值就是能同时列出全部候选并各自证伪/证实；③**"定义了却没接线"的常量是审计金矿**（`ServerMaxCatchUpPerTick` 定义三周无人发现未接线）；④**修复要修"口径"而不是"阈值"**：把 0.75 调大只是把风暴变小，把判定改到正确口径（corrected）才消除风暴；⑤epoch 残留不必动协议也能关死可达路径（冻结窗口拒收）——**先评估最小修复的可达性闭环，再决定是否值得动 wire 契约**。

### 案例 9：Dedicated Server 上的"视觉表现"污染了"权威判定"（2026-09-18 实机：侧/背射击不掉血 + 血液弹孔浮空）

**现象**：双端对局中从敌人**正面**射击基本稳定掉血，但从**侧面和背后**射击经常完全不掉血；且命中时的血液喷溅/弹孔贴花不贴在人物身上——敌人倒地后，特效仍悬停在原本站立的位置（录屏 57-65s 血溅浮空在身侧、2:44 尸体已倒地弹孔仍悬在站立胸口高度）。

**证据与推理**：
- 链路：`ServerFireRequest → LagComp 回溯 → WeaponController.TryFire → CombatResolver（QueryTriggerInteraction.Collide）`，请求到达率逐 id 对齐无丢包，`[FireGeom]` 的 miss 分类指向 GEOMETRY（射线没打中碰撞体，不是归属/存活问题）。
- 方向性签名：横移目标最难打中、正面最好打——**命中难易与"目标相对射线的位移方向"相关**，而不是与距离/朝向角相关。
- 关键结构事实：玩家 hitbox（BodyHitbox 胶囊）挂在 **TP_Model** 下；而 9/16 起远端视觉平滑（0.05–0.25s 缓冲插值）在**所有非 Owner 实例**上运行——**包括 Dedicated Server 自己**。DS 每帧把 TP_Model 写到"滞后的插值视觉位姿"，服务器权威根却在最新位姿 → **DS 上 hitbox 与权威根解耦**；LagComp 每 tick 记录、开火时回滚的正是这个漂移位姿。横移时胶囊侧向偏移最大 ~0.25s×3.4m/s≈0.8m ≫ 胶囊半径 0.35m → 侧/背射线落空；正面射击的误差沿射线轴方向，被胶囊 1.8m 纵深容忍 → 打得中。方向性完全吻合。
- 特效浮空同根：命中点取自服务器权威射线=打在漂移胶囊表面，与客户端看到的视觉模型位置不一致；且 SpawnImpact 世界坐标 Instantiate 不挂载 → 尸体倒地后特效悬停原位。

**修复（2026-09-18）**：
1. **DS 上 TP_Model 钉到权威根**：`UpdateRemoteVisualSmoothing` 增加 `IsServerInitialized && !IsClientInitialized` 早分支（`PinTpModelToRootForServer`：直接写 根∘作者基准、缓冲清空）——headless 无视觉平滑需求；Host/纯客户端插值不变。
2. **站桩可命中保险**：Unity CC 必须 `Move()` 过才进入 Raycast 命中集——生成/重生后补一次 1mm 沉降 Move（`RegisterCharacterControllerForRaycast`）。
3. **特效贴人**：命中玩家（`HitscanResult.Target != null`）时 SpawnImpact 挂到 Target 视觉体下（Instantiate parent 保持世界位姿）——尸体倒地/移动跟随；静态场景命中保持世界坐标。**契约零变更**（复用已在广播载荷内的 Target）。
4. 回归锁：`PinTpModelToRootForServer_AlignsModelToRootBaseline`（钉根恒等+缓冲清空）、`SpawnImpact_WithTarget_ParentsEffectToTarget/WithoutTarget_StaysWorldSpace`。
5. 同批顺带修复：**重生弹药不重置**（ServerRespawn 对两槽 `ServerResetAmmoToLoadoutDefault`：满弹匣+初始备弹+清切枪缓存+OnAmmoChanged 推送）——重生链路审计时发现弹药/切枪缓存都不在重置清单里。

**教训**：①**"表现层优化"在服务器上跑就是判定层缺陷**——任何写 Transform 的"视觉平滑/视觉跟随"，接入前先问一句"这个 Transform 上挂着判定物吗？"（本项目 TP_Model 同时是视觉节点与 hitbox 载体，两个身份在客户端可以分离、在 DS 上必须钉死）；②**方向性症状是最强的几何线索**——"正面中、侧背不中"直接把搜索面从归属/网络/冷却压缩到"碰撞体与视觉的空间关系"，先画"目标位移方向 vs 射线方向"的命中热区再谈根因；③**视觉贴花/特效的挂点决策要在生成时就定好"跟随谁"**——世界坐标 Instantiate 是默认最省事的写法，但对会动/会倒的目标必然悬空，数据载荷里带上 Target 引用比事后补偿便宜得多；④**重生是一个"重置完整性检查点"**：位姿/生命/弹药/缓存/表现/物理注册（CC Move）每一项都要点名，缺一项就是一个"重生后 X 不对"的实机缺陷。

## 3. 方法论沉淀（本项目反复用到的判定法）

1. **先修证据，再修根因**：第一批交付永远是"能让下一次复现给出答案"的诊断（同 tick 双端状态、写者链归因），而不是猜测性修复。本项目两次验证了这一点：13:07 轮的取证在 16:40 轮直接指认了跳变型误差。
2. **误差的"形状"比阈值重要**：渐进增长（漂移）→ 会进平滑带；单步跳变（碰撞/传送）→ 只会触发硬校正。"平滑校正从不触发"本身就是根因分类器。
3. **误差增长速率反推机制**：增长速率 ≈ 移动速度 → 有一端"没在动"（减速/卡住）；增长速率 ≈ 速度 × sin(角度) → 有一个持续的角度分歧；离散跳变 → 碰撞/去贯穿/传送类事件。
4. **不对称性指认角色**：同机同网下只有一方中招 → 差异在"双方在模拟里扮演的角色"（追击方 vs 被追方、移动方 vs 静止方、持枪方 vs 死亡方），不要在网络上找对称解释。
5. **区分"物理失效"与"同步失效"**：`cflags=None` / 深度穿插是物理层静默放弃，同步修不好它，需要游戏层兜底。
6. **协议纪律**：动 RPC 载荷/SyncVar 形状 → `GameProtocolIdentity` 递增 + 双端同批重建 + 核对运行进程的 APP_PROTOCOL/buildId 与磁盘 manifest（旧进程会静默吞掉整轮修复）。纯表现/纯客户端逻辑改动不动协议。
7. **一次只动一个可疑层**：本轮先修时间轴/外推/接地（13:07 轮），复测确认移动层面干净后，剩下的 36 次 SNAP 才能被干净地归因到碰撞层——如果一次全改，就无法归因。

## 4. 面试问答（可直接使用的说法）

**Q：你们的帧同步/状态同步方案是什么？**
A：服务器权威 + 客户端预测 + 和解（reconciliation）。客户端固定 30Hz tick 预测，输入按 tick 编号批量冗余上传（抗丢包），服务器每 tick 消费一条并每 tick 向 Owner 下发权威快照；客户端拿快照和同 tick 的预测快照做差：误差 <3cm 忽略、0.03–0.75m 平滑收敛（指数衰减）、≥0.75m 硬对位 + 从确认 tick+1 重放未确认输入。快照携带完整确定性状态（位置/旋转/速度/接地/步态计时/冲刺意图/后坐补偿债务），保证重放与首跑同起点。

**Q：遇到过最难的一个同步 bug？**
A：追击方被反复硬校正，一局 36 次，而且平滑校正几乎从不触发。这个"平滑从不触发"是关键线索——说明误差不是渐进漂移而是单步跳变。用自建的同 tick 双端取证（每个模拟 tick 记录输入、接地来源、collisionFlags、完整状态）+ 回拉写者归因，定位到：本地预测碰撞撞的是远端玩家的**插值代理**位姿（滞后 2–8 tick），而服务器撞的是**权威**位姿，近身交火时 CharacterController 去贯穿推挤每 tick 给出不同结果。修复是把远端玩家的碰撞根停在最新权威位姿（和服务器同一个碰撞对象），视觉平滑移到模型节点上用指数追随，碰撞确定性恢复后误差回落到平滑带。这个案例里不对称性也很典型：只有追击方中招，被追方无感——差异在双方扮演的角色，和网络无关。

**Q：怎么定位"误差从哪来的"？**
A：三个手段。①给每个模拟步做双端同构取证：按 clientTick 对齐，逐字段比（输入、接地来源、碰撞标志、速度、计时器），第一个不一致的字段就是分叉点；②给回拉做写者链归因：把一次校正拆成 Move（碰撞解算）/ Smooth（软纠偏）/ Authority（重基+重放）/ Render（视觉插值）四个写者，谁的位移是负的谁就是嫌疑；③用误差增长速率反推机制：速率≈移动速度说明有一端"没在动"（后来证实是服务器空队列用空输入模拟、被地面减速刹停），速率≈速度×sin(角度) 说明有持续的角度分歧，离散跳变说明是碰撞/传送类事件。

**Q：服务器输入队列为空时怎么办？**
A：**保持位姿，完全不模拟**（2026-09-17 定案）。这个问题我们前后改了三版，每一版都有可讲的教训：第一版空命令（Move=0）——地面减速 48 m/s² 在 0.07s 内把冲刺角色刹停，而客户端还在全速前进，每个"到批间隙"都制造约一个身位的误差（签名：误差以移动全速增长）；第二版按最后已知输入有界外推——修掉了"客户端在动"的场景，却在"客户端停了"的场景原样复发：菜单/聊天冻结时客户端不产输入，服务器却按最后输入外推前进 k 步，而外推位移没有任何配对口径（快照 Tick=ACK+k，客户端按 ACK 取配对快照）——每开一次菜单必产 0.9m+ 的虚假硬校正。最终定案 hold：空 tick 两端同静（误差恒 0）；瞬时到批间隙的 1–3 步位移 ≤0.34m 落平滑带由平滑收敛、配合 `Drain(3)` 有限追赶立即回填；真实长断流（>0.75m）仍硬对位——那是不可预测的，修的是"无断流也校正"的虚假路径。一句话版本：**配对比较的两侧必须同口径——任何"单方推进"（外推、空命令减速）都会被 reconciliation 误读成分叉；服务器没有输入时唯一正确答案是不动。**

**Q：预测里状态恢复的坑？**
A：两个。①接地：快照恢复时 CharacterController 刚被瞬移，`isGrounded` 还没重新解算，直接读它会走错分支（地面/空中），所以重放首步的分支输入必须用快照显式携带的接地值，只覆盖一步，之后回到物理实际接触——坡沿和跳跃语义不受影响；②后坐补偿债务：输入会被债务消费（压枪），客户端和服务器各自持有债务状态，快照必须携带债务并在重放前恢复，否则重放会二次消费或漏消费。

**Q：客户端和服务器输入消费不一致会怎样？**
A：我们有个真实案例：压枪时鼠标反向输入会先被后坐补偿债务消费，剩余部分才旋转身体。渲染视角超前量的扣减基准如果用"身体实际旋转"，被债务吃掉的输入就会永远留在超前量里，压枪一次泄漏一点，最后累积成 4–5° 的永久视角/身体夹角——玩家体感是"按 W 角色斜着走、贴不住墙"。修复是把扣减基准改成提交的输入本身：债务消费发生在提交点，不允许进入视觉层。教训是"累积器−消费器"系统出现净残留时，先检查两个基准是否同口径。
**（追更 2026-09-16）** 同一条问题线次日复现，说明上面那次只修了一半：真正让残差**不可衰减**的是"钳制加在了累积端"。设 `R = 超前量 − 未提交输入`，则**不饱和帧 R 严格不变**（`(V+d)−(L+d)=R`），饱和帧单向漂移——R 是个粘滞随机游走，只能靠死亡复位清零。实测 `yawLead` 冻在 1.5/2.3/3.29/4.5 与恰好 ±10（钳制值）达 20–36 秒；90 发逐发对账 |客户端瞄准−服务器射线| ≈ |yawLead|（30/30，最大 13.5°），因为服务器弹道沿身体 yaw、客户端只上传 tick。修法：**累积无损、只钳制写进视觉节点的显示角度**。面试可用的一句话：**"凡是'钳制一个还要继续被减法消费的量'，都会留下不衰减的残差——钳制必须放在输出侧。"**

**Q：reconciliation 的判定阈值怎么定？误差刚好贴着阈值怎么办？**
A：这是我们的 Critical 级真实缺陷：硬校正判定用的是 raw 误差，而"已施加但还没被任何权威快照确认"的平滑校正步进（在途量）没有扣除——于是所有误差都被系统性夸大，硬校正永远命中而平滑带从不触发，日志形态是 err 全部挤在阈值上方 0.003–0.058m、一局 47 次、每约 7 tick 一次，而且每次硬对位清空台账让在途量从零重积，形成自我维持的风暴。修法是把判定挪到正确口径：`corrected = raw − inFlight` 之后再进 0.03/0.75 双阈值，诊断同时记两个口径（err/errRaw）用于对账。面试可用的一句话：**"误差判定前先问一句：这个量里混入了多少'我自己已经修过的部分'——凡是'边修边量'的系统，判定口径必须扣除在途修正量，否则修得越勤判得越狠。"** 另一个收获：贴阈值的误差形态（集中在阈值上方极窄区间）本身就是"口径被污染"的签名，而不是"误差刚好都这么大"的巧合。

**Q：服务端把 96% 的开火请求都拒了，是 bug 吗？怎么判断？**
A：不是，先看**计数是否对齐**：服务端 `[FireTrace]` 行数（reject+resolve）= 6228+248 = 6476，客户端 submit = 4573+1903 = 6476，逐 id 完全对齐 → 没有丢包/吞包。96% 被拒是因为客户端在 `FireHeld` 时**每帧**提交一次请求，而服务器只在自身武器冷却结束后接受（`CanAttemptFire` 廉价闸：冷却/弹药/动作槽，先挡掉必被拒的请求，避免为它们付 hitbox 回溯代价）。所以"拒绝率高"与"打中不掉血"是两件事，必须分开查。判断口径：**能计数的先计数（到达数 vs 处理数 vs 生效数），再谈定位**；真正的掉血问题要用"几何结果分类"（`OK / GEOMETRY / NO_TARGET / TARGET_DEAD / FRIENDLY`）+ 逐发对账。

**Q：命中归属为什么不能按几何写？**
A：我们踩过：归属回退假设"根 CharacterController 与 BodyHitbox 同体积共心"，用 ±5cm 容差在同根其余命中里找可归属碰撞体。实测（PlayMode 1000+ 组几何扫描）两者射线表面差 **0.04–0.29m**（skin width 量级，且不随入射角保持恒定）→ 最近命中落在根 CC 时归因失败，`NO_TARGET` → 零伤害，日志里表现为"射线明确打中敌方玩家碰撞体却 target=null"。修法是按**对象语义**归属：命中对象在受害实体祖先链上时，用该对象子树里的 `DamageableTarget`；搜索范围限定子树 + 射手根排除，保证"不同根绝不归属"。教训：**把"两个碰撞体应该重合"当契约，就是用资产实现细节当接口**——这类假设要么加实测断言，要么别用。附带一个 Unity 事实：CharacterController 必须在 `Move()` 过之后才会进入射线命中列表（静止时查不到）。

**Q：玩家互相碰撞的预测分歧怎么处理？**
A：这是目前最硬的一类。本地预测撞的是远端玩家的插值代理（滞后 2–8 tick），服务器撞的是权威位姿——推挤方向和强度每 tick 都可能不同，而且是离散跳变，直接跳过平滑带。我们定的方案是把远端玩家的碰撞根停在最新权威位姿（与服务器同一个碰撞对象，残余差 ≈ RTT/2），视觉平滑移到模型节点。关键教训是这类分歧有强不对称性：追击方（把对方往回顶）中招、被追方无感，同机同网也一样——遇到"只有一方有问题"先想角色差异。

**Q：多进程日志怎么保证可审计？**
A：三层。①每个客户端实例独立 `-logFile`（启动器统一分配，路径打印在启动行）；②诊断行内自带 pid/conn/obj/match，行被拼接也能归属；③对"直接双击 exe"的误用路径，进程启动时自建按 pid 命名的镜像日志（每行带时间戳+pid）。原因是踩过真实的坑：两个进程共享默认 Player.log，文件偏移互相覆盖，同一文件两次读取内容都不同，事后任何解析都救不回被覆盖的行。

**Q：这套方案的已知边界？**
A：①远端权威碰撞根仍差 RTT/2 的碰撞对象延迟（≈11cm，落在平滑带内，不触发硬校正）；②基础俯仰（aim pitch）两端仍有分配时序差（中位 1–3°），影响瞄准精度、不影响移动，已列入待办；③穿地无自愈（长时间 airborne + 低于安全高度 → 权威传送）已立项未实施；④回溯命中窗口 200ms，输入领先过大时会降低命中注册质量——所以我们给时间轴积压做了显式告警与首快照对齐。
