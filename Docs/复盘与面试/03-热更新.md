# 03-热更新（xLua 主线：从审计到两个试点上线）

> 2026-09-17 全程复盘：可行性审计 → 用户拍板 xLua 路线 → P0-P5 全阶段交付。
> 配套：交接报告 `Docs/交接/2026-09-17-热更新xLua接入与两试点-报告.md`、演示手册 `热更新Demo演示手册.md`、开发规范 `Lua热更页开发规范.md`。

## 一、决策链（为什么是 xLua）

**背景**：项目要具备热更能力，首批任务=①大厅战绩页 ②新地图。用户此前已导入 xLua（零使用）与 Addressables 包（未初始化）；当时是 Windows Mono 后端，程序集干净（Game.Core←{Gameplay,Account}←{Presentation,UI}，无人反向引用）。

**三条路线对比**（审计结论）：

| | xLua（已选） | HybridCLR | Mono+Assembly.Load 自研 |
|---|---|---|---|
| 范式 | 新功能用 Lua，与 C# 存量并存 | C# 无缝，但需切 IL2CPP+程序集热冷切分+Boot 重构 | 最小改动但绑死 Mono |
| 平台 | Mono/IL2CPP/iOS 均可（Gen 铺路） | 需先 IL2CPP 化 | 上 IL2CPP 即废 |
| 迁移风险 | 低（加法式 seam） | 高（大爆炸式） | 无（但也无长期价值） |

用户拍板 xLua（当时平台预期"不确定"→xLua 的 Mono/IL2CPP 双兼容是实际加分项）；分发链路选"完整链路"。

## 二、踩坑实录（按时间序，全部实证）

1. **asmdef 布局两次返工**：①放 `Src/` 下 → Gen 的 partial 扩展（WrapPusher 等）在 Gen/（Assembly-CSharp）与 XLua 程序集**类型身份分裂**，2924 错误；②根级 asmdef 与 WSA 托管插件 xlua.dll 同名被 Unity 拒 → 最终 `XLua.Runtime`（根级含 Src+Gen）+ 两个嵌套 Editor asmdef。**教训**：xLua 的 Gen 产物是引擎类型的 partial 扩展这一事实，决定了整个程序集拓扑。
2. **Gen 配置的"鸡生蛋"**：改完 GenConfig 不编译就点 Generate Code → 生成器读的是**旧编译域里的旧配置**（还含 Game.* 类型）→ 重生出循环引用代码。恢复：备份 Gen → 还原 → 编译 → 再 Gen。**教训：Generate Code 前必须 start_compilation_pipeline**。
3. **asmdef 循环引用是"延迟爆炸"的**：Game.UI 的 wrap 文件在第一次 Gen 就生成，但当时编译过了（当时 Gen 在 Assembly-CSharp）；拆程序集后同一配置才炸。根因链要连着看。
4. **Resources 双扩展名**：`foo.lua.txt` 资源名=`Lua/foo.lua`，Load 必须带 `.lua` 中缀——xLua loader 静默失败走了内置搜索链，报错信息（no such resource）极具迷惑性。**EditMode 下 AddComponent 不触发 Awake**（既有惯例）继续应验。
5. **PS5.1 curl JSON 引号剥坏**（已知坑再+1）：换 `@file` body 一次过。
6. **版本号自动递增踩自己**：制包脚本"读服务器 manifest+1"在我连续制/部署自验时把给用户的 v3 覆盖成含 bundle 的版本并部署了——用显式 `-Version` 重整版本线。**教训：给用户的交付物版本一旦定版，后续自验必须显式版本号**。
7. **既有 EF 缺陷被活体验证挖出**：`SubmitForPlayerAsync` 把 C# 方法 `RoomStatus.Normalize` 写进 EF 谓词——InMemory 测试全绿、真 MySQL 500（R02 上线起就炸，只是在线对局走服务器结算路径绕过了它）。**"InMemory 绿 ≠ 关系库可用"再+1**；修复=先取状态列再内存归一。

## 三、架构精髓（面试可讲）

1. **稳定 seam 模式**：热更的真正难点不是"加载 Lua"，而是**预先设计好热更代码能挂进现有系统的插口**。三个 seam：动态页注册表（LobbyPresenter 壳读表生成页签+导航分发）、Facade 数据通道（Task→主线程回调→LuaTable）、loader 优先级链（下载目录→Resources 兜底）。seam 只增不改签名——改签名=静默炸线上脚本。
2. **内容寻址分发**：manifest 只存 {path,sha256,size}；差异下载=哈希比对；版本目录不可变；回滚=换 manifest 指针；DowngradeRejected 保护本地。原子性：installed.json 只在全部文件校验通过后写。
3. **可玩性优先的失败策略**：远端不可达→已装版本→内置兜底，永不阻塞进大厅；minClientVersion 门→提示整包更新（exe 不可热更的物理边界）。
4. **双通道场景加载**：内置图（SceneName 在 BuiltinScenes）走 SceneManager，热更图走 AssetBundle（LoadFromFile 后 SceneManager 按名加载——Unity 语义：bundle 注册进虚拟文件系统）。fail closed：bundle 未就绪拒绝入场并提示更新。
5. **红线管理**：热更面永不触碰协议层（Game.Gameplay/FishNet），用 AssemblyBoundaryGuardTests 把 asmdef 依赖方向锁进 CI。

## 四、面试问答（可直接背）

**Q: 你们的热更新怎么做的？**
A: 代码热更用 xLua：C# 侧预置三个稳定 seam——页面注册表、LuaFacade 数据通道、自定义 loader（下载目录优先、内置 Resources 兜底）；Lua 页面调 C# 的 DesignSystem 静态构建器搭 UI，Mono 下走反射模式互操作，Gen 固化 Unity/TMP 核心类型面（业务类型因程序集环约束走反射，IL2CPP 化时用桥程序集解）。资源热更用 AssetBundle：manifest（path/sha256/size）+ 版本目录不可变 + 内容寻址增量下载 + 失败回退内置。Boot 时序：下载器在 AppRoot 初始化前完成，LuaEnv 的 loader 直接指向已下载目录。

**Q: 为什么选 xLua 不用 HybridCLR？**
A: 决策时平台预期不确定——xLua 在 Mono 和 IL2CPP 下都能跑（Lua 是解释执行，iOS 合规），而 HybridCLR 必须先 IL2CPP 化并做程序集热冷切分+Boot 重构，是一次高风险大爆炸迁移；且我们 UI 全是代码程序化构建，Lua 调 C# 静态构建器非常顺。代价是引入双语言范式，用"每个 Lua 页配 EditMode 冒烟+只增不改签名的 seam 纪律"管理。如果将来全 C# 热更需求变强，HybridCLR 是明确的演进方向。

**Q: 热更怎么保证安全？**
A: 分层回答：完整性=SHA256 逐文件校验+失败不写指针（原子性）；可用性=三级回退（远端→已装→内置）；版本治理=整数版本单调+DowngradeRejected+minClientVersion 整包门；路径安全=相对路径消毒防目录穿越；协议面=热更代码永远碰不到网络权威层（asmdef 守卫测试锁死）。v1 没做代码签名，是已知后续项。

**Q: 热更一个新地图的完整链路？**
A: 场景不进客户端构建清单；构建成 ChunkBasedCompression 的 AssetBundle，走与 Lua 相同的 manifest 分发；客户端地图目录改由后端 /api/maps 数据驱动（DTO 含 SceneName），建房页按钮和入场解析都消费它；入场时内置图走 SceneManager、非内置走 bundle 双通道，bundle 未就绪 fail closed。关键认知：**服务器无法被热更**——DS 构建清单必须同步登记新地图并重发（中心化部署），租用查询按 mapId 匹配实例，这一点在方案设计时就要讲清楚，不能只做客户端。

**Q: 踩过最深的坑？**
A: 两个值得讲：①xLua 的 Gen 产物是引擎核心类型的 partial 类，这决定了"Gen 必须与 Src 同程序集"，而同程序集又意味着 Gen 面不能引用业务程序集（会循环）——最后用"业务面走反射模式（Mono 下无损）+ 未来 IL2CPP 用桥程序集解"收尾，一次布局错误在两轮编译后连坏三处才收敛，教训是新第三方库接入前先画程序集拓扑图。②改 Gen 配置后没编译就执行 Generate Code，生成器读的是旧域里的旧配置，重生出已删除的循环引用代码——工具链的"读编译产物"特性要求每步后重新建立诊断边界。
