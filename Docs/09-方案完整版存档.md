## 1. 项目定位说明

**一句话定位**：一个具备商业游戏流程感的多人 FPS Vertical Slice——证明「Client/Server 架构理解 + Gameplay 系统设计 + 数据持久化 + 热更新 + 模块化架构」，而非证明画面或内容量。

- 与第一个项目（RE4 入村 Demo）的能力互补：Demo1 证明场景/动画/整合能力；Demo2 证明网络/架构/服务端能力。
- 流程闭环：登录 → 大厅 → Loadout → 技能升级 → 进入房间 → Arena 对战 → XP 结算 → 升级 → 回大厅强化。
- **明确不做**：匹配系统、排位、大厅3D场景（纯UI大厅）、载具、移动端、语音、观战、反作弊实装、Dedicated Server 实装。

## 3. 整体架构图

### 3.1 客户端三层（程序集边界 = 依赖单向）

```
┌───────────────────────────────────────────────────────────┐
│ Presentation 层  (Game.Presentation)                       │
│   FP Rig(Cam sway/bob/recoil) · FP/TP AnimDriver ·        │
│   WeaponView · VFX/SFX · HUD · 菜单UI                      │
│   职责：把 Gameplay 状态渲染出来。唯一允许触碰动画/UI      │
│   (AnimDriver 内部经 Animancer 播放, 对上层不可见)         │
└──────────────△────────────────────────────────────────────┘
               │ 只读 State + 订阅 Event（严格单向向下引用）
┌──────────────┴────────────────────────────────────────────┐
│ Gameplay 层  (Game.Gameplay, 纯C#, 不引用 FishNet/UI)      │
│   PlayerEntity · Locomotor · ActionSystem · Arsenal ·     │
│   WeaponController/WeaponRuntime · Health · CombatResolver│
│   · Upgrade · InputReader · IBalanceConfig(接口)          │
└──────────────△────────────────────────────────────────────┘
               │ 接口反转：INetGateway（Gameplay 不知道 FishNet）
┌──────────────┴────────────────────────────────────────────┐
│ Network 层  (Game.NetworkAdapter)                          │
│   PlayerNetwork(SyncVar/RPC) · RoomFlow · FishNet 适配     │
└───────────────────────────────────────────────────────────┘
```

**三条铁律（针对 RE4 遗留问题的总纲）**：
1. 依赖方向单向：`Presentation → Gameplay ← NetworkAdapter`。Gameplay 不引用上层任何类型（上层通过 C# event / 接口回调获知变化）。
2. 单写者原则：每个可变状态全局只有一个写者（详见 §5 表A）。
3. Gameplay 离线可跑：Week 1 不连网也能完整开发 FPS 手感（本地假网关），这是两周排期的核心调试策略。

### 3.2 全系统拓扑

```
[Unity Client]                          [Backend 本机]
  ApiClient ──HTTP/JWT──> ASP.NET Core WebAPI ──EF Core──> MySQL 8
     │注册/登录/档案/配装/升级                       (Navicat 管理)
     │
  RoomFlow(房主Host/客户端Join) — LAN — FishNet Transport
     │                          [Host = 房主客户端 = 权威服务器]
     │                          权威逻辑: CombatResolver/Lua公式
     └── 比赛结束: Host 广播战绩 → 各客户端自报 POST /api/matches
[热更新] Assets/StreamingAssets/Lua/*.lua → LuaEnv → IBalanceConfig
         (编辑器热重载按钮; Build 包从磁盘读, 改数值免重Build)
```

## 4. 模块职责与依赖关系

| 模块 (目录) | 职责（做什么） | 明确不做什么 |
|---|---|---|
| Core | GameEvents、轻量 ServiceRegistry、IBalanceConfig 接口、TickDriver | 不含 gameplay 规则 |
| Account | ApiClient(HTTP+JWT)、登录/注册/档案/配装/升级的请求与响应模型 | 不做任何 gameplay |
| Lobby | 菜单流程状态机（Login→Main→Loadout→Upgrade→Room），纯 UI 编排 | 不持有玩家战斗数据 |
| Player | PlayerEntity 组合根、Health、Upgrade 属性应用 | 不直接操作武器/动画 |
| Movement | Locomotor：输入采样→速度→CharacterController.Move；LocomotionState | 不做打击/技能位移逻辑 |
| Weapon | WeaponDefinition(SO) / WeaponRuntime / WeaponController / WeaponView | 不算伤害（交给 Combat） |
| Combat | CombatResolver（服务器单点）：命中判定、调 Lua 公式、发伤害事件 | 不播任何特效 |
| Action | ActionSystem：互斥动作状态机（Reload/Switch/Grenade/HitReact/Death） | 不含各动作的具体效果 |
| Network | PlayerNetwork(SyncVar/RPC)、RoomFlow、INetGateway 实现 | 不含 gameplay 规则 |
| Animation | FPAnimDriver / TPAnimDriver / AnimEventReceiver | 不做 gameplay 判定，动画事件只上报 |
| Presentation | FP CameraRig(sway/bob/recoil/ADS)、VFX/SFX 触发器 | 不改任何 gameplay 状态 |
| HotUpdate | LuaEnv 生命周期、balance 加载/重载、OnBalanceChanged 广播 | 不让 Lua 拿到引擎对象 |
| UI | HUD（血量/弹药/击杀信息）、各菜单面板 | 不直接读网络层 |

**asmdef 划分（6 个，适度即可）**：`Game.Core` ← `Game.Gameplay` ← { `Game.Presentation`, `Game.NetworkAdapter`, `Game.UI` }，`Game.HotUpdate` 独立。Gameplay 程序集 **不引用** FishNet / UnityEngine.UI（编译期强制依赖方向，AI 改代码时越界会直接报编译错——这是防混乱的硬约束）。

**依赖规则**：UI/Presentation/NetworkAdapter 只订阅 Gameplay 的事件、读 Gameplay 的只读状态；Gameplay 之间只允许同层引用（如 WeaponController 查询 ActionSystem 状态），禁止反向。

## 5. State Ownership Table

### 表A：本地单写者（防 RE4 问题 1/3/4 的制度层）

| 状态 | 唯一写者 | 其余系统 |
|---|---|---|
| Transform 位置/旋转 | **MovementSystem（Locomotor）**，且只经 CharacterController.Move | 全部只读；摄像机跟随也只读 |
| 动画播放（Animancer 状态/权重/淡入淡出） | **AnimDriver（FP/TP 各一）** | Gameplay 层引用不到 Animancer（asmdef 隔离）；出现 `GetComponent<Animator>()` 即违规 |
| WeaponRuntime（弹药/冷却/换弹计时） | WeaponController（服务器权威；客户端仅预测显示） | 动画事件只上报「动画播完」，不直改弹药 |
| ActionState（当前动作/可否开火） | ActionSystem | Weapon 查询它，不写它 |
| ExternalForce（击退/爆炸冲量） | Locomotor 内的 ForceAccumulator | 其他系统只能提交 ForceRequest |
| 输入 | InputReader（唯一采样点） | — |

### 表B：网络权威（谁拥有真相）

| 数据 | 权威端 | 机制 | 备注 |
|---|---|---|---|
| 位置/旋转/速度 | Server | V1: NetworkTransform；V1.5(可选): FishNet Prediction | 见 §9 评估 |
| LocomotionState 枚举 | Server | SyncVar | 远端 TP 动画 BlendTree 输入 |
| 生命/存活 | Server | SyncVar + 死亡事件 RPC | |
| 当前武器索引 | Server | SyncVar | |
| 弹药/冷却/换弹进度 | Server | SyncVar(低频) | 客户端 HUD 只读显示 |
| 开火 | Client 提交意图 | ServerRpc(FireRequest) | 服务器验证：冷却/弹药/动作槽/方向合法 |
| 命中判定+伤害 | **Server** | 服务器 Raycast + Lua 公式 | V1 无 lag comp（小图+局域网可接受） |
| 换弹/切枪/手雷 | Server | Start/Complete 双事件 ObserversRpc | 远端播动画的关键 |
| XP/等级/技能点 | **MySQL** | 比赛结束客户端自报 POST /api/matches | 服务器端 clamp 校验；信任边界在 §11 讨论 |
| Lua 数值 | 静态配置 | 服务器端计算用 | Host=房主，天然一致 |

**核心叙事（面试）**：「位置、生命、弹药都是服务器权威的状态同步；开枪、换弹、死亡是服务器广播的事件同步。客户端开枪先本地播动画（表现预测），命中与伤害必须等服务器判定。」——这句话就是本项目的网络设计主线。

## 6. Gameplay FSM 架构与 Action System（防 RE4 问题2）

### 6.1 Locomotion / Weapon(Action) / Life 三个 FSM：**分离——且是三个正交状态维度，绝不合并为一个大 FSM**

| FSM | 状态集 | Owner（唯一写者） | 更新频率 | 职责边界 |
|---|---|---|---|---|
| **LocomotionFSM** | Idle / Walk / Sprint / Jump / Air / Land | Locomotor | 每 FixedUpdate | 只管移动与速度；不知道玩家在换弹还是濒死 |
| **ActionFSM**（上半身互斥槽） | None / Reload / SwitchWeapon / GrenadeThrow | ActionSystem | 事件驱动+计时器 | 只管占用上半身的互斥动作；不知道玩家在跑还是在空中 |
| **LifeFSM** | Alive / Dying / Dead / Respawning | Health | 事件驱动 | 只管生死；**最高层门控**：死亡即冻结另两个 FSM 的输入 |

**为什么不是一个大 FSM**：
1. 合并 = 状态爆炸（6 Loco × 4 Action × 4 Life ≈ 96 状态，转移表不可维护、AI 改一处崩一片）；
2. 三个维度**变化频率与网络同步策略不同**（Locomotion 每 tick 连续同步、Action 偶发事件同步、Life 极少状态同步），合并会让同步粒度变粗；
3. 竞技 FPS 行业惯例就是「移动层 + 动作层 + 生命层」正交叠加（跑动中可换弹、换弹中可被打死）。

**Fire 不是任何 FSM 的状态**：开火是被 ActionFSM gate 的瞬时行为（CurrentAction==None 且冷却好即可触发），若做成状态，全自动武器会导致状态机每发子弹自旋一次。这是面试高频追问点。

### 6.2 门控矩阵（FSM 间只读查询，禁止反向写入）

| 查询方 → 被查方 | 读取 | 用途 |
|---|---|---|
| WeaponController → ActionFSM | CurrentAction == None? | 换弹/切枪/手雷期间禁止开火 |
| Locomotor → LifeFSM | IsAlive? | 死亡冻结移动输入 |
| ActionSystem → LifeFSM | IsAlive? | 死亡打断一切动作 |
| AnimDriver → 三者 | **PlayerStateView**（聚合只读结构：locoState/speed/action/life/weaponIdx） | 合成动画的唯一输入源 |

**跨 FSM 唯一允许的"写" = LifeFSM 死亡时的 Interrupt 广播**（C# 事件，非直接方法调用）。HitReact 从 ActionFSM 中**移除**：它降级为 additive 叠加层（受击只加动画权重+镜头 shake，不占动作槽、不打断换弹）——竞技 FPS 中「挨一枪换弹就断」惩罚过重；这一取舍本身就是好的面试谈资。

### 6.3 ActionFSM 生命周期

```
Request → TryStart(条件: 动作槽空闲 / 弹药未满 / 存活)
        → Start(锁定动作槽, 发 OnActionStarted)        ← AnimDriver 收事件播动画
        → Execute(计时器推进 0→1)                       ← 真相在计时器, 不在动画
        → Complete(应用效果: 弹药回满/切枪生效, 发 OnActionCompleted)
任意时刻: Interrupt(reason) → Cancel(回滚: 弹药不变/槽清空, 发 OnActionInterrupted)
                                                    ← AnimDriver 收事件淡出动作层
```

### 6.4 打断优先级表

| 优先级 | 动作 | 可被打断于 | 说明 |
|---|---|---|---|
| 最高 | （Death 属 LifeFSM） | 不可被打断 | 广播 Interrupt 打断一切 |
| 1 | SwitchWeapon | Death | 切枪可打断换弹（FPS 手感惯例） |
| 2 | Reload / GrenadeThrow | Death、SwitchWeapon | 被打断弹药不变 |
| 叠加层 | HitReact | 不打断任何人 | additive 权重 0.2s 衰减 |

### 6.5 真相规则

**Reload 完成 = WeaponController 计时器到点（duration 来自 Lua），不是动画播完**。动画事件只用于表现对齐；两者谁先到都收敛：计时器到 → 服务器完成并广播；动画没播完也强制切回姿势。动画被打断**永远**不会卡死换弹状态——这就是 RE4 问题2 的制度级解法。

### 6.6 网络如何同步 Action（而不是 Animator）

**原则：网络上只传 Action 语义（枚举 + tick + 参数），从不传 Animator 参数、动画名、进度百分比。每端各自把 Action 语义翻译成本地动画。**

| 机制 | 载荷 | 用途 |
|---|---|---|
| SyncVar CurrentAction | (ActionType, startTick, weaponIdx) | 迟加入者补齐 + 正确性兜底 |
| ObserversRpc OnActionStart / Complete / Interrupt | (actionType, reason) | 触发远端动画/VFX/音效 |
| ServerRpc ReloadRequest / SwitchRequest / GrenadeRequest | 玩家意图 | 服务器验证后正式启动权威计时器 |
| TargetRpc OnActionRejected | 拒绝原因 | 客户端回滚本地预测（弹药/姿势显示恢复） |

三端一致性流程（以 Reload 为例）：
```
本机(预测端): R键 → ActionSystem.TryStart(Reload) 本地立即启动
   → FP 换弹动画立刻播、HUD 进换弹态 → ServerRpc(ReloadRequest)
服务器(权威): 验证(存活/动作槽空/弹药未满)
   → 启动权威 Reload 计时器 → SyncVar CurrentAction=Reload
   → ObserversRpc(OnActionStart, Reload)
远端客户端: OnActionStart → TPAnimDriver.Play(reloadClip, 淡入0.1s)
本机收到自己的广播: 已预测 → 去重跳过
服务器拒绝: TargetRpc(OnActionRejected) → 本机 Interrupt 本地预测并回滚显示
被打断:   服务器 Interrupt → SyncVar=None + ObserversRpc(OnActionInterrupt,reason)
   → 远端淡出动作层回 locomotion; 本机同步回滚
```
远端换弹动画时长由 clip 决定，但**换弹是否真实完成只由服务器计时器决定**——逻辑与动画在各端解耦、再经事件对齐。这就是「同步 Action 而非同步 Animator」的完整含义，也是本项目 Animation×Network 交叉处的核心设计。

## 7. Animation 架构（防 RE4 问题1）——Animancer 作为 Presentation 播放引擎

### 7.1 分层定位

```
Gameplay FSM (Locomotion/Action/Life, 真相)          ← §6
        │ PlayerStateView(只读) + C# 事件(OnActionStart...)
        ▼
AnimDriver (FP/TP 各一, 唯一动画写者)                 ← Presentation 层的"翻译官"
        │ 状态→Clip映射 / 事件→Play()调用, 全部显式代码
        ▼
Animancer (播放引擎: Mixer/Layer/Fade/EndEvent)       ← 插件, 只做播放
        ▼
Animator (渲染)  ← 不再有 AnimatorController 资产图, 不再有参数表
```

**Animancer 在本架构中的角色 = 纯播放引擎**（等同 FishNet 之于网络）：它不含任何 gameplay 逻辑，只是让「代码驱动动画」比裸 Mecanim 干净一个数量级。**Gameplay 层完全不知道 Animancer 存在**（asmdef 隔离），AnimDriver 内部才使用它——若哪天换回 AnimatorController，只改 AnimDriver 一个类。

选用理由（面试讲法）：
1. AnimatorController 资产图是**不可代码评审、不可 diff、AI 无法可靠编辑**的黑盒；Animancer 把状态机搬进代码 = 可单测、可 git diff、可让 AI 精确修改；
2. 天然匹配单写者制度：没有参数表就没有「谁都能 SetBool」的漏洞；
3. 网络事件→动画的映射（OnActionStart→Play(clip)）用 Animancer 是一行显式调用，无需 Any State/Trigger 这类脆弱机制。

### 7.2 动画职责表（谁播什么）

| 动画 | Local (FP Rig) | Remote (TP Model) | Animancer 实现方式 | 触发源 |
|---|---|---|---|---|
| Idle/Walk/Run/Jump | FP 手臂/武器随呼吸轻摆 | TP 移动混合 | **LinearMixerState**(0=idle,1=walk,2=run) 按速度参数驱动 + 空中Clip切换 | **状态**：LocomotionFSM SyncVar |
| Fire | 立即播（表现预测） | TP 开火 | Action 层 `Play(fireClip, 0.05s fade)` | **事件**：OnFireShot(本机预测/远端RPC) |
| Reload | FP 换弹 | TP 换弹 | Action 层 `Play(reloadClip)` | **事件**：OnActionStart(Reload) |
| SwitchWeapon | 收枪/出枪两段 | TP 收出枪 | Action 层两段 clip + EndEvent 串联 | **事件**：OnActionStart(Switch) |
| GrenadeThrow | FP 投掷 | TP 投掷 | Action 层 | **事件**：OnActionStart(Grenade) |
| HitReact | 不播（仅镜头 shake+红屏） | TP 受击方向 | **additive 叠加层**（不占动作槽） | **事件**：OnHitReact(dir) |
| Death | 相机坠落+隐藏手臂 | TP 死亡 | 停掉 mixer 与动作层, Play(deathClip, 不淡入) | **事件**：OnDeath |
| Sway/Bob/Breathing/Recoil/ADS | **不走动画系统**：FPCameraRig 纯数学计算偏移 | — | — | 本地输入/状态 |

Animancer 层划分（TP 模型）：`Layer0 = Locomotion mixer`（全身）、`Layer1 = Action 层`（上半身 AvatarMask）、`Layer2 = Additive 层`（HitReact/呼吸）。FP 手臂 Rig 更简单：单层 + mixer + action 即可。

### 7.3 Animation Event 使用规范（白名单制度）

1. **首选 Animancer State Events**（代码注册 `state.Events.OnEnd` / `OnNormalize(0.5f)` 回调）——注册点就在 AnimDriver 代码里，可评审、不藏在 clip 资产里；
2. clip 内 Unity AnimationEvent 仅允许作**时间标记**：命名 `EVT_<Action>_<Marker>`（如 `EVT_Reload_MagOut`、`EVT_Fire_Muzzle`），载荷只允许 枚举int + 可选float，禁止传字符串命令/对象引用；
3. 接收者唯一：挂在同一对象上的 `AnimEventReceiver` → 翻译成 C# 事件 → 仅流向 AnimDriver/WeaponView（表现层内部）；**需要通知 Gameplay 的（如换弹动画结束对齐）也必须经 AnimDriver 转发**，且 Gameplay 只把它当「对齐提示」，不当真相（真相=计时器）；
4. **服务器判定永不依赖动画事件**（服务器可能根本没有播这段动画）；网络层永不出现在动画事件链路上；
5. 事件丢失必须可容忍：没有 `EVT_Reload_MagOut` 播出来，换弹照样成功（音效可由计时器近似触发兜底）。

### 7.4 FP/TP 双表现组织

- 同一 PlayerEntity 下两个互斥子对象：本机激活 FP Rig（摄像机+手臂+FPAnimDriver），远端激活 TP Model（TPAnimDriver+武器挂点）。**避免同步两套模型**，`IsOwner` 分支决定激活谁。
- 两个 AnimDriver 输入完全相同（PlayerStateView + 事件流），输出各自模型——这正是「同一 Gameplay 状态，两种表现」的架构证明点。
- 远端换弹可见 = OnActionStart(Reload) 事件驱动，不是从位置/速度推断——满足「远端必须看到换弹」需求，且延迟=一次 RPC 而非动画同步。
- 备注：Animancer 需要 Animator 组件存在（作为播放后端），但**不再使用 AnimatorController 资产与参数**；Root Motion 保持关闭（§13 问题3）。

## 8. Network Replication 设计（状态 vs 事件）

| 类别 | 用途 | 机制示例 | 原则 |
|---|---|---|---|
| **状态同步**（持续真值） | 位置/朝向、LocomotionState、HP、武器索引、弹药、**CurrentAction(枚举+tick)** | FishNet SyncVar / NetworkTransform | 丢失可自愈；新加入者能补齐（含动作状态） |
| **事件同步**（一次性） | 开火特效、**OnActionStart/Complete/Interrupt**、受击、死亡、飘字 | ObserversRpc（可靠） | 只发一次，不重放；事件仅触发表现，真相在状态 |
| **请求**（客户端→服务器） | FireRequest(dir, tick)、ReloadRequest、SwitchRequest、GrenadeRequest | ServerRpc | 服务器逐项验证（冷却/弹药/动作槽/存活） |

**铁律：网络上传输的永远是 Gameplay 语义（FSM 状态枚举 + Action 事件），从不传输 Animator 参数、动画名、归一化进度。每端用 AnimDriver 把语义各自翻译成本地动画。**

**开火全链路（一条主线讲清整个 C/S 设计）**：
```
本地客户端: 鼠标按下 → InputReader → WeaponController.TryFire
  → [客户端预测] 立即播 FP 开火动画/枪口特效/后坐力 (弹药显示-1)
  → ServerRpc(FireRequest, dir, tick)
服务器(Host): 验证(冷却/弹药/动作槽) → Raycast 命中 → Lua 公式算伤害
  → 扣弹药/扣目标血 → ObserversRpc(OnFireShot, hitInfo) 广播全员
  → 目标死亡则 OnDeath + 战绩累计
远端客户端: OnFireShot → TP 开火动画+弹道特效; OnReloadStart → TP 换弹动画
```
本机自己也收到 OnFireShot（去重：本机已预测过则跳过重复特效）——这个去重细节是很好的面试谈资（预测与权威结果合并的最小案例）。

## 9. 网络高级功能 A/B/C 评估

| 功能 | 建议 | 实现成本 | 面试价值 | 两周风险 | 结论 |
|---|---|---|---|---|---|
| Client Prediction | **A 第一版实现**（FishNet Pro 自带，不自研） | 中：学习 OnTick/InputData/Reconcile，基于官方 demo 改 | **高**（FPS 网络必聊） | 中 | Day 8–9 专窗；**回退线：Day 9 午未跑通官方 demo → 切 NetworkTransform**，面试照样能讲取舍 |
| Server Reconciliation | **A**（与 Prediction 绑定，Pro 自带） | 同上 | 高 | 同上 | 同上 |
| Lag Compensation | **A- 升级：低成本接入**（Pro 自带） | **低**：CombatResolver 中 `Physics.Raycast` → `LagCompensator.Raycast` 一处替换 + 配置历史缓冲 | 高（能讲 history buffer/回滚射线原理） | 低 | Day 9 若 Prediction 成则顺带接入（半小时级）；若 Prediction 回退则降回 B 仅讲解 |
| Rollback（物理回滚） | **C 放弃** | 高 | 中 | 高 | 不做；面试讲「Pro 有 rollback，Demo 场景无需要」 |
| Matchmaking | **C 放弃** | 高 | 低 | 高 | 房间码/直连 IP 加入，够用 |
| Dedicated Server | **C 放弃**（一句话说明可行） | 高 | 中 | 高 | 面试讲：FishNet 支持 headless build，当前用 Host 模式是 Demo 权衡 |
| Anti Cheat | **C 放弃** | 高 | 中 | 高 | 面试讲服务器权威已覆盖哪些验证点（§5 表B）即可 |
| Custom UDP Transport | **C 放弃** | 高 | 中 | 高 | 用默认 transport；能讲 transport 抽象即可 |

> **Pro 版带来的唯一变化是成本曲线**：Prediction 与 Lag Compensation 从「贵」变「便宜」，但**学习成本不变**——面试价值不在「你启用了 Pro 功能」，而在你能讲清 tick 制、输入回放、reconcile 快照、history buffer 原理，以及为什么 CombatResolver 单点化让 lag comp 只改一行。学习时间已排入 Day 9，并保留硬回退线。

## 10. 网络扩展设计（适度预留，禁止空接口）

| 概念 | V1 做法 | 未来扩展路径 |
|---|---|---|
| Tick System | 不自研，直接用 FishNet TimeManager 的 tick；Gameplay 输入采样对齐 OnTick | 天然支持 prediction |
| Input Command | 定义 `InputData` 结构体（moveDir、lookDelta、buttons 位域：fire/aim/reload/jump/sprint/switch1-3/grenade） | 这就是未来 prediction 的输入格式；V1 由 Locomotor 直接消费，无需第二套 |

| Network Message Layer | **INetGateway 薄接口**：Gameplay 通过它发请求/收广播，实现类持有 FishNet | 这就是「自己的同步层设计」，一层接口而非空壳框架 |

### 表结构（4 张，刻意克制）


### API（JWT 鉴权；Swagger 自带）

```
POST /api/auth/register  {username, password}
POST /api/auth/login     → {token, profile}          (GET /api/profile 同构)
PUT  /api/profile/upgrades {upDamage,upAmmoCap,upMaxHealth}   (校验技能点+上限)
GET  /api/loadout | PUT /api/loadout
POST /api/matches        {kills,deaths,score} → {xpEarned, levelUps, skillPoints} 
                          (服务器端按公式表 clamp 防刷)
```

### 结算信任边界（面试讨论点，V1 明确取舍）
- V1：**比赛结束 Host 广播各客户端战绩 → 每个客户端自报自己的 POST /api/matches**，服务器对数值做范围 clamp。
- 坦诚标注：这不防作弊（客户端可伪造战绩），正确做法是 Host 用 server-to-server 密钥上报——Demo 权衡，面试主动讲出这一点比假装安全更加分。
- XP/升级公式放 Lua（GetXpForLevel），两端同源。

### 落地路径（针对你的后端经验）
1. `dotnet new webapi` + Swagger → 跑通一个 echo 接口（半天）
2. EF Core + Pomelo 连 MySQL，Code-First Migration 建表（半天；比手建表更能讲）
3. 注册/登录 + BCrypt + JWT（1 天内，AI 辅助下模板化程度高）
4. 档案/配装/升级/战绩 CRUD（1 天）
5. Unity 侧 ApiClient 用 UnityWebRequest + JSON（半天）

## 12. Hot Update 设计（xLua）

### Lua/C# 边界（白名单式，只暴露纯函数）

```csharp
interface IBalanceConfig {           // Game.Core 中定义, Gameplay 只见此接口
  WeaponStat GetWeaponStat(string weaponId);   // damage/rpm/magSize/reloadTime/spread/adsFov...
  int GetFinalDamage(string weaponId, int upDamageLv);   // 伤害公式
  int GetXpForLevel(int level);                        // XP 曲线
  int GetUpgradeCost(string statId, int currentLv);    // 升级消耗
}
```
- Lua 侧 = `balance.lua`：纯数值表 + 纯函数。**不引用任何 UnityEngine 类型、不持有任何对象引用**——Lua 拿不到 NetworkObject/Transform/Animator 是由注册机制天然保证的（只注册 delegate，不注册对象）。
- HotUpdateManager 持 LuaEnv；启动从 `StreamingAssets/Lua/`（Build）或 `Assets/HotUpdate/Lua/`（编辑器）加载；提供 `Reload()`（编辑器按钮 + 快捷键）→ 广播 `OnBalanceChanged` → WeaponDefinition 缓存失效、重读数值。
- **伤害/XP 公式只在服务器端调用**（Host=房主客户端）；客户端 HUD 显示静态副本即可。
- 演示脚本（面试/录屏用）：改 `AK.damage 32→50` → 点 Reload → 开枪伤害变化，无需重新 Build。

### xLua 风险与降级
- 风险：xLua 仓库更新停滞，Unity6/团结引擎下可能有小编译错。**Day 0/1 立即验证 HelloWorld**。
- 降级线：修坑 >0.5 天 → 改为 JSON 配置热载 + 保留 IBalanceConfig 与公式委托设计。面试叙事不变：「选型 xLua，因版本兼容降级 JSON 热载，接口边界不变」——这本身就是合格的工程决策故事。

## 13. 四大历史架构问题的防御方案 + Player/Weapon 架构

| # | RE4 问题 | 防御方案（本方案落点） |
|---|---|---|
| 1 | 多脚本写 Animator | 单写者制度（§5表A）+ AnimDriver 层（§7，内部经 Animancer 播放）+ asmdef 编译期隔离（Gameplay 引用不到动画层类型） |
| 2 | Reload 被打断状态错误 | ActionSystem 真相在计时器，动画只是表现（§6） |
| 3 | 移动权混乱 | Locomotor 唯一拥有 Transform；Root Motion 全关（动画 in-place，位移=速度驱动）；击退等外力走 ForceAccumulator 请求；若必须用 RootMotion（死亡踉跄）也经 OnAnimatorMove 回调进 Locomotor，不旁路 |
| 4 | 武器状态与动画耦合 | WeaponRuntime 纯数据 + 计时器为真相；动画事件仅对齐表现（§6/§14） |

### Player Entity 组合（依赖方向图）

```
PlayerEntity (NetworkObject 根, 房间生成)
 ├─ Gameplay:  PlayerLocomotor · PlayerActionSystem · PlayerArsenal(武器集)
 │             · PlayerHealth · PlayerUpgrades(读Lua/档案)
 ├─ Network:   PlayerNetwork(NetworkBehaviour: SyncVar/RPC, 实现 INetGateway)
 └─ Presentation:
     ├─ FP Rig  (仅 Owner 激活): FP CameraRig + FP Arms + FPAnimDriver + WeaponView
     └─ TP Model(仅远端激活):    TPAnimDriver + TP 武器挂点
依赖: Presentation→Gameplay; NetworkAdapter→Gameplay(写状态/转发事件); Gameplay 对二者无感知
```

### Weapon 五件套

| 类 | 性质 | 内容 | 禁止 |
|---|---|---|---|
| WeaponDefinition | ScriptableObject（静态） | weaponId、视图资源引用、**FP/TP 动画 clip 集**（Animancer 无控制器资产）、挂点 | **不存 damage 等数值**（数值一律 Lua）；严禁存运行时状态 |
| WeaponRuntime | 纯 C# 类（每实例） | currentAmmo、cooldownRemaining、reloadTimer、state 枚举 | 禁止写回 SO |
| WeaponController | Gameplay 逻辑 | TryFire/TryReload/TrySwitch；服务器权威验证与执行；本地预测触发 | 不碰 Animator |
| WeaponView | Presentation | FP viewmodel 挂载、特效、弹壳、TP 挂点切换 | 不含判定逻辑 |
| WeaponNetwork | Network | 当前武器索引 SyncVar、弹药 SyncVar、Fire/Reload/Switch 事件 RPC | 不含规则 |

武器 = 3 长枪 + 1 手枪 + 1 手雷，全部由 WeaponDefinition 数据驱动，**零逐武器脚本**。手雷为第一候选砍项（见 §17 风险）。

## 14. 插件使用原则与评估

| 插件 | 结论 | 理由 |
|---|---|---|
| **FishNet Pro** | ✅ 用 | 只用其 Transport/SyncVar/RPC/Prediction/LagComp 底层；movement/weapon/combat/同步策略全自研 |
| **xLua** | ✅ 用 | 只做数值/公式热更层 |
| **Animancer Pro** | ✅ 用（仅 Presentation 播放引擎） | 不含 gameplay 逻辑、不藏同步设计——只是把「代码驱动动画」变干净（§7 详述）。注意讲解时主动展示 AnimDriver 的状态→clip 映射代码，证明逻辑自研 |
| ProBuilder | ✅ 用 | Arena 白盒搭建（URP 兼容好） |
| FPS Framework / FPS Template（各类成品 kit） | ❌ 拒绝 | 会把 movement/weapon/combat 变黑盒——面试死亡问题「讲讲你移动系统怎么实现的」将无法回答。本项目核心卖点恰是这些系统自研 |
| FinalIK | ❌ 不用 | 成本高、Demo 价值低；TP 持枪姿势用动画包自带姿势即可 |
| Cinemachine | ⚠️ V1 不用 | FP 相机手写更可控更好讲（sway/bob/recoil 都是自己写的）；若时间富余可用于死亡观 cam |

**总原则**：插件提供地基（网络传输、Lua VM、动画播放），业务层（gameplay 规则/同步策略/状态机设计）必须自研且能逐行讲解。Animancer 与 FishNet 同属「地基」类：替换它们不动摇业务架构。

## 18. Senior Review（面试官视角）

**像真实工程项目吗？** —— 是，且结构上是国内中大型项目常见形态：网络同步策略自研于插件之上、服务器权威战斗、状态/事件二分、Lua 数值层、HTTP 账号服。流程闭环（登录→对战→成长）给了完整「商业感」叙事。

**容易被认为「插件拼装」的部分**（要主动防御）：
- 登录/HTTP 部分（模板感强）→ 讲清 JWT 流程与信任边界取舍
- FishNet Pro + Animancer 都是付费插件，容易被质疑「堆插件」→ **主动展示自研部分**：AnimDriver 的状态→clip 映射代码、CombatResolver 单点判定、三 FSM 门控矩阵、ActionSystem 打断规则——证明插件只是地基，业务全自研
- NetworkTransform 直同步（如果 prediction 回退了）→ 必须能讲「为什么可以不用」以及「用的话怎么做」
- 大厅 UI（无技术含量）→ 一句话带过，别花面试时间

**体现个人能力的部分**（面试主打）：
1. State Ownership 表 + 单写者原则（直接回应真实工程痛点）
2. 三 FSM 正交分解 + 门控矩阵 + 打断优先级（§6，有理论有取舍）
3. 「网络同步 Action 语义而非动画」的三端一致性流程（§6.6，本项目最独特的讲解点）
4. ActionSystem 与动画解耦（RE4 踩坑→本项目的防御设计，**最好的成长叙事**）
5. 状态同步 vs 事件同步的划分与开火全链路
6. 服务器权威 + 验证点清单（FireRequest 校验什么）
7. Lua/C# 边界（白名单式纯函数暴露）
8. asmdef 编译期架构隔离

**应砍**：手雷（候选）、MatchRecord（可选）、死亡观战等一切锦上添花。
**加分项**：Prediction 跑通（哪怕基于官方 demo 改造）、EF Migration、热更演示视频、架构图文档。

**「为什么这样设计」应答框架（背熟）**：
- 为什么 FishNet 不用 NGO/Mirror/Fusion？→ 源码可读性/Pro 工具链（Prediction+LagComp）/授权与学习曲线权衡（§2 表）
- 三个 FSM 为什么分开、不合成一个大状态机？→ 状态爆炸(≈96态)/三维度同步策略不同/行业惯例正交叠加；Fire 为何不是状态（§6.1）
- 网络怎么同步动画？→ **不同步动画，同步 Action 语义**：SyncVar 兜底 + 事件触发表现 + 本机预测去重（§6.6）
- 为什么用 Animancer 不用 AnimatorController？→ 资产图不可 diff/不可单测/AI 无法可靠编辑；Animancer 让状态→动画映射全部显式在代码，且它只是播放引擎，可整体替换（§7）
- 为什么服务器权威？→ 客户端权威在 FPS 意味着什么；哪些验证点必须在服务器（§5 表B）
- 为什么 ActionSystem？→ 讲 RE4 reload 卡死案例：真相在计时器，动画是表现（§6）
- 为什么 Lua 只放数值？→ 热更边界与风险控制；Lua 碰 Transform/网络对象会破坏权威模型（§12）
- Lag Compensation 为什么一行就能接入？→ CombatResolver 单点化（所有判定只在此发生）+ 讲 history buffer/回滚射线原理（§9）
- 为什么战绩客户端自报？→ 信任边界取舍，正确方案是什么（§11）
