## 4. 职责与数据边界

| 数据/状态 | 权威来源 | 持久化位置 | Unity 职责 |
|---|---|---|---|
| 账号、密码哈希、登录时间 | 后端 | MySQL | 提交凭据、保存短期登录态、处理错误 |
| 等级、XP、技能点 | 后端 | MySQL | 展示、请求升级/结算 |
| 金币余额 | 后端 | `PlayerWallet` | 只展示服务端返回值，不本地加减 |
| 金币变化历史 | 后端 | `WalletLedger` | 不提供客户端直接写入入口 |
| 商品价格、等级门槛、启用状态 | 后端目录 | `CatalogItem` | 读取并渲染，不提交自定义价格 |
| 武器/配件所有权 | 后端 | `PlayerInventory` | 读取、筛选、发起购买 |
| 当前武器和配件装配 | 后端 | `PlayerLoadout` 与附件表 | 编辑草稿并提交版本化更新 |
| 武器模型、图标和预览 Prefab | Unity | ScriptableObject/Prefab | 通过稳定 `AssetKey` 映射展示 |
| 图形、音频、按键设置 | Unity 本地 | PlayerPrefs 或项目现有本地设置层 | 本地保存，不写数据库 |
| HUD 血量、弹药、准星和临时战斗状态 | Gameplay Runtime | 内存/网络运行态 | 订阅现有运行时状态，不写数据库 |
| 战后 XP/金币结果 | 后端结算 | MySQL | 使用幂等比赛 ID 提交并展示结果 |

禁止 Unity 客户端成为价格、余额、等级门槛、购买结果或比赛奖励的权威来源。

## 5. 数据库与迁移设计

### 5.1 迁移原则

- 不再修改 `20260827120000_InitialCreate`。
- 为项目建立本地 `.config/dotnet-tools.json`，固定与项目兼容的 `dotnet-ef` 8.0.x 版本；不得继续手写缺少 Designer/Metadata 的迁移。
- 新增前向迁移，建议名称：`AddEconomyInventoryShopAndAttachments`。
- 先在 `unitylowpolyfps_test` 应用并运行完整集成测试，再应用到开发库。
- 操作测试库前必须解析连接串并断言数据库名严格以 `_test` 结尾。
- 禁止删除、重建或清空开发库；任何可破坏性重置只允许作用于已验证的测试库。
- 生产/多实例场景不依赖每个 API 实例自动迁移；本地开发可保留启动迁移，部署设计改为独立迁移步骤。

### 5.2 新增 `CatalogItem`

统一保存武器、配件和投掷物目录：

- `ItemId varchar(64)`：稳定业务主键。
- `ItemType`：Weapon、Attachment、Throwable。
- `SlotType`：Primary、Secondary、Optic、Muzzle、Magazine、Tactical 等。
- `DisplayName varchar(64)`。
- `Description varchar(512)`。
- `AssetKey varchar(128)`：映射 Unity 资源，不使用显示名做关联。
- `PriceCoins bigint`，不得小于 0。
- `UnlockLevel int`，不得小于 1。
- `MaxStack int`。
- `IsActive bool`。
- `DataVersion bigint`。
- `UpdatedAtUtc datetime(6)`。

必要索引：

- `(ItemType, IsActive, UnlockLevel)`。
- `(SlotType, IsActive)`。
- `AssetKey` 唯一或至少受唯一约束保护。

商品下架使用 `IsActive=false`，禁止物理删除已产生购买历史的目录项。

### 5.3 新增 `PlayerWallet`

- `UserId bigint`：PK，同时 FK 到 `UserAccount.Id`。
- `BalanceCoins bigint`：当前金币余额，不得为负。
- `Version bigint`：并发版本，默认 1。
- `UpdatedAtUtc datetime(6)`。

金币的数据库字段以 `PlayerWallet.BalanceCoins` 为唯一余额真相；API/Unity 对外字段名统一为 `coins`。

### 5.4 新增 `WalletLedger`

- `Id bigint`：PK。
- `UserId bigint`。
- `DeltaCoins bigint`。
- `BalanceAfter bigint`。
- `OperationKind varchar(32)`：StarterGrant、MatchReward、ShopPurchase、AdminGrant 等。
- `ReferenceId varchar(64)`。
- `IdempotencyKey varchar(64)`。
- `PayloadHash varchar(64)`。
- `CreatedAtUtc datetime(6)`。
- 可选 `MetadataJson`，限制长度。

唯一索引：

- `(UserId, OperationKind, IdempotencyKey)`。
- 需要全局业务 ID 的操作增加 `(OperationKind, ReferenceId)`。

### 5.5 新增 `PlayerInventory`

- `UserId bigint`。
- `ItemId varchar(64)`。
- `Quantity int`。
- `Version bigint`。
- `UpdatedAtUtc datetime(6)`。

主键为 `(UserId, ItemId)`；武器和非消耗型配件数量只能为 0 或 1。

### 5.6 新增 `ShopPurchase`

- `PurchaseId char(36)` 或后端统一 UUID 类型。
- `UserId bigint`。
- `ItemId varchar(64)`。
- `Quantity int`。
- `UnitPriceCoins bigint`。
- `TotalPriceCoins bigint`。
- `Status varchar(24)`。
- `IdempotencyKey varchar(64)`。
- `PayloadHash varchar(64)`。
- `CreatedAtUtc datetime(6)`。
- `CompletedAtUtc datetime(6)`。

唯一索引：

- `(UserId, IdempotencyKey)`。

查询索引：

- `(UserId, CreatedAtUtc, PurchaseId)`。

购买历史必须保存成交时价格，不能使用目录当前价格反算历史。

### 5.7 新增 `WeaponAttachmentCompatibility`

- `WeaponId varchar(64)`。
- `AttachmentId varchar(64)`。
- `SlotType varchar(24)`。
- `IsImplemented bool`：区别“设计上兼容”和“当前项目已有可用挂点/资源”。
- `CalibrationKey varchar(128)`：Unity 侧校准配置键。

复合主键：`(WeaponId, AttachmentId, SlotType)`。

反向索引：`(AttachmentId, WeaponId)`。

只有 `IsImplemented=true` 的组合可以保存为实际装配；其他组合可以显示为“暂未适配”，不得提交。

### 5.8 修改 `PlayerLoadout` 并新增附件装配表

`PlayerLoadout` 新增：

- `Version bigint`，默认 1。
- 保留 `UpdatedAtUtc`。

新增 `PlayerLoadoutAttachment`：

- `LoadoutId bigint`。
- `UserId bigint`。
- `WeaponSlot varchar(24)`。
- `AttachmentSlot varchar(24)`。
- `AttachmentItemId varchar(64)`。
- `UpdatedAtUtc datetime(6)`。

主键：`(LoadoutId, WeaponSlot, AttachmentSlot)`。

装备前必须同时验证：

- 用户拥有武器；
- 用户拥有配件；
- 商品仍然有效；
- 武器与配件兼容；
- 槽位匹配；
- 该兼容组合已真实实现；
- `ExpectedVersion` 与数据库版本一致。

### 5.9 修改 `MatchRecord`

新增：

- `ClientMatchId varchar(64)`。
- `PayloadHash varchar(64)`。
- `CoinsEarned bigint`。
- 可选 `SettlementStatus varchar(24)`。

唯一索引：`(UserId, ClientMatchId)`。

历史数据需要回填稳定的 `legacy-{Id}`，再增加非空和唯一约束。

### 5.10 注册与旧数据回填

注册事务必须一次性创建：

- `UserAccount`
- `PlayerProfile`
- `PlayerWallet`
- `PlayerLoadout`
- M4 初始库存
- AK 初始库存
- 现有默认副武器库存（若 Gameplay 仍要求副武器槽非空）
- 初始金币流水（仅当配置的 `StarterCoins > 0`）

对已有用户执行幂等回填：

- 创建缺失钱包，余额采用配置的旧用户补偿值。
- 将已有配装中的合法武器写入库存。
- 增加 M4、AK 初始所有权，不重复插入。
- Profile/Loadout/Inventory 版本设为 1。
- 历史比赛 `CoinsEarned=0`，补齐 legacy 幂等键。

## 6. 武器身份、初始解锁和目录规则

业务 ID 与 Unity 资源名分离：

- `weapon.m4`
- `weapon.ak`
- `weapon.service_pistol`

当前资源没有明确证明哪一个模型就是 M4 或 AK。为保证实施不中断，采用可替换的临时映射并集中放在目录 Seed/Unity Catalog 中：

- `weapon.m4` 暂映射 `rifle.day3 / Assault_Rifle_01`。
- `weapon.ak` 暂映射 `rifle.02 / Assault_Rifle_02`。
- 如果实施者从模型外观或现有定义中获得更可靠证据，可以调整 `AssetKey`，但不得更改稳定业务 ID。

规则：

- M4、AK 是仅有的初始解锁“主武器/步枪”。
- 现有 Service Pistol 可以保留为初始副武器，它不计入“初始解锁步枪”数量。
- 其他主武器全部设置 `UnlockLevel > 1` 或 `PriceCoins > 0`，购买前不可装备。
- 等级达到只表示获得购买资格，不自动获得武器。
- 价格和等级门槛只能来自服务端目录。
- 初始金币、比赛金币公式、武器价格和等级门槛必须集中配置并有测试，不散落硬编码。

## 7. 后端 API 与事务规则

### 7.1 必须提供的 API

- `POST /api/auth/register`
- `POST /api/auth/login`
- `GET /api/profile`
- `PUT /api/profile/upgrades`
- `GET /api/shop/catalog`
- `GET /api/inventory`
- `POST /api/shop/purchases`
- `GET /api/loadout`
- `PUT /api/loadout`
- `GET /api/loadout/attachments`
- `PUT /api/loadout/attachments`
- `POST /api/matches`
- `GET /health` 或等价的后端/数据库健康探针

### 7.2 商城购买

请求至少包含：

```json
{
  "itemId": "weapon.example",
  "quantity": 1,
  "idempotencyKey": "uuid"
}
```

同一 MySQL 事务中完成：

1. 校验幂等键。
2. 校验商品存在、启用、等级、数量和所有权。
3. 使用原子条件更新或显式行锁扣除钱包余额。
4. 写入购买记录。
5. 写入库存。
6. 写入金币流水。
7. 提交事务并返回余额与获得物品。

规则：

- 相同幂等键、相同请求：返回原结果，`replayed=true`。
- 相同幂等键、不同请求：返回 409。
- 非堆叠武器已拥有：返回稳定错误码，不再次扣款。
- 余额永远不得小于 0。
- 客户端提交的价格字段即使存在也必须忽略或拒绝。

### 7.3 比赛结算

- 使用 `ClientMatchId` 防止网络重试重复发 XP/金币。
- 服务端计算奖励；客户端战绩只能作为受约束输入。
- Profile、Wallet、MatchRecord、WalletLedger 在同一事务中更新。
- 统一锁顺序：Profile → Wallet → 幂等记录，避免死锁。

### 7.4 配装更新

- 请求携带 `ExpectedVersion`。
- 只有拥有的武器才能装备。
- 只有拥有、兼容且真实实现的配件才能装备。
- 版本过期返回 `409 LOADOUT_CONFLICT`，不得后写覆盖前写。
- 用户 ID 只从 JWT 获取，不接受请求体覆盖。

### 7.5 稳定错误码

至少包含：

```text
ECONOMY_INSUFFICIENT_COINS
ECONOMY_CONCURRENCY_CONFLICT
SHOP_ITEM_NOT_FOUND
SHOP_ITEM_INACTIVE
SHOP_LEVEL_REQUIRED
SHOP_ALREADY_OWNED
SHOP_INVALID_QUANTITY
SHOP_IDEMPOTENCY_CONFLICT
INVENTORY_NOT_OWNED
LOADOUT_ATTACHMENT_INCOMPATIBLE
LOADOUT_ATTACHMENT_SLOT_INVALID
LOADOUT_CONFLICT
MATCH_IDEMPOTENCY_CONFLICT
AUTH_INVALID_CREDENTIALS
SERVICE_UNAVAILABLE
```

## 8. Unity UI 全量范围

### 8.1 UI 架构要求

- 拆分现有 `LobbyBootstrap` 巨型职责，至少分为页面导航、视图组件、ViewModel/Presenter、API Client、资源目录和错误映射。
- 使用项目当前 UI 技术栈，不为追求形式引入新的大型 UI 框架。
- 修正 Input System：使用与项目配置一致的 `InputSystemUIInputModule` 或项目已有等价方案。
- API 调用必须可取消、可超时、可重试；页面销毁后不得继续写已销毁对象。
- 所有按钮在请求中进入禁用/忙碌状态，防止重复购买或重复保存。
- 统一加载遮罩、Toast、确认弹窗、错误弹窗和重试组件。
- 不允许以 release 路径中的假数据冒充后端成功；离线 Mock 只能通过显式开发开关启用。

### 8.2 视觉规范

参考视频采用：

- 青蓝/蓝绿色渐变背景；
- 半透明玻璃面板与细描边；
- 顶部主导航；
- 中央内容区配合右侧详情；
- 武器页面以 3D 武器为视觉中心；
- 商城/仓库使用规则物品网格和详情购买区；
- 属性使用横向进度条；
- 选中、锁定、已拥有、不可用状态具有明显区别。

必须适配：

- 1920×1080 基准分辨率。
- 16:9 与常见 16:10 窗口。
- Canvas Scaler、Safe Area、文字溢出和长用户名。
- 键鼠导航；若项目已有手柄输入则保留可扩展路径。

### 8.3 页面清单与验收状态

#### A. Boot/连接页

- 检查 API 可用性和版本兼容。
- 状态：连接中、成功、超时、服务器不可用、重试。

#### B. 登录页

- 用户名、密码、登录按钮、跳转注册。
- 状态：空输入、格式错误、提交中、401、网络错误、成功。

#### C. 注册页

- 用户名、密码、确认密码、注册按钮、返回登录。
- 状态：校验失败、用户名占用、提交中、成功自动进入大厅。

#### D. 首次昵称/身份确认

## 11. 测试与性能门槛

### 11.1 基础数据规模

- 基线：10,000 用户、100 个目录商品、每用户约 10 个库存物品、1,000,000 条比赛记录。
- 扩展：100,000 用户、500 个商品、5,000,000 条比赛记录。
- 压测预热 2 分钟、正式 10 分钟、冷却 1 分钟；基线通过后执行 30–60 分钟 soak。

### 11.2 必测并发场景

1. 同一用户 100 个并发请求购买同一非堆叠武器：只允许一次扣款和一次入库。
2. 100 个完全相同的幂等请求：只生成一个 PurchaseId、一条扣款流水和一次库存变化。
3. 相同幂等键购买不同商品：必须 409，余额和库存不变。
4. 同一比赛 ID 并发结算 100 次：XP 和金币只增加一次。
5. 余额只够一件商品时并发购买不同商品：最终余额不小于 0。
6. 50 个相同 `ExpectedVersion` 的配装更新：恰好一个成功，其余返回冲突。
7. A 用户伪造 B 用户的库存、购买或配装标识：全部拒绝。
8. 数据库瞬时断开后恢复：验证 EF 执行策略与手工事务组合不会重复提交。
9. 登录/注册单独压测 BCrypt work factor 12 对 CPU、线程池和吞吐的影响。

### 11.3 性能指标

- 档案/目录/库存读取：p95 ≤ 150 ms，p99 ≤ 400 ms。
- 商城购买/配装更新：p95 ≤ 300 ms，p99 ≤ 800 ms。
- 比赛结算：p95 ≤ 500 ms，p99 ≤ 1 s。
- 登录：p95 ≤ 800 ms，p99 ≤ 1.5 s。
- 非预期 5xx < 0.1%。
- 超时 < 0.05%。
- 正常负载连接池耗尽为 0。
- 正常负载无未处理死锁；若实现重试，最多 2–3 次并带抖动。
- 点查询必须命中唯一键/索引，扫描行数接近 1。
- 数据库连接数保持低于 `max_connections` 的 70%。

指标如果受本机硬件限制未达到，必须报告实际硬件、吞吐、瓶颈和可复现实验，不得直接删除或放宽指标后宣称通过。

### 11.4 压测后对账

- 钱包余额等于该用户金币流水的累计结果加初始化基线。
- 每个完成购买恰好对应一条扣款流水。
- 每条比赛奖励最多对应一条金币流水。
- 不存在负金币。
- 非堆叠物品数量不超过 1。
- 不存在孤儿购买、流水、库存或装配记录。
- 玩家不能装备未拥有武器或未拥有/不兼容配件。

## 12. 安全、操作与回滚边界

- 不得读取后打印 User Secrets；验证时只输出键是否存在、数据库名和脱敏后的连接结果。
- 不得将密码、JWT SigningKey 或完整连接串写入 `appsettings*.json`、Unity 资源、日志或 Git。
- 不得使用 MySQL root 权限作为正式设计前提；当前本地 root 只视为用户允许的临时开发条件。
- 不得对开发库执行 drop database、全库 truncate 或破坏性 Down。
- 测试库重建前必须二次校验精确数据库名和 `_test` 后缀。
- 已产生购买/流水数据后，回滚优先关闭功能、回滚服务代码并保留新增数据；不得直接用破坏性 Down 回滚开发数据。
- 不实现真实支付、充值、退款或第三方支付。
- 不声称当前客户端战绩上报已具备正式反作弊；比赛幂等与数值裁剪是本轮最低安全线。
- 不以 InMemory 测试结果替代 MySQL 事务、锁、FK、索引和性能验证。
