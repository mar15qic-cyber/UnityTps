## 2. 房间、地图与 TDM

### 2.1 房间规则

| 项目 | 冻结规则 |
|---|---|
| 容量 | 房主可选 2／4／8／12／16 人，两队平均上限 |
| 默认规则 | 16 人、100 杀、10 分钟 |
| 可选规则 | 50／100／150 杀；5／10／15 分钟 |
| 开局条件 | 双方至少一人；全部非房主已准备；房主点击开始视为本人准备 |
| 选边 | 等待期可自由选择未满队；换队取消本人准备 |
| 修改设置 | 仅房主可改；修改后清空所有准备 |
| 房主离开 | 自动移交给加入时间最早的成员 |
| 局中补人 | 可加入任一未满队，不强制人数平衡 |
| 局中换队 | 禁止 |
| 首版排除 | 密码房、踢人、观战 |

房主是房间管理身份，不是网络主机。房主离开不应停止仍满足继续条件的比赛。

### 2.2 生命周期

使用 `Waiting → Starting → InMatch → Returning → Waiting`，另设 `Closed`。

- Waiting：成员属于后端房间，不连接战斗 DS；保留心跳、准备和选边。
- Starting：冻结地图、模式、规则和队伍快照，原子租用 DS，签发个人一次性连接票据。
- InMatch：DS 权威管理队伍、比分、重生、补人和终局。
- Returning：结算只提交一次；断开战斗连接并回到原等待房间，清空准备。
- 最后一名成员离开时关闭房间；比赛结束释放 DS。

启动默认等待 60 秒。未成功连接者移出本轮参赛名单并取消准备；双方均有已加载玩家才进入 3 秒倒计时。无可用 DS 时保留等待房间和准备状态并允许重试。Starting 阶段拒绝新成员加入，避免启动名单变化。

每场比赛使用独立 `matchId` 和 generation。旧比赛的断线、退出、结算回调不得触碰新比赛或新连接。必须区分“离开战斗连接”和“离开房间”，返房不能调用会清空新会话的完整退房路径。

### 2.3 地图配置

新增地图目录，包含稳定 `mapId`、显示名、缩略图、场景标识、支持模式、容量上限和红蓝出生点组。首版目录只有 Arena，但界面和协议必须使用地图 ID，不能硬编码场景路径。

房主只能选择后端白名单、客户端和 DS 均支持的地图。开始时验证地图版本和容量；新地图通过目录、场景及出生点配置接入，不新增专用房间逻辑。

### 2.4 TDM 规则

- 敌方有效击杀使所属队伍加一分；自杀、环境死亡不增加对方分数。
- 达到击杀目标立即结束；时间结束按团队击杀比较，相同判平局。
- 关闭友伤；友军身体仍可阻挡子弹。
- 死亡 3 秒后自动重生，优先使用远离敌人的己方出生点；没有安全点时选最远点。
- 补人由 DS 验证队伍和容量后出生；Pending 连接计入名额，防止并发超员。
- InMatch 中一队参赛者归零，立即判另一队胜；双方同时归零则终止比赛，不虚构赢家。
- 局中退出或确认掉线者不获得之后产生的胜方奖励；补入玩家从入场时开始统计参与时长。
- 不新增中途退出后的战绩恢复；沿用同账号会话接管机制并防止旧代际误清理。

HUD 展示红蓝总分、目标、倒计时和队伍标签；战绩面板按队伍展示 K/D/A 与延迟。结算扩展团队胜负，个人统计仍由服务器生成，沿用既有奖励与幂等提交。

## 3. 聊天设计

### 3.1 交互

- 收起状态显示左下角最近 3 条；每条显示 8 秒，之后 2 秒淡出。
- 展开状态使用半透明深色底板，显示最近 30 条可滚动记录。
- Enter 打开全体频道；Shift+Enter 打开队伍频道。
- 输入法组合输入期间 Enter 只确认候选；发送成功后清空输入。
- Esc 关闭并保留草稿。
- 输入时封锁移动、视角、开火、ADS、换弹和切枪；关闭后释放输入占用。
- 死亡和结算界面仍可聊天；菜单打开时聊天让出焦点。
- 全体、队伍、系统消息使用不同标签；系统消息不能由客户端选择或伪造。
- 滚动历史时新消息不强制拉到底部，显示“新消息”提示。

### 3.2 传输与权限

等待房间没有 DS，采用鉴权 HTTP 发送和游标增量拉取；局内及 DS 尚未断开的结算阶段只允许 Owner 调用 `ServerRpc`。两种传输共享客户端消息模型和 UI，但不混用权限实现。

客户端请求只携带频道、正文和去重标识。身份、队伍、房间、时间和收件人由服务器决定。客户端频道仅允许 All／Team；System 由服务端内部构造并定向投递。队伍消息必须在网络投递层筛选，禁止全员广播后由客户端隐藏。

### 3.3 校验与历史

- 单条最多 100 个 Unicode 字符；拒绝空白、非法频道、换行和控制字符。
- 禁止正文富文本解析，避免 TMP 标签注入。
- 令牌桶容量 3，每 2 秒恢复 1 个额度；按账号和房间限频。
- 重复请求不重复显示；历史按服务器顺序排列。
- 每个接收者最多保留 30 条可见记录；新成员不补发此前历史。
- 同一房间返房可保留本地可见历史；离开房间清空。换队时清除旧队聊和队伍草稿。
- 历史不落数据库，不增加私聊、举报和长期审计后台。

系统消息覆盖进入／退出、准备、设置变更、开始失败、倒计时、队伍获胜和返房。

## 4. 实体倍率镜与 ADS

### 4.1 LPFP 瞄具适配

原厂 LPFP 资源保持只读，项目使用 `_Project` 派生资源。先建立瞄具适配表：镜片区域、镜身、光轴、分划、倍率和眼距。

LPFP 倍率镜存在淡蓝色不透明镜片。不得只在其上叠加 HUD 准星，也不得把整个瞄具材质改透明。可分离镜片使用项目镜片材质显示 RenderTexture；镜片与镜身共用网格和材质槽时，在项目副本中按明确选定的镜片三角面拆出镜片表面，保留镜身几何。使用镜片遮罩和深度关系，使镜内画面与分划只出现在有效镜口内。

红点／全息保留 1× 透视瞄具路径；中倍和高倍使用实体镜身 + 镜内独立画面。先完成当前装配中倍镜样板，再推广到全部正式可装备倍率镜和内置狙击镜。

### 4.2 镜内渲染

- ADS 保留枪模和镜身，移除旧的高倍率全屏遮罩与隐藏枪模路径。
- 在现有 ADS 姿态链中增加眼距和光轴补偿；不修改瞄具相对导轨安装校准，不添加第二个同时写武器根节点的驱动器。
- 镜内相机使用主视图的观察位置和朝向；只渲染世界，排除第一人称枪模、HUD 和镜片自身。
- 倍率只作用于镜内：`scopeFov = 2 × atan(tan(worldFov / 2) / magnification)`；镜外保持正常视野。
- 镜内分划中心与相机中心射线对齐；不宣称未实现的弹道归零。
- 首版优先稳定可瞄准，不模拟眼位偏轴黑边。
- 默认 RenderTexture 1024×1024，提供 512 档；只为本地活动瞄具启用一台镜内相机，退出 ADS、切枪、死亡和离场时关闭或释放。

视觉验收必须确认：看见镜身结构、镜内目标真实放大、中心刻度可见、淡蓝色镜片不遮挡敌人、分划居中、导轨安装位置未变化。不能用屏幕中心 HUD 准星替代。

## 5. 权威命中与枪口验证

将现有“射线查询并立即伤害”拆成查询最终命中和只提交一次伤害：

1. 服务器根据可信相机视点和实际射击方向计算相机候选 AimPoint，保留散布、后坐和霰弹逐弹丸逻辑。
2. 从服务器逻辑枪口向候选点做遮挡检测，忽略射手自身。
3. 无近处遮挡时使用相机候选命中；有遮挡时使用枪口路径最近命中。
4. 对最终结果只应用一次伤害；枪口已经伸进墙体时，增加身体侧可信锚点到逻辑枪口的穿墙检查。
5. 同一回溯窗口内完成两段查询，结束后恢复物理状态。
6. 客户端枪模位置、客户端提交的命中目标或最终 AimPoint 都不能成为权威事实。
7. 表现事件携带射击标识、最终点和弹丸结果；FP／TP 枪火、曳光和弹着从可见枪口连接到最终点，并对预测与服务器确认去重。

逻辑枪口来自服务器玩家姿态、武器配置和权威附件配置。保留现有冷却、弹药、动作和有限回溯验证。
